<objective>
Add the DB-level assertion — a PL/pgSQL trigger on every tenant-scoped table that raises an exception when `app.current_tenant` is not set. This is the second wall of the layered defense, protecting against any code path (present or future, in any language) that bypasses the middleware.

Purpose: Middleware protects HTTP handlers. RLS silently filters SELECTs. Neither catches a raw INSERT/UPDATE/DELETE in a debug script, migration, or new worker that forgot to set the tenant. The trigger catches it loudly. Combined with 17-01/02, this closes the write-path gap.

Output: Migration 000009 adds an `assert_tenant_scoped()` PL/pgSQL function and attaches it as a BEFORE trigger to all 9 multi-tenant tables. Down migration cleanly reverses.
</objective>

**Constraining decisions (from CONTEXT.md):**
- Mechanism: PL/pgSQL trigger over RLS-based check (triggers are explicit, easier to audit, don't affect query plans, and raise clear errors developers can act on)
- Scope: BEFORE INSERT/UPDATE/DELETE on tenant-scoped tables
- SELECTs are NOT protected by this trigger (Postgres triggers don't fire on SELECT); SELECTs remain protected by the RLS policies from migration 000008 (silent filter). This is the accepted design — SELECT footgun is contained to debugging pain; mutation footgun is contained to loud error.

**Tenant-scoped tables (from migration 000008):**
- organizations
- projects
- repositories
- ingestion_runs
- chunks
- queries
- retrievals
- feedback
- organization_memberships

**Not tenant-scoped (by design — do NOT attach trigger):**
- users (a user record must be creatable during signup, before an org exists to claim ownership)

**v2 door-keeping:**
- The `assert_tenant_scoped()` function is generic. Future graph tables added in v2 attach the same trigger with a one-line ALTER TABLE; no re-design needed.
</context>

  <action>
Create the up migration:

```sql
-- Function: raises exception if app.current_tenant is not set to a non-empty value
CREATE OR REPLACE FUNCTION assert_tenant_scoped() RETURNS trigger AS $$
BEGIN
  IF current_setting('app.current_tenant', true) IS NULL
     OR current_setting('app.current_tenant', true) = '' THEN
    RAISE EXCEPTION 'tenant isolation violated: app.current_tenant must be set for % on %',
      TG_OP, TG_TABLE_NAME
      USING HINT = 'See docs/isolation.md — call TenantScope() (Go) or require_tenant() (Python) before this operation.',
            ERRCODE = '42501';
  END IF;
  RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

COMMENT ON FUNCTION assert_tenant_scoped() IS
  'Second wall of tenant isolation. Fires BEFORE INSERT/UPDATE/DELETE on tenant-scoped tables. Middleware sets app.current_tenant; this function ensures no code path bypasses that requirement. See docs/isolation.md.';

-- Attach to each tenant-scoped table
CREATE TRIGGER trg_assert_tenant BEFORE INSERT OR UPDATE OR DELETE ON organizations
  FOR EACH ROW EXECUTE FUNCTION assert_tenant_scoped();
-- ... repeat for projects, repositories, ingestion_runs, chunks, queries,
-- retrievals, feedback, organization_memberships
```

Attach `trg_assert_tenant` to all 9 tables listed above. Do NOT attach to `users`.

Create the down migration:
```sql
DROP TRIGGER IF EXISTS trg_assert_tenant ON organizations;
-- ... for each of the 9 tables
DROP FUNCTION IF EXISTS assert_tenant_scoped();
```

Include a header comment in the up migration explaining: (a) what this does, (b) how to add the trigger to a future new table (one-line pattern), (c) why users is exempt.

Avoid: attaching to `users` (breaks signup flow). Avoid: firing on TRUNCATE (statement-level, needs separate trigger — out of scope; TRUNCATE not used in production paths).

Avoid: setting `current_setting('app.current_tenant', true)` with the `false` second argument — that itself raises an exception before our custom message can run. The `true` argument means "return NULL if unset" and lets our function raise the clearer message.
