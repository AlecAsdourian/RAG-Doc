<task type="auto">
  <name>Task 1: Isolation tests for /api/search</name>
  <files>services/backend/pkg/api/handlers/search_isolation_test.go</files>
  <action>
Create a test file using the 17-01 harness. Structure with subtests via `t.Run`:

Fixtures (via `WithTwoOrgs`):
- Org A has repository `repo-a` with a chunk containing "orange marmalade recipe"
- Org B has repository `repo-b` with a chunk containing "purple velvet cake"

Insert chunks directly using `TenantScope` — bypasses the ingestion pipeline for test speed. Both chunks stored with correct `organization_id`.

Scenarios (each a subtest):
1. **Org A queries own repo** — POST /api/search with Org A's owner JWT, `{"query": "orange", "repository_id": "repo-a"}`. Expect: 1 result, org A's chunk.
2. **Org B queries own repo** — POST as Org B, `{"query": "purple", "repository_id": "repo-b"}`. Expect: 1 result, org B's chunk.
3. **Cross-tenant repo access blocked** — POST as Org B, `{"query": "orange", "repository_id": "repo-a"}`. Expect: either 403 (repo not owned by org) or 200 with empty results. Test asserts BOTH acceptable outcomes but distinguishes: if handler returns 200 with data, that's a leak — FAIL.
4. **Missing tenant claim rejected** — POST with a JWT that has no `organization_id` claim. Expect: 400 or 401 (middleware rejects before handler).
5. **JWT tampering (org substitution)** — Sign a JWT for user in Org A but with `organization_id` claim swapped to Org B. Middleware should either reject (signature mismatch would catch this in prod, but test-JWT signs whatever we give it, so this test verifies handler doesn't blindly trust the claim). Assert either 403 or that returned data is Org B's, never a mix.

Use `AssertNoCrossTenantLeak(t, pool, orgA, orgB, insertChunk, searchAsOrgB)` for scenario 3 as the canonical wrapper.

Wire the test to spin up a real HTTP server via `httptest.NewServer(router.New(...))` — do NOT test the handler function directly, test through the router so middleware chain is exercised.

Avoid: mocking the Python RAG service. Use the real service running from docker-compose (workers-test profile) OR stub the RAG client with a fake that echoes back tenant filter — the goal is to test Go's tenant scoping, not Python's (that's 17-04). Choose approach based on speed; stub is fine here.
  </action>

`cd services/backend && go test ./pkg/api/handlers/... -run TestSearchIsolation -v` — all 5 subtests pass. If any FAIL because of a real leak: STOP, fix the leak in `search.go` or `rag_client.go`, re-run. Do not proceed to Task 2 until all pass.
  </verify>
