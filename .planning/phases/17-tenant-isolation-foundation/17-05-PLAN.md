**Constraining decisions (from CONTEXT.md):**
- Scanner language: Python 3 (portable, no npm/deno needed, standard on GitHub Actions runners)
- Endpoint detection: regex on git diff for Go route registrations (`r.Post`, `r.Put`, `r.Patch`, `r.Delete`, `chi.HandleFunc` with method) and Python FastAPI decorators (`@router.post`, `@router.put`, `@router.patch`, `@router.delete`, or `@app.post/put/patch/delete`)
- Test file matching: for each detected endpoint at `foo/bar_handler.go` adding `POST /api/repositories`, expect a modified/new file matching `*_isolation_test.go` (Go) or `test_*_isolation.py` (Python) in the same PR that references the handler function name or route path
- Escape-hatch marker: `// @skip-isolation-test: <reason>` (Go) or `# @skip-isolation-test: <reason>` (Python) on the route registration line; reason is REQUIRED (empty reason still fails)
- Scanner behavior: exit 0 if all mutation endpoints covered or skip-hatched; exit 1 with structured output listing missing coverage otherwise

**v2 door-keeping:**
- Scanner is table-driven for endpoint patterns. When v2 adds new frameworks (e.g., MCP server endpoints), extending the scanner is a one-line addition to a pattern registry.

  <action>
Create `scripts/ci/check-isolation-tests.py`:
- Argparse: `--base-ref` (default `origin/main`), `--head-ref` (default `HEAD`), `--verbose`, `--json` (structured output for PR comment generation)
- Uses `subprocess` to run `git diff --unified=0 <base>...<head> -- '*.go' '*.py'`
- Parses diff into (file, added_lines) tuples
- Pattern registry (module-level dict):
  ```python
  ENDPOINT_PATTERNS = {
      "go":     [r'^\+.*r\.(Post|Put|Patch|Delete)\s*\(\s*"([^"]+)"',
                 r'^\+.*chi\.HandleFunc\s*\(\s*"(POST|PUT|PATCH|DELETE)\s+([^"]+)"'],
      "python": [r'^\+\s*@(?:router|app)\.(post|put|patch|delete)\s*\(\s*[\'"]([^\'"]+)[\'"]'],
  }
  SKIP_PATTERN = r'@skip-isolation-test:\s*(\S.*?)(?:$|\*/)'  # non-empty reason required
  TEST_FILE_GLOBS = {
      "go":     ["**/*_isolation_test.go"],
      "python": ["**/test_*_isolation.py", "**/*_isolation_test.py"],
  }
  ```
- For each detected mutation endpoint (path, method, source_file, source_line):
  - Check if the same line (or the 3 lines above/below within the diff hunk) contains a skip marker; if yes, extract reason, record as skipped
  - Check if ANY test file in the same PR (modified or added, matching test globs) contains a string reference to the path OR the handler function name (extract handler name via a follow-up regex on the same file)
  - If neither: record as missing coverage
- Print human-readable report (missing endpoints, skipped endpoints with reasons)
- If `--json`, also emit JSON to stdout for downstream consumption
- Exit 0 if all covered/skipped; exit 1 otherwise

Create `scripts/ci/test_check_isolation.py` with pytest scenarios:
1. Diff adds `r.Post("/api/foo", handler)` with no matching test → exit 1, reports `/api/foo`
2. Same diff BUT adds `foo_isolation_test.go` that mentions "/api/foo" → exit 0
3. Diff with `// @skip-isolation-test: exempt because health` → exit 0, reports skipped with reason
4. Diff with `// @skip-isolation-test:` (empty reason) → exit 1 (empty reason not allowed)
5. Python: `@router.post("/api/bar")` with no test → exit 1
6. Python: same with a `test_bar_isolation.py` containing "/api/bar" → exit 0
7. Non-mutation route (`r.Get(...)`) → exit 0 regardless (isolation matters most on mutations; reads are RLS-covered)

Feed synthetic diffs into the tests using temp git repos or fixture diff strings.

Create `scripts/ci/requirements.txt` — just standard library (no external deps ideally; if regex isn't enough, add pytest to dev only). Create `scripts/ci/README.md` explaining local usage: `python scripts/ci/check-isolation-tests.py --base-ref main` from repo root.

Avoid: parsing Go or Python ASTs. Regex on diffs is sufficient, ~100x faster, and easier to maintain. Miss cases (e.g., dynamically registered routes) are acceptable — those are rare and the reviewer catches them.

Avoid: making the script online (no git fetch inside). It runs against a diff the CI runner has already fetched.

<task type="auto">
  <name>Task 2: GitHub Action wiring</name>
  <files>.github/workflows/isolation-check.yml</files>
  <action>
Create the workflow:

```yaml
name: Isolation Test Coverage

on:
  pull_request:
    branches: [main]

jobs:
  check-isolation:
    runs-on: ubuntu-latest
    timeout-minutes: 3
    steps:
      - name: Checkout with full history
        uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - name: Run isolation-test scanner
        id: scan
        run: |
          python scripts/ci/check-isolation-tests.py \
            --base-ref origin/${{ github.base_ref }} \
            --head-ref HEAD \
            --json > isolation-report.json
        continue-on-error: true
      - name: Comment on PR if missing coverage
        if: steps.scan.outcome == 'failure'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const report = JSON.parse(fs.readFileSync('isolation-report.json', 'utf8'));
            const body = [
              '❌ **Isolation test coverage missing**',
              '',
              'The following mutation endpoints were added or modified without a matching isolation test:',
              '',
              ...report.missing.map(m => `- \`${m.method} ${m.path}\` in \`${m.file}:${m.line}\``),
              '',
              'Add a test in `*_isolation_test.go` (Go) or `test_*_isolation.py` (Python) that references the endpoint path or handler name.',
              '',
              'To intentionally skip (rare): add `// @skip-isolation-test: <reason>` (Go) or `# @skip-isolation-test: <reason>` (Python) on the route line, with a non-empty reason.',
              '',
              'See `docs/isolation.md` for the pattern.',
            ].join('\n');
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body,
            });
      - name: Fail if missing coverage
        if: steps.scan.outcome == 'failure'
        run: exit 1
```

Adds fast-fail behavior — the scanner runs in <30s and blocks merge on missing coverage before any heavier test suite runs.

Avoid: running the full test suite in this workflow — that's a separate workflow (Phase 24 CI/CD sets up the full pipeline). This workflow does exactly one thing: check isolation coverage on the diff.

Create `docs/isolation.md`. Structure:
1. **Overview** — the three walls (middleware / DB trigger / isolation tests + CI gate). One paragraph each explaining what it does and when it fires.
2. **Writing a tenant-scoped handler (Go)** — code example using TenantMiddleware; note that any handler under the auth middleware chain gets `app.current_tenant` set automatically; if you write raw SQL outside the middleware chain (e.g., a background job), wrap it in `TenantScope`.
3. **Writing a tenant-scoped worker (Python)** — code example using `require_tenant(pool, tenant_id)`; every function touching tenant-scoped tables MUST accept a tenant_id and use `require_tenant`; the 000009 trigger will raise if you forget.
4. **Writing an isolation test** — Go example using `WithTwoOrgs` + `AssertNoCrossTenantLeak`; Python example using the `with_two_orgs` fixture + `assert_no_cross_tenant_leak`.
5. **CI gate** — how the scanner works; how to make a PR pass (add a test); how to escape (rarely — `@skip-isolation-test: <non-empty reason>`).
6. **Adding a new tenant-scoped table** — one-line pattern for attaching the trigger; add to the harness fixture's population list; add to the DB assertion test's table-driven list.
7. **Troubleshooting** — common errors and what they mean:
   - `tenant isolation violated: app.current_tenant must be set for INSERT on chunks` → you forgot to wrap in `require_tenant` / `TenantScope`
   - Empty SELECT results in dev → check `SET app.current_tenant`; RLS silently filters
   - Isolation test passes but data leaks in staging → the test might not be exercising the real middleware chain — use `httptest.NewServer` over calling the handler directly
