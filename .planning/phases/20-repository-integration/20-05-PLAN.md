<objective>
Receive GitHub webhooks, verify their signatures, and turn them into durable work items. Phase 21 builds the queue that consumes them; this plan makes sure nothing is lost before it exists.

Output: `POST /webhooks/github`, HMAC-SHA256 verification, handlers for `push` / `installation` / `installation_repositories`, and idempotent delivery handling.
</objective>

**Use the captured payloads from 20-02 finding E.** They are real deliveries from the real App. Do not hand-write fixtures from the documentation — that is how a test suite ends up agreeing with itself and disagreeing with the sender, which is what 19-03's flat-vs-nested claim bug was.

**`pkg/auth/webhook.go` is the local precedent** and has already been through two review rounds. Carry over what it learned:
- Verify the signature over the RAW body, before parsing. Use `hmac.Equal`, never `==`.
- Fail closed: the constructor panics on an empty secret rather than accepting unsigned deliveries.
- Bound the body with `http.MaxBytesReader` before reading it.
- **Do not add a per-IP rate limit.** It was tried in PR #13 and removed: with `middleware.RealIP` in the chain the "IP" is a client-supplied header. Signature verification is the control.

**The lesson that shapes this plan most** — from 19-03's blocker: *do not assume a delivery mechanism will retry.* GitHub does redeliver failed webhooks, unlike Supabase, but a design that relies on that is one vendor behaviour change from silent data loss. Make the handler recoverable without redelivery.

<task type="auto">
  <name>Task 1: Receiver and signature verification</name>
  <files>services/backend/pkg/api/handlers/github_webhook.go</files>
  <action>
**`POST /webhooks/github`**, public (no JWT — GitHub has no token of ours), authenticated entirely by the signature.

1. `http.MaxBytesReader` first. Push payloads on a large repository are not small.
2. Read the raw body.
3. Verify `X-Hub-Signature-256` = `sha256=<hex>` HMAC over the raw bytes with `GITHUB_WEBHOOK_SECRET`, using `hmac.Equal`. Confirm the exact format against 20-02 finding F rather than assuming it matches Supabase's.
4. Only then parse.
5. Dispatch on `X-GitHub-Event`.

Return 202 for handled events and 202 for ignored ones — an unrecognized event is not an error, and 4xx-ing it fills GitHub's delivery log with red for events we simply do not care about.

`GITHUB_WEBHOOK_SECRET` required at construction; panic if empty, per 19-01.

Mark the route `// @skip-isolation-test:` with a real reason — it is signature-verified and resolves its own tenant, exactly like the Supabase webhook. Put the marker on the route line itself, not a neighbouring one: 19-04's review found a marker on an adjacent GET that the scanner never reads, which was one reformat from silently un-gating a route.
  </action>
  <verify>Valid signature accepted; invalid, missing, and truncated rejected with 401; oversized body rejected before parsing; empty secret panics at construction. Mutation-check the signature verification: replace `hmac.Equal` with `==` and confirm a test fails.</verify>
  <done>Only GitHub can deliver events.</done>
</task>

<task type="auto">
  <name>Task 2: Idempotency</name>
  <files>services/backend/migrations/000011_webhook_deliveries.up.sql, github_webhook.go</files>
  <action>
GitHub redelivers, and the **Redeliver** button in the App UI is a normal part of development, so duplicate deliveries are routine rather than exceptional.

Record `X-GitHub-Delivery` (a UUID, per finding E) in a `github_webhook_deliveries` table with a UNIQUE constraint, and treat a duplicate as success — 202, no reprocessing.

This table is **not** tenant-scoped: a delivery arrives before we know which tenant it belongs to, and some events (installation deleted) concern a tenant that is going away. Say so in the migration comment, because every other new table this phase adds does get RLS and the inconsistency will otherwise read as an oversight. Add a retention note — this table grows forever otherwise.
  </action>
  <verify>Delivering the same payload twice produces one effect and two 202s. Concurrent duplicate delivery does not double-process — test it, do not reason about it.</verify>
  <done>Redelivery is safe.</done>
</task>

<task type="auto">
  <name>Task 3: Event handlers</name>
  <files>services/backend/pkg/api/handlers/github_webhook.go</files>
  <action>
Three events, using the captured payloads as fixtures.

**`installation`** — `created` is normally redundant (the callback already linked it) but must be handled: a user can install from GitHub's directory without ever hitting our callback, and that installation has no organization to link to. **Decide what happens to an orphan installation** and write it down; the tempting answer, linking it to whichever organization the last caller belonged to, is a cross-tenant bug.
`deleted` → mark the installation gone and decide the fate of its repositories (recommendation: keep them, mark unsyncable — an accidental uninstall should not delete a user's ingested history).
`suspend` / `unsuspend` → set `suspended_at`.

**`installation_repositories`** — `added` / `removed`. `removed` means we lost access, not that the repository is gone; do not delete rows.

**A webhook cannot populate a `repositories` row on its own.** Verified
2026-09-08 (20-02 finding E): the `repositories` array in these payloads
is a REDUCED shape — `id`, `node_id`, `name`, `full_name`, `private` — with
**no `size`, `default_branch`, `visibility`, or `archived`**. Record the
ids and mark them as needing detail; fetching the full payload requires an
API call with an installation token. Decide where that fetch happens
(inline here, or as work for Phase 21) and write it down — doing it inline
makes webhook processing depend on GitHub being reachable, which is a
different reliability posture than recording intent.

**Handle `ping`.** GitHub sends one when the App is created. It carries no
`action` and no installation. Answer 202; do not let it show as a failure
in the App's delivery log, which is the first thing anyone looks at when
webhooks seem broken.

**`push`** — mark the repository as needing a sync. Ignore pushes to branches other than the repository's `default_branch`; ingesting every feature branch is not the product.

**All of these record intent, not work.** The queue is Phase 21. Set `sync_state` and `last_synced_at`; do not spawn goroutines to do the work — a goroutine started here dies with the process and takes the only record of the work with it.
  </action>
  <verify>Table-driven tests over the real captured payloads. Each asserts the database end state, not just the status code.</verify>
  <done>The three events we subscribed to are handled and recorded.</done>
</task>
