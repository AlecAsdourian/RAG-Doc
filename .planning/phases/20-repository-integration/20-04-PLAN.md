<objective>
The installation flow: send a user to GitHub to install the App, handle the callback, and link the resulting installation to exactly one of our organizations.

This is where a GitHub-side fact becomes a tenant-side fact, so it is an authorization boundary, not plumbing.

Output: `GET /api/github/install`, `GET /api/github/callback`, and an endpoint listing what an installation can see.
</objective>

**Depends on 20-02** for the verified installation payload shape and the GitHub client.

**Locked:** one installation serves exactly one organization, enforced by the UNIQUE constraint on `github_installations.github_installation_id`.

**Two prior lessons that apply directly here:**

1. **CSRF state is not optional** (ISS-003, Phase 4). The install redirect must carry a single-use state token, and the callback must validate it. `pkg/auth/state_store.go` already implements exactly this against Redis, single-use with a 5-minute TTL — use it rather than writing a second one. This is the reason 20-CONTEXT kept the StateStore probe alive.

2. **The claim-less window** (19-03/19-04). A user who has just installed the App is authenticated and has an organization, so this is simpler than the signup case — but the callback must still resolve the caller's organization from their verified JWT claim, never from a query parameter.
</context>

**`GET /api/github/install`** — authenticated. Generates a state token bound to the caller's organization, stores it via `auth.StateStore`, and redirects to:

```
https://github.com/apps/{GITHUB_APP_SLUG}/installations/new?state={token}
```

The state token is what carries the organization across a round trip through GitHub. Bind it to the organization id server-side; do not put the organization in the URL, where the user can edit it.

`GITHUB_APP_SLUG` comes from configuration (`docs/github-app-setup.md` step 3). Fail at construction if it is unset — the 19-01 fail-closed pattern. A router that starts without it serves a redirect to a nonexistent GitHub App.

<task type="auto">
  <name>Task 2: Callback — the authorization boundary</name>
  <files>services/backend/pkg/api/handlers/github_install.go</files>
  <action>
**`GET /api/github/callback?installation_id=...&state=...&setup_action=...`**

**Mount this OUTSIDE `JWTAuthMiddleware`.** Verified 2026-09-08: the path
currently falls inside the authenticated `/api` group and returns **401**
to GitHub's redirect, because a browser following a redirect sends no
`Authorization` header. A callback mounted there fails 100% of the time.
The state token is the only credential on this request, which is exactly
why it must be single-use and organization-bound.

**A missing `state` must be refused, not defaulted.** Verified: installing
from GitHub's "Install App" button produces a redirect with
`installation_id` and `setup_action` but **no `state`**. Falling back to
"the caller's current organization" in that case would link an
installation to whoever happened to be logged in — and on a public route
with no JWT, there is no caller. Refuse and tell the user to start from
the in-app install button.

Order matters, and it is the whole security argument:

1. **Validate the state token first.** Invalid, expired, or already-used → refuse. Single-use is what makes replay impossible; `StateStore` already deletes on validate.
2. **Resolve the organization from the state token**, not from the request and not from the caller's current claim. The token was bound at install time; using it prevents a user who switched organizations mid-flow from linking the installation to the wrong tenant.
3. **Verify the installation exists and we can authenticate to it** — mint an installation token via 20-02's client. This proves the `installation_id` in the query string is real and ours, rather than a number someone typed.
4. **Persist**, and handle the UNIQUE violation on `github_installation_id` explicitly. Colliding means this installation is already linked to another organization. That is a **409 with an explanation**, not a 500 — it is a comprehensible situation (someone installed the App on a GitHub org another tenant already connected) and the operator needs to know which two tenants are involved. Log both; tell the user only that it is already connected, since naming the other tenant leaks its existence.
5. Redirect to the frontend with a result.

**Steps 1-3 must all pass before anything is written.** A callback that persists first and validates after is an open door: `installation_id` is an attacker-supplied integer.
  </action>
  <verify>Unit tests: bad state refused; reused state refused; unreachable installation refused; UNIQUE collision returns 409 rather than 500; the happy path writes exactly one row with the organization from the token.</verify>
  <done>An installation can only be linked by someone who started the flow, and only to the organization they started it from.</done>
</task>

<task type="auto">
  <name>Task 3: List installation repositories</name>
  <files>services/backend/pkg/api/handlers/github_install.go</files>
  <action>
**`GET /api/github/installations/{id}/repositories`** — what this installation can see, for a UI to pick from before calling `POST /api/repositories`.

Verify the installation belongs to the caller's organization **before** calling GitHub. Otherwise this becomes an oracle: an attacker enumerating installation ids would learn about other tenants' repositories, and would do it using our credentials and our rate-limit budget.

Pass through GitHub's pagination rather than accumulating everything server-side; an installation with 5,000 repositories should not become a 5,000-row response.
  </action>
  <verify>Isolation test: orgA requesting orgB's installation is refused, and the GitHub client is never called — assert on the mock, not just the status code. Refusing after the call still burns budget and still leaks timing.</verify>
  <done>A UI can list candidate repositories without becoming a cross-tenant oracle.</done>
</task>
