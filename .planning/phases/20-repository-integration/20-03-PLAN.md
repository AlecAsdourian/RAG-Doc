<task type="auto">
  <name>Task 1: Handlers</name>
  <files>services/backend/pkg/api/handlers/repositories.go, services/backend/pkg/api/router.go</files>
  <action>
Four endpoints, all under JWT auth AND the tenant middleware (unlike 19-04's user-scoped routes — these read tenant data, so they belong behind the tenant gate):

**`POST /api/repositories`** — connect a repository the caller's installation can see.
Body: `{"github_repo_id": 123, "installation_id": "<uuid>"}`. Deliberately NOT a git URL: the numeric id is stable across renames, and accepting a URL invites someone to pass a repository their installation cannot access. Validate that the installation belongs to the caller's organization, then that the repository is visible to that installation (via 20-02's client), then persist what GitHub reports.

**`GET /api/repositories`** — paginated. Use cursor pagination keyed on `(created_at, id)`, not `OFFSET`: offset pagination skips and duplicates rows under concurrent inserts, and repositories will be inserted by webhooks while a user pages.

**`GET /api/repositories/{id}`** — 404 for both "not found" and "another tenant's", indistinguishable.

**`DELETE /api/repositories/{id}`** — the open product question from 20-CONTEXT: what happens to ingested chunks. The FK cascade already defines the database behaviour; decide and document whether the API refuses when chunks exist, deletes them, or soft-deletes. **Whichever is chosen, say so in the plan summary** — a silent choice here is a data-loss surprise later.

Wire on the router inside the existing tenant-scoped group.

<task type="auto">
  <name>Task 2: Isolation tests</name>
  <files>services/backend/pkg/api/handlers/repositories_isolation_test.go</files>
  <action>
The 17-05 CI gate requires these for the mutation endpoints, and this is the first handler set touching RLS-scoped tables — the coverage matters more here than the gate does.

Using `WithTwoOrgs`:

1. **orgA lists, sees only orgA's repositories.** The baseline.
2. **orgA cannot GET orgB's repository by id** — 404, not 403, and identical to a nonexistent id.
3. **orgA cannot DELETE orgB's repository**, and orgB's row still exists afterward. Assert the row, not just the status code.
4. **orgA cannot connect a repository through orgB's installation** — the cross-tenant write, and the most important test in the file.
5. **A claim-less token is refused** before reaching a handler.
6. **Pagination does not leak across tenants** — fill both orgs past one page and confirm the cursor never walks into the other tenant's rows.

**Mutation-check at least scenarios 3 and 4**, per the standard from 19-03/19-04: break the scoping and confirm exactly those tests go red. If they stay green, they are asserting the absence of something that was never going to be present — the failure mode that shipped twice in Phase 19 before a reviewer caught it.

Note the trap 19-04 hit: sign tokens with `OwnerSupabaseID`, not `OwnerID`, for anything resolving `sub` back to a user row.
  </action>
  <verify>All scenarios pass; mutations produce targeted failures. CI scanner passes.</verify>
  <done>Cross-tenant access is proven impossible and proven to be detectable.</done>
</task>
