**Constraining decisions:**
- One installation serves exactly one organization — a UNIQUE constraint, not a convention.
- GitHub only. Columns are named `github_*`, honestly.
- The webhook secret is App-level configuration, not a database column.
- Record `visibility` / `size_bytes` / `default_branch`; enforce nothing.

**Read 19-03's summary before starting.** That phase's central lesson is the reason this plan exists in this order: a full plan was written against an assumed Supabase contract, and verification found the assumption architecturally impossible. The verification below is not a formality.

  <name>Task 1: Verify the GitHub contract against the live App (ISS-002 pattern)</name>
  <files>.planning/phases/20-repository-integration/20-02-PLAN.md (record findings inline)</files>
  <action>
Before designing anything, answer these against the real App. Record the actual observed values, not the documented ones, and mark each finding VERIFIED with a date.

**A. App authentication.** Mint an App JWT from the private key (RS256, `iss` = App id, ≤10 min expiry) and call `GET /app`. Confirm the key works and record the response shape.

**B. Installation token exchange.** `POST /app/installations/{id}/access_tokens`. Record: the token's TTL, its prefix, whether the response enumerates repositories or permissions, and what an expired App JWT returns (so the error path is known before it happens in production).

**C. What an installation actually looks like.** `GET /app/installations`. Record `account.login`, `account.type` (User vs Organization — both are possible and the schema must hold both), `repository_selection` (`all` vs `selected`), and any suspension fields.

**D. Repository payload shape.** `GET /installation/repositories` using the installation token. Record: the `id` (numeric, stable across renames — this, not the name, is the durable key), `full_name`, `private`, `size` (**confirm the unit — GitHub documents kilobytes, and storing it as `size_bytes` while it is actually KB is exactly the kind of silent unit error that survives for years**), `default_branch`, `archived`, `disabled`.

**E. Webhook payloads.** Use the App's Advanced → Recent Deliveries → Redeliver to capture real payloads for `installation` (created / deleted / suspend / unsuspend) and `installation_repositories` (added / removed). Save the redacted bodies. Record which headers carry the signature (`X-Hub-Signature-256`), the event type (`X-GitHub-Event`), and the delivery id (`X-GitHub-Delivery`) — the last is what makes webhook processing idempotent.

**F. Signature format.** Confirm `X-Hub-Signature-256` is `sha256=<hex>` over the **raw body**, and note that verification must happen before JSON parsing. This mirrors the Supabase webhook, but do not assume the two are identical.

**Write every answer into this plan file under a VERIFIED heading.** If any finding contradicts what this plan assumes, revise the plan before writing code — the 19-03 pattern.

<task type="auto">
  <name>Task 2: Resolve the repository-to-project question</name>
  <files>.planning/phases/20-repository-integration/20-02-PLAN.md</files>
  <action>
`repositories.project_id` is NOT NULL and references `projects`, but nothing creates projects, and the user-facing concept is "connect a repo to my organization". This must be settled before the migration.

Three options:

**A. Provisioning creates a default project per organization.** Smallest schema change; `projects` stays as the grouping layer it was designed to be. Requires backfilling existing orgs and extending `CreateOrganizationForUser`.

**B. `repositories` references `organization_id` directly**, and `project_id` becomes nullable or is dropped. Matches the product concept most directly. A bigger migration, and it discards a grouping layer that may be wanted later.

**C. Defer** by having the API create an implicit project on first repository connect. Hides the concept without removing it; risks two implicit projects racing.

Recommendation: **A**, because it is reversible and does not throw away a layer the product may want, and because RLS policies and the 000009 trigger are already written against the existing shape — changing the FK target means revisiting both, in a phase that has enough novelty already.

Decide, record why, and note what the migration must do about existing rows.
  </action>
  <verify>Decision recorded with reasoning and a migration consequence.</verify>
  <done>Task 3 knows what it is writing.</done>
</task>

<task type="auto">
  <name>Task 3: Migration</name>
  <files>services/backend/migrations/000010_github_integration.up.sql, .down.sql</files>
  <action>
**`github_installations`** — new, tenant-scoped:

- `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
- `organization_id UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE`
- `github_installation_id BIGINT NOT NULL UNIQUE` — the UNIQUE is what enforces one-installation-one-org. Comment it as such; it looks like a dedup constraint and is actually the tenancy boundary.
- `account_login TEXT NOT NULL`, `account_type TEXT NOT NULL` (User or Organization, per finding C)
- `repository_selection TEXT NOT NULL`
- `suspended_at TIMESTAMPTZ`, `created_at`, `updated_at`

**`repositories`** — new columns, all nullable so the migration does not break existing rows:

- `installation_id UUID REFERENCES github_installations(id) ON DELETE SET NULL` — SET NULL, not CASCADE: uninstalling the App should not delete the user's ingested data.
- `github_repo_id BIGINT` — the durable key. Unique per installation.
- `visibility TEXT`, `size_bytes BIGINT` (**name it for the unit finding D actually established**), `archived BOOLEAN NOT NULL DEFAULT false`
- `sync_state TEXT NOT NULL DEFAULT 'never_synced'`, `last_synced_at TIMESTAMPTZ`

Plus whatever Task 2 decided about `project_id`.

**RLS and the trigger are mandatory on `github_installations`.** It is tenant-scoped, so per `docs/isolation.md` it gets a policy in the 000008 style and `assert_tenant_scoped` in the 000009 style. Skipping this is the single most likely way to reintroduce a cross-tenant hole in this phase, and the CI scanner will not catch it — the scanner checks endpoints, not tables.

Grant the `rag_doc_app` role on the new table, matching `ensureAppRole` in the test harness, or every isolation test against it fails confusingly.

Write the `.down.sql` and **test it**: apply, roll back, re-apply. A down migration nobody has run is not a down migration.
  </action>
  <verify>`migrate up` then `down` then `up` against a scratch database, clean each time. The isolation harness applies it without error.</verify>
  <done>Schema exists, is tenant-scoped, and is reversible.</done>
</task>

<task type="auto">
  <name>Task 4: GitHub client</name>
  <files>services/backend/pkg/github/client.go, client_test.go</files>
  <action>
A small client covering what later plans need:

- `NewAppClient(appID, privateKeyPath)` — loads the key, fails at construction with a legible error if it is missing or malformed. This is a credential; the 19-03 `AdminClient` is the local precedent for how to handle one.
- `AppJWT()` — RS256, ≤10 minute expiry.
- `InstallationToken(ctx, installationID)` — exchanges for a token. **Never persist one**; they expire in an hour. Cache in memory with an expiry margin at most.
- `ListInstallationRepositories(ctx, installationID)` — paginated.

Carry over the two lessons from `pkg/auth/supabase_admin.go`, both of which were reviewer findings there and apply identically here:

- **Redact the private key and any token from error messages.** A proxy or WAF error page that echoes request headers will otherwise put a credential in the logs.
- **Refuse to follow redirects** (`CheckRedirect` returning `http.ErrUseLastResponse`). Go strips `Authorization` across hosts, but only for headers it knows about.

Set a request timeout. Do not add retry logic yet — Phase 24 owns rate limiting, and a naive retry against GitHub's budget is worse than none.
  </action>
  <verify>Unit tests with `httptest` cover: token minting, non-2xx handling, pagination, and that neither the key nor a token appears in any error string. Mutation-check the redaction — revert it and confirm the test fails.</verify>
