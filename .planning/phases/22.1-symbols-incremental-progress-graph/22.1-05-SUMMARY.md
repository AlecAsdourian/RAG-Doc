## 3. A-L3, before and after (S12)

`write_results` now runs a lock-free fence check first and attaches the run
**last** (`FENCE_CHECK_SQL`, `check_fence`), so the job row is locked only for
the final statements.

- **Before** (attach first): the row was locked for the whole store (330–463 s
  at the cap); 16 beats were cancelled with `57014` and the heartbeat twice
  logged a false "assuming it is lost".
- **After:** zero cancelled beats and zero false losses over every post-fix
  run; the longest beat 0.165 s.
- `test_a_long_store_never_blocks_its_own_heartbeat` failed on the unfixed
  code first, then passed. The fence's predicates are pinned on a real
  database by `test_a_reclaimed_or_superseded_worker_never_starts_the_store`,
  and its control flow by two unit tests. **Mutations M1–M4 all killed**
  (`22.1-05-records/mutations.json`).

## 5. The recall test (S13): R3 fails

`tests/recall/test_d2_recall.py` runs on demand and is marked `recall`;
CI's default run shows it skipped with its reason. It was run twice, each on a
fresh scratch database, and gave the same verdict both times.

- **R1 holds:** the planner chooses HNSW for L (48,604 rows in a 120,160-row
  shared partition) under default settings.
- **R2, R4 and R6 hold.**
- **R3 fails:** mean recall@10 is 0.926–0.937 against ≥ 0.95, the worst query
  0.00–0.20, and mean recall@50 0.878–0.890, in both HNSW-served scopes (H/L
  and the twin T).
- **R5 failed in one of the two runs:** one short result.
- **The flip point:** exact search up to 20,000 rows, HNSW at 48,604 rows.
- **The `ef_search` exploration:** 80, 100 and 200 all give 1.000.
- Nothing was tuned; changing `ef_search` changes rankings.

`DECISIONS.md` D2 and `22-CONTEXT.md`'s inheritance row point at the record.

## 6. Measured versus inferred

Measured: everything in sections 2–5, on one host (Windows 11, Docker Desktop
VM 16 CPUs / 31 GiB). Inferred, and marked in the records:

- a production partition shared by many tenants would make the store slower;
- the slowest "before" parse (712 s) was the host's own load. It overlapped
  this plan's mutation tests and full test suite;
- the 0.5 s sampler missed little of the disk peak;
- one worker's embed rate is the key's limit as much as the worker's;
- the default `ef_search` (40) fails because it is below `LIMIT 50`.

## 7. Deviations from the plan, and readings of it

- **The harness synthesizes GitHub's tarball redirect locally** (to
  `codeload.github.com`, which serves the real bytes), so the unauthenticated
  API's 60-an-hour limit could not fail a run. The plan said to forward the
  API request.
- **tiktoken's encoding file is baked into the measurement image.** tiktoken
  downloads it on first use, so the "no network" dry run would otherwise need
  one fetch that is not OpenAI's.
- **At-cap copies are made distinct.** One comment line is added per copy
  after the real chunker runs, and replayed vectors are perturbed on each
  pass after the first. Otherwise `_embed`'s dedupe and pgvector's HNSW
  duplicate handling would make the store cheaper than a real repository's.
- **The real runs and the "before" runs mounted a `git archive` of
  `526c7f7`**, so editing the fix could not change a running measurement.
  Every record states its code and its store order.
- **`ANALYZE` in the recall test runs as the superuser** (it needs the
  table's owner), so it joins migrations and grants as privileged.
- **`F_cap`** reads "the four real repositories" as Task 2's real runs. Read
  to include the confirmation's stalled fetch (23.3 s per MB),
  `max_job_duration` would be 13 h.
- **`P_cap`** takes the maximum over all six cap runs, as written. Over the
  post-fix runs only it would be 3 h 15 min.
- **ISS-042, not ISS-041:** main took ISS-041 while this plan ran (22.2-01's
  Python 3.11 test failures). Commit `1f4054a`'s message says ISS-041; the
  merge `2cbfdce` renumbers it.
- **22.2-02 merged while this plan ran.** Every measurement used the chunker
  before it, which is one of this plan's re-measure triggers (the dry runs
  re-run free).

## 9. For the user

1. **R3 failed. Choose one** (nothing was tuned):
   - (a) set `hnsw.ef_search` to 80 or more on the production search. Measured
     as 1.000 here. It changes rankings, so it goes through 22.2's protocol;
   - (b) accept the measured recall and revise R. Only you can revise it;
   - (c) investigate further before deciding.
2. **The pool is one worker** because one worker nearly saturates the key's
   1,000,000 tokens a minute. A second worker needs a higher OpenAI tier
   first.
3. **`F_cap`'s reading.** The record applies the narrower reading (3 h 45
   min). The inclusive one would give 13 h.
4. **Memory: 9.7 GB per worker at the chunk cap** (ISS-042). Phase 24 sizes
   the host for it, or the store is reworked first.
5. **Should the recall test run in CI?** That needs its vectors (about 1 GB
   of `float32`; the export here was 382 MB for 62,116 vectors) hosted somewhere CI can fetch
   them, a release asset for example. **Recommended:** on demand now, on the
   triggers; decide in Phase 24 or 25.

## 10. The user's decisions, 2026-10-06

1. **R3 is a correctness fix, then a re-test.** `hnsw.ef_search = 100`
