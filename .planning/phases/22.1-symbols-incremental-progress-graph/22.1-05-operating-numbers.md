## Rules

*Measured quantities* (every run as `rag_doc_app` on a scratch
`pgvector/pgvector:pg16`, 22-01's digest; the host recorded). **No
`pg_stat_statements`**: it records only statements that complete, so a beat
cancelled with `57014` would never reach it.
- **Stage times:** from the runtime's stage lines (`runtime.py:794-801`,
  one per report), the claim line and the completion line.
- **Fetch size:** the archive's bytes from fetch's own line
  (`handler.py:450-461`), and the expanded bytes, the sum of the fetched
  files' sizes, recorded by the harness.
- **Statement times, client-side.** The harness wraps `psycopg2.connect` for
  the worker's process, as `test_the_heartbeat_keeps_its_callers_identity`
  (`test_job_worker_runtime.py:2187`) does for identity, and **passes
  `cursor_factory=` a timing subclass of `psycopg2.extensions.cursor`** to the
  real `connect`. psycopg2's cursors are C types, so `execute` cannot be
  patched on an instance. The heartbeat (`_unscoped(conn)`) and `complete()`
  (`require_tenant(conn, …)`) use the connection's default factory, so both
  are timed; the claim's `RealDictCursor` is not, which no rule needs. The
  subclass times every `execute` of `HEARTBEAT_SQL` on the heartbeat
  connection (`application_name` `rag-doc-worker-heartbeat`,
  `runtime.py:270`), **including the ones that raise** (their duration is
  until the exception), and records each exception's `pgcode`. It times the
  store's statements on the loop connection the same way (`ATTACH_RUN_SQL`,
  the chunk delete and insert, `COMPLETE_SQL`). One record per beat.
- **Beat outcomes.** **No log line contains `57014`:** a cancelled beat is
  logged as `heartbeat failed (n in a row) …: QueryCanceled: canceling
  statement due to statement timeout`, through `sanitize_error`
  (`transitions.py:641`, called at `runtime.py:1532-1538`). So a cancelled
  beat is counted two ways, and both counts are recorded:
  - **primary:** the timing subclass's exceptions with `pgcode == '57014'`;
  - **cross-check:** captured log records containing both `"heartbeat
    failed"` and `"QueryCanceled"`, the match
    `test_job_worker_runtime.py:2421-2424` already uses.

  Every "assuming it is lost" line is counted from captured log records too.
- **Tokens, calls and 429s:** an `httpx` event hook on the OpenAI client
  records, per HTTP response, its status, its latency, `usage.total_tokens`
  when present, and the `x-ratelimit-limit-tokens` and
  `x-ratelimit-limit-requests` headers (names and numbers only). **Every HTTP
  429 is counted there**, including the ones the SDK retries silently.
- **Memory:** peak RSS from `ru_maxrss`, measured in `python:3.11-slim`, the
  production image.
- **Disk:** peak working-directory bytes, sampled every 0.5 s.

*The rules:*

- **N1 — `max_job_duration`.** Let `T_cap` = `F_cap + P_cap + E_cap +
  S_cap`, where:
  - `F_cap` = 500 MB × the largest measured (fetch-stage seconds ÷ archive
    MB) over the four real repositories. The fetch stage includes the
    download, the extraction and the walk, so charging it all to the archive's
    size overstates per-MB cost (the expansion is larger than the archive),
    which errs long;
  - `P_cap` = the parse time measured at the cap (Task 2's synthetic run),
    the maximum over its runs;
  - `E_cap` = 100,000 × the highest measured tokens per chunk ÷ the lowest
    measured single-worker tokens per second;
  - `S_cap` = the store time measured at the cap **after** the A-L3 fix, the
    maximum over its runs.

  Then **`max_job_duration` = 3 × `T_cap`, rounded up to the next 15
  minutes**, and never less than 3 × the longest real job measured. The ×3
  is P16's own margin, kept. A result above 4 h is still applied, and the user
  is told, because a deterministic overrun costs five attempts (22-05 §16).
- **N2 — the lease (A-L3).** First, measure A-L3 on the code as it is, at the
  cap. Then fix it and measure again. **N2 is decided only after every
  post-fix run exists: the single-worker runs at every size and the
  concurrency confirmation (N4).**
  - The lease **stays 5 minutes** if, across all those post-fix runs:
    - no heartbeat is cancelled: zero `pgcode == '57014'` exceptions in the
      timing subclass, **and** zero log records with both `"heartbeat
      failed"` and `"QueryCanceled"`;
    - no "assuming it is lost" line is logged;
    - every timed `HEARTBEAT_SQL` execution is under 1 s.
  - **Otherwise the lease = max(5 min, 2 × `S_cap`), rounded up to the
    minute**, so it never shrinks below today's, and the user is told the fix
    did not separate the store from the lease.
  - **The beat stays a fixed 60 s** (`DEFAULT_HEARTBEAT`, `runtime.py:246`);
    a longer lease only allows more beats to be missed.
- **N3 — the heartbeat's `statement_timeout`.** **Valid only when N2's
  keep-condition held** (no `57014`, no false loss): otherwise blocked beats
  contaminate the timings, and the timeout **stays 15 s**, reported.
  - Let `H` = the longest timed `HEARTBEAT_SQL` execution over every post-fix
    run. The timeout = **the larger of 5 s** (`CONNECT_TIMEOUT_SECONDS`,
    `runtime.py:284`, so a beat's two waits share one scale) **and 10 × `H`,
    rounded up to the second**.
  - **Constraint:** 4 × `DEFAULT_HEARTBEAT` + timeout < the lease, so four
    blocked beats still fit inside it (the reasoning of `runtime.py:327-333`).
  - If 10 × `H` exceeds 15 s, the database is the finding, not the number.
    Report it.
  - **N2 and N3 cannot contradict each other.** When N3 applies, N2 kept the
    lease at 300 s and `H` < 1 s, so the timeout ≤ 10 s and 240 + 10 < 300.
    When N3 does not apply, the timeout is 15 s and the lease ≥ 300 s, so
    240 + 15 < 300 ≤ the lease.
- **N4 — the pool size.**
  - Let `W_tpm` and `W_rpm` = the large repository's single-worker embed
    rate, in tokens per minute and calls per minute over its embed stage.
  - Let `TPM`, `RPM` = the key's limits from the headers.
  - `N_openai` = ⌊0.7 × min(`TPM`/`W_tpm`, `RPM`/`W_rpm`)⌋. The 30 % is left
    for query embeddings and bursts.
  - `N_db` = ⌊0.25 × `max_connections` / 2⌋, with the scratch server's
    `max_connections`; each worker holds two connections.
  - **`N` = max(1, min(`N_openai`, `N_db`)).**
  - **Confirmation:** `N` workers run concurrently, each on its own job, with
    every job enqueued **before** any worker starts. **The jobs are copies of
    the smallest corpus, each its own repository row**, so `N` jobs exist
    whatever `N` is; each copy is a real embed and costs one pass of that
    corpus. If the hook counts **any HTTP 429**, or any job does not complete
    in one attempt, then `N` := `N` − 1 and run again, down to 1.
  - **Spend:** before each confirmation run, the ledger checks that the run's
    projected cost fits under $3.00. If it does not, **stop and ask the
    user**; `N` stays provisional. The checkpoint reserves **one**
    confirmation run (`N` passes). Each `N` − 1 retry is another run, so the
    worst case is N(N+1)/2 passes (78 at `N` = 12). That worst case is **not**
    reserved: the ledger stops any retry that would pass the cap, and the
    projection says so.
  - **Memory is recorded as a host constraint, not folded into `N`:** a host
    needs `N` × the peak RSS at the cap, plus headroom. Phase 24 picks the
    host.
- **N5 — the OpenAI throughput ceiling.** Record:
  - `TPM` and `RPM` as the key reported them, dated, naming the model;
  - `W_tpm` and `W_rpm`;
  - every 429 the hook counted, and when;
  - **the ceiling `C` = ⌊min(`TPM`/`W_tpm`, `RPM`/`W_rpm`)⌋ concurrent
    embedding workers.**

  No run provokes a `429` on purpose; that would spend tokens to learn what
  the headers already say.
- **N6 — compose's `stop_grace_period`.** A shutdown never interrupts a store:
  `write_results` has no checkpoint, so a worker that gets SIGTERM mid-store
  finishes the store first.
  - `stop_grace_period` = the larger of 2 min and `S_cap` + 30 s, rounded up
    to the minute.
  - Otherwise a store at the cap is SIGKILLed and rolled back on every
    shutdown.
- **N7 — memory and disk at the cap: findings, not settings.**
  - If peak RSS at the cap exceeds **4 GB**, file an issue carrying the
    measurement, proposing `float32` arrays and streaming the tree.
  - Replace the docs' "about 1 GB" disk figure with the measured peak.
  - **U6's caps are not changed.** They are the user's (U6 says they are
    "revisited after 22.1-05 measures"); the record reports what the
    measurements say about them.
