<objective>
Give Phase 23 a progress contract it can poll, and a way to reach it from a
repository (P12, U8, ISS-034). This plan:
- **documents the `progress` column as built** by 22-05, and pins the document
  to the code with a test, so a new key or skip reason cannot ship
  undocumented;
- **puts the repository's current job on the repository API** (ISS-034's
  shape 1): `current_job` on `GET /api/repositories`, `GET
  /api/repositories/{id}` and the `201` of `POST /api/repositories`, as the
  same object `GET /api/admin/jobs/{id}` returns;
- **adds a `status` to that object**, computed in SQL against the database
  clock, so a UI can say "stalled", "retrying", "dead" or "paused because the
  App is suspended" from the job row and never from `sync_state`;
- adds the index that keeps "the latest job of this repository" from scanning
  the queue;
- tests every new read of `ingestion_jobs` **on purpose**, and proves each
  test can fail by mutation, because the table has no row-level security and
  the CI gate ignores `GET`s.

**Output:**
- the progress contract in `docs/api-ingestion-jobs.md`, and its pin test;
- `current_job` and `status`, with one shared SQL fragment;
- one migration (an index);
- the current-job isolation test, the updated job-endpoint test and the
  mutation record;
- ISS-034 closed.

**Estimate:** 10–14 h, 3 tasks. `22-CONTEXT.md`'s row said 6–10 h; the
difference is `status` (~2 h, which the row did not name but S8 needs), the
index migration (~1 h) and the drift scenario that makes the organization

**ISS-034: the choice, and the trade-off.**

ISS-034 offers two shapes. **This plan takes shape 1: `current_job` on the
repository response.**

- **Shape 1, chosen: a `current_job` object on the repository response.**
  - *For it:* the screen that needs it is a list. `RepoSettingsPage.tsx:24-28`
    (mock data today) shows every repository with a status. With shape 1 the
    page polls one endpoint; with shape 2 it polls one per repository every
    few seconds.
  - *For it:* `POST /api/repositories` can return the job it just enqueued,
    which closes ISS-034's literal gap (the id is logged, never returned).
  - *For it:* it forces the server to define "current" once, rather than every
    client deriving it.
  - *Against it:* the repository response grows, additively (no client reads
    it yet: the frontend pages use mock data). The list query gains a
    `LATERAL` join and needs an index. It does not answer "show me the last
    ten syncs".
- **Shape 2, not chosen: `GET /api/repositories/{id}/jobs`.** It keeps the
  repository response stable and answers history as well as status, which
  23-03's "real sync history" wants. But the list page then makes one call per
  repository per poll, and each client works out "current" for itself.
- **Bottom line.** Shape 1 serves the screen Phase 23 builds first, in one
  request. If 23-03 wants a history list, shape 2 is additive later (~3–4 h,
  the same isolation pattern as below), and nothing here blocks it.

**"Current" is defined once:** the live job (`queued` or `running`; at most
one, by `idx_ingestion_jobs_one_live_per_repo`) when there is one; otherwise
the most recent job by `(created_at DESC, id DESC)`; otherwise `null`.
The live-first rule is explicit in the `ORDER BY`, not left to timestamps.
`created_at DEFAULT NOW()` is the transaction's start time, and commit order
can disagree with it (measured for `repositories` and recorded at
`repositories.go:150-156`). After Phase 24's 30-day pruning
(`docs/api-ingestion-jobs.md:569-581`), a repository untouched for a month
reads `current_job: null`. The doc says so.

**`status`: the vocabulary, decided here.** It is computed in SQL with
`NOW()`, like `stalled`, and its one authority is the new table in
`docs/api-ingestion-jobs.md`. It is evaluated in this order, and the first
match wins:

| `status` | The row | What a UI says |
|---|---|---|
| `dead_pending` | `attempts >= max_attempts` and either `running` with a NULL or expired lease, or `queued` (a row the claim refuses). **Not** a `running` row with a live lease: the claim increments `attempts`, so a healthy final attempt also reads `attempts = max_attempts` | "failed; about to be marked dead" (the sweeper writes it) |
| `stalled` | `running`, and the lease is NULL or expired | "the worker stopped responding; it will be retried" |
| `running` | `running`, lease live | progress from `last_stage` and `progress` |
| `deferred_suspended` | `queued`, and the repository's installation has `suspended_at` set and `uninstalled_at` NULL | "paused: the GitHub App is suspended; checked hourly" |
| `retrying` | `queued`, `attempts > 0` | "failed; retrying at `run_after`" (or "now", once it has passed), with `last_error`. This is the doc's existing rule, `state = 'queued' AND attempts > 0` (`docs/api-ingestion-jobs.md:64-66`) |
| `scheduled` | `queued`, `attempts = 0`, `run_after > NOW()` | "waiting to start" (for example the rest of an hour after an unsuspend) |
| `queued` | `queued`, `attempts = 0`, `run_after <= NOW()` | "waiting for a worker" |
| `completed`, `dead`, `superseded` | that state | done; failed for good (`last_error` says why); stood down |

- `deferred_suspended` reads the **installation row**, not `last_error`'s
  wording. It joins `repositories` and `github_installations` the way the
  claim-time check does (`INSTALLATION_SQL`, `runtime.py:383-390`), inside the
  caller's tenant transaction, where both tables' row-level security applies.
- A `running` job whose installation was just suspended reads `running`: the
  token route defers it mid-run (22-05).
- **Not covered, and said so in the doc:** a job queued under an
  **uninstalled** installation (ISS-033's race) reads `queued` until a worker
  claims and abandons it.
- **The alternative not chosen:** document a client-side derivation table
  and add no field. That puts the precedence rules (the cap, the clock, the
  installation join) in every client, which is the failure "one authority per
  list" names.

**Isolation: why the organization filter needs a planted row.** In
`jobByIDSQL` the job's `organization_id` filter is the only guard, so
neutering it fails Scenario2. In the repository responses, the job is reached
by correlating on a repository the caller can already see under
`repositories`' row-level security, and `ingestion_jobs_repo_tenant_fk`
makes a job's tenant equal its repository's. A cross-tenant request therefore
cannot observe a neutered filter, and the filter would be decoration under
test. **So the test plants the case the filter exists for:** a job row whose
`organization_id` is B's on A's repository. It is inserted under
`SET LOCAL session_replication_role = replica` in a superuser transaction
that is **never committed**, and then the **production statement** runs
inside the same transaction after `SET ROLE` to the app role and A's tenant.
This is the pattern `chunks_partition_test.go:516-640` already uses. A
neutered filter returns B's job as A's current job, and the test fails. The
row is unrepresentable in normal operation (the composite key); that is the
point of testing the authorization column directly.
