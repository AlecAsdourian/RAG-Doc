# Phase 22.1 — Acceptance criteria

Written 2026-10-06, with the plans for 22.1-03 and 22.1-05. The criteria for
22.1-01, 22.1-02 and 22.1-04 are **numbered placeholders**, written when those
plans are: 22.1-01 waits for 22.2-02 (`22.2-CONTEXT.md` QD11), 22.1-02 builds
on 22.1-01's symbols, and 22.1-04 builds on both.

`../22-repository-clone-ingestion/22-CONTEXT.md` is the authority for
decisions (Phase 22.1 shares it, U2). This file is the authority for **what
"done" means**.

**How it is used** (as in `22-ACCEPTANCE.md`):
- **A PR body** has a section "Acceptance criteria" listing the IDs it
  advances, each with its evidence (a test name, a measurement, a CI log
  line). "Advances" can mean partially; say which part.
- **A review verdict** has a "Criteria check" line per cited ID: holds, does
  not hold, or not verifiable, with what was run.
- **The phase closes** when every criterion is met with evidence recorded in
  a SUMMARY, not when the last plan merges.
- **A criterion that turns out wrong** is corrected here with a dated note,
  never met by a weaker reading.
- **A plan that needs more criteria** appends them after the last number in
  use. It does not renumber.

### 22.1-03 — the progress contract and ISS-034

**S5 — The `progress` contract is documented as built, and pinned to the
code.** `docs/api-ingestion-jobs.md` states, in one place: what `null` and
`{}` mean; that the column is per attempt, replaced whole, and cumulative
within an attempt; that no ending touches it, so a failed, rejected or dead
job keeps its last report; every key, the stage that first reports it and its
type; and every skip reason the fetcher can count, with its meaning. A test
fails when the handler emits a key the document does not list (or omits one
it does), and when the fetch package can produce a skip reason the document
does not list (or the document lists one nothing produces). *Evidence:* the
doc section; `tests/ingest/test_progress_contract.py`; its mutations killed.

**S6 — A repository's current job is reachable from the repository API, and
ISS-034 is closed.** `GET /api/repositories`, `GET /api/repositories/{id}`
and the `201` of `POST /api/repositories` carry `current_job`: the same
object `GET /api/admin/jobs/{id}` returns, or `null`. "Current" is the live
job when there is one, otherwise the most recent job by `(created_at, id)`,
otherwise `null`, and it does not depend on `created_at` happening to order a
live job last. A connect's response carries the job that connect enqueued.
The lookup is served by an index, not a scan of the queue. *Evidence:* the
current-job isolation test's definition and connect scenarios; the migration
and its `EXPLAIN`; ISS-034 moved to Closed with that evidence.

**S7 — Every reader of `ingestion_jobs` is isolated by a test written on
purpose, and the test can fail.** The table has no row-level security and
the CI gate does not scan `GET`s, so each statement that reads it from a
request handler filters by the caller's organization explicitly, and a test
fails when that filter is neutered. For the repository responses, where the
repository's own row-level security would otherwise mask the mutation, the
test plants a drifted job row (another organization's, on the caller's
repository) in a transaction that is never committed. The response never
carries `lease_owner` or `payload`; the key set is asserted, not two names.
Another organization's repository stays a byte-identical `404`. *Evidence:*
the isolation tests; the mutation table (organization filter, repository
correlation, live-first order, a forbidden column, each `status` branch, the
connect read), each mutation proven present before it ran.

**S8 — A UI can tell what a job is doing from the job row, never from
`sync_state`.** The job object carries a `status` computed in SQL against the
database clock: `queued`, `scheduled`, `retrying`, `deferred_suspended`,
`running`, `stalled`, `dead_pending`, `completed`, `dead` or `superseded`.
The vocabulary, its precedence and what a UI should show for each are in
`docs/api-ingestion-jobs.md`, which is its one authority. Each value is
reached by a seeded row in a test whose repository reads `syncing`, so the
test proves the status does not come from the projection. *Evidence:* the
status scenarios; the doc table; the branch mutations killed.

### 22.1-05 — D2's recall test and the operating numbers

**S9 — The rules come first.** Before any timing run or recall query, a
commit records the rule that will set each operating number
(`max_job_duration`, the pool size, the heartbeat's `statement_timeout`, the
lease, the OpenAI throughput ceiling, and compose's `stop_grace_period`) and
the recall rule. Nothing measured afterwards changes a rule; a rule that turns
out unworkable is reported to the user with its measurement, and the number
stays provisional. *Evidence:* the rule commit's hash precedes every
measurement commit; the reviewer diffs the rules section against it.

**S10 — Per-stage ingest timings are measured and recorded.** Fetch, parse,
embed and store, from the worker's own stage log lines, for the three
benchmark corpora and one large public repository, each at a pinned commit,
through the real `Worker` as `rag_doc_app` on a scratch database. Also at
U6's chunk cap (synthetic, no OpenAI): the store's duration, peak worker
memory and peak working-directory disk. Incremental timings are recorded as
equal to full until 22.1-02 makes them differ (S3 carries the rest).
Measured and inferred values are marked. *Evidence:*
`22.1-05-operating-numbers.md`; the committed scripts.

**S11 — Every operating number is set by its rule, as a dated record that
replaces P16.** The code constants, compose's defaults, the tests that pin
them and the operator docs all carry the measured values; `22-CONTEXT.md` P16
points at the record. The OpenAI ceiling is the key's own reported limits
(dated, per key), with the measured per-worker rate beside them. Each number
names the events that require it to be measured again. *Evidence:* the
record; the changed pins; a confirmation run at the chosen pool size with no
rate-limit error.

**S12 — A store never blocks its own heartbeat (A-L3).** Measured before the
fix at the chunk cap; then `write_results` takes the job row's lock last,
after a lock-free fence check, so heartbeats land throughout the store.
Measured again after the fix. A test fails if the lock moves back to the
start. *Evidence:* the before and after measurements; the mid-store
heartbeat test; its mutation killed.

**S13 — D2's recall test exists and passes its committed rule.** Seeded with
the corpora's and the large repository's **real** ada-002 vectors, copied
into synthetic tenants, through the production writer as `rag_doc_app`. At
least one scope is served by HNSW under default settings, and the test
asserts it from the plan. Repositories are filtered inside a partition; one
partition is shared by several tenants, one of whom holds the same vectors as
another; the exact baseline runs the production statement in the same scope
with index scans off, and its plan is asserted exact. Recall and short
results are both asserted. No result row belongs to another tenant or
another repository. `DECISIONS.md` D2's verification item points at the
record. *Evidence:* `22.1-05-recall.md`; the test's output.

### Phase-wide

**S14 — The phase leaves honest records.** Every SUMMARY marks what was
measured and what was inferred; every "does NOT pin" item reaches the
phase-level hand-off; the issue register is accurate; no file claims a
guarantee a test does not give. *Evidence:* the reviewer's criteria checks on
each PR.
