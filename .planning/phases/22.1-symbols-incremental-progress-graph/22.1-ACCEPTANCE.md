**How it is used** (as in `22-ACCEPTANCE.md`):
- **A PR body** has a section "Acceptance criteria" listing the IDs it
  advances, each with its evidence (a test name, a measurement, a CI log
  line). "Advances" can mean partially; say which part.
- **A review verdict** has a "Criteria check" line per cited ID: holds, does
  not hold, or not verifiable, with what was run.
- **The phase closes** when every criterion is met with evidence recorded in
  a SUMMARY, not when the last plan merges.
- **A criterion that turns out wrong** is corrected here with a dated note,
  never met by a weaker reading.
- **A plan that needs more criteria** appends them after the last number in
  use. It does not renumber.

## Criteria

### 22.1-01 — D1 symbol identity, and ISS-036

*Written 2026-10-06 with `22.1-01-PLAN.md`. P8 is locked by the user at that
plan's approval (SU1–SU5, SU9); a criterion below that depends on an SU
answer says which, and is corrected here, dated, if the answer differs from
the recommendation.*

**S1 — Every indexed definition has a deterministic identity, and nothing
ranks differently.** A full ingest writes, inside `complete()`'s
transaction, one `symbols` row per definition under P8 as locked (the kind
table in `workers/chunker/symbols.py`, its one authority), including one
`module` symbol per indexed file, Go non-struct types and package
constants (SU2, SU3), and TypeScript interfaces, type aliases and enums
(QU4), and none for an alias. Each row's `id` is uuid_v5 over
`(repository_id, file_path, symbol_path, kind, ordinal)`, pinned by a
golden value; `symbol_path` is the full ancestor chain, never the
four-level breadcrumb; the span starts at the leading doc comment or the
first decorator, whichever is earlier (SU1(c)), and `span_digest` covers
it. Every chunk's `symbol_id` names a symbol of its own file (`function`
and `class` their definition's, `class_summary` its class's,
`file_summary` and `fixed_size` the module's). And:
- (a) re-ingesting an unchanged commit gives identical ids and digests (D1,
  verification 1);
- (b) adding a line above a definition changes neither its id nor its
  digest (D1, verification 2), and the premise (its `start_line` moved) is
  asserted;
- (c) a decorator or a doc-comment edit changes the digest and not the id;
- (d) a definition that vanishes is archived, never deleted, and returns
  with the same id and its original `first_seen_commit`; archival never
  reaches another repository, including one in the same tenant;
- (e) the four measured collision shapes (two Go `init()`, a property and
  its setter, `@typing.overload` stubs, TypeScript declaration merging) get
  distinct ids through `ordinal` or `kind`;
- (f) **no ranking input changed**: on all seven census corpora the
  chunk-set digest, every chunk's `metadata`, and the `(file_path,
  chunk_type, breadcrumb)` multiset are identical before and after; no file
  under `workers/retrieval/` changed; `retrieval_code_version` is equal. A
  change that would move any of these is a 22.2 protocol decision, not
  this criterion's.

*Evidence:* `workers/chunker/test_symbols.py`; the D1 tests in
`test_ingest_end_to_end.py`; `22.1-01-records/census-checks.txt`; the
mutation tables (M1–M8, M14–M18); `DECISIONS.md` D1's dated lines.

**S2 — A chunk can cite only its own repository's run and symbol (ISS-036
closed).** `chunks` carries `(ingestion_run_id, repository_id) →
ingestion_runs (id, repository_id)` and `(symbol_id, repository_id) →
symbols (id, repository_id) ON DELETE SET NULL (symbol_id)`, both
validated; the single-column keys are gone. As `rag_doc_app`, with nothing
lifted, a chunk citing another tenant's run or symbol, **or another
repository's of the same tenant**, is refused with `23503`. The migration
is proven **over seeded chunks** in at least two partitions, because the
seeded gate holds no chunk after 000017: in the deployment shape it passes
with the tenant audit empty and FORCE restored on every table it lifted,
and with one drifted chunk planted it fails with `23503`, so the
validation read every partition. The seeded gate passes on a fresh
database, and up, down, up leaves an identical schema. The drift query's
`:run` and `:symbol` arms stay, because replica mode bypasses the keys
(P3). *Evidence:* `TestChunkCompositeKeysValidateOverSeededChunks` (a) and
(b); `TestChunksPartition_ARunOrSymbolOfAnotherRepositoryIsRefused`; the
gate's subtest; mutations M9–M13; ISS-036 in Closed.

### 22.1-02 — incremental ingestion and ISS-027

*Written 2026-10-06 with `22.1-02-PLAN.md`. P11 is locked by the user at
that plan's approval (SU10–SU14).*

**S3 — An incremental re-indexes only what changed, and ends where a full
ingest of the same tree would.** `incremental` and `full_ingest` are
different handlers. An incremental classifies every file of the fetched
tree against the repository's manifest (`repository_files`: content hash,
indexer version, embedding model, chunk count) as added, changed,
unchanged or removed; it parses and embeds only added and changed files
(asserted by a spy on the chunker and by the texts the embedder received);
and in the completion transaction it replaces those files' chunks, deletes
the removed files' chunks, upserts their symbols, archives the vanished
ones and updates the manifest, with the job row's lock last. And:
- (a) **the equivalence rule**: for each tested sequence (a force-push, a
  missed push, a file deleted then restored, a rename, a file that becomes
  skipped, an indexer-version bump, a model change, a doc-comment-only
  change), the stored chunks, live symbols and manifest after a full
  ingest then incrementals equal a full ingest's of the last tree, compared
  as the plan defines; the duplicate-body rows SU13 names are listed and
  counted, never silently excluded;
- (b) **reuse is exact**: a vector is reused only from a stored row whose
  `embedded_text_sha256` (the text actually sent to the API) and model
  equal the new chunk's; a doc-comment change with an unchanged body is
  re-embedded; no vector crosses models; a `full_ingest` reuses nothing
  (SU11);
- (c) **U6's cap and the parse guard read the whole tree**: one bad file in
  a large repository completes an incremental as it completes a full
  ingest, and a push that takes the repository over 100,000 chunks is
  `Rejected`;
- (d) **ISS-027 is closed**: after a change, no chunk of a superseded file
  version is stored or returned by either retrieval leg, and a store that
  fails leaves the manifest and the chunks as they were;
- (e) every new progress key is a row in `docs/api-ingestion-jobs.md`'s
  contract, and 22.1-03's pin test passes;
- (f) **S10's incremental half**: incremental timings (no change, one
  file, ten files) on the three corpora, measured and inferred values
  marked (SU12), or recorded as waiting for PR #69 if its harness has not
  merged.

*Evidence:* the equivalence sequences and targeted tests in
`test_ingest_end_to_end.py`; `tests/ingest/test_incremental.py`; mutations
N1–N13; `22.1-02-timings.md`; ISS-027 in Closed; the in-run sharing issue
filed with an owner.

### 22.1-04 — D3 tier 1

*Written 2026-10-06 with `22.1-04-PLAN.md`. P9 is locked; SU16–SU22 are
the user's at that plan's approval.*

**S4 — The tier-1 graph is stored, tier-2-safe, cycle-safe and current.**
`symbol_edges` exists with D3's evidence lattice and partial unique
indexes, RLS, FORCE, the policy, the trigger, and composite keys from both
symbol references into `symbols (id, repository_id)` (SU16), all inside
`CREATE TABLE`; an edge citing another repository's symbol is refused with
`23503`. Before any producer exists, tests prove (D3's verifications):
- (a) a tier-2 edge upgrades a tier-1 edge **in place** (the same row);
- (b) a tier-1 re-ingest does not downgrade a tier-2 edge, and does not
  re-insert an unresolved tier-1 edge that tier 2's reconciliation retired
  (the phantom guard);
- (c) the reconciliation omits `edge_kind` (P9): a tier-2 `references`
  edge retires a tier-1 `calls` phantom for the same `(from,
  to_symbol_name)`;
- (d) a traversal over a cyclic fixture terminates under a statement
  timeout, returns each reachable symbol once, and never traverses to or
  from an archived symbol.

Then every ingest writes `calls` and `imports` edges with `to_symbol_name`
always set (`partial` when bound, `unknown` when not, SU18); an
incremental rebinds an unchanged file's edge when its target's file
changes; the graph after incrementals equals a full ingest's on the tested
sequences; and **a re-export resolves to the same id as its leaf** (D1's
third verification, moved here by P8) for Python and TypeScript re-exports
and a Go type alias, with a re-export cycle terminating. The census
records, per corpus and kind, the share of candidates bound (SU21:
recorded, not gated), and the chunk-set digests stay unchanged.
*Evidence:* `test_symbol_edges.py`; the candidate and resolver tests; the
store tests in `test_ingest_end_to_end.py`; mutations E1–E14; the census's
edge section; `DECISIONS.md` D1's and D3's dated lines.

### 22.1-03 — the progress contract and ISS-034

**S5 — The `progress` contract is documented as built, and pinned to the
code.** `docs/api-ingestion-jobs.md` states, in one place: what `null` and
`{}` mean; that the column is per attempt, replaced whole, and cumulative
within an attempt; that no ending touches it, so a failed, rejected or dead
job keeps its last report; every key, the stage that first reports it and its
type; and every skip reason the fetcher can count, with its meaning. A test
fails when the handler emits a key the document does not list (or omits one
it does), and when the fetch package can produce a skip reason the document
does not list (or the document lists one nothing produces). *Evidence:* the
doc section; `tests/ingest/test_progress_contract.py`; its mutations killed.

*Met 2026-10-06 by 22.1-03 (`22.1-03-SUMMARY.md` §1, §6):* "The progress
contract" in `docs/api-ingestion-jobs.md`, with the keys table (type, first
stage) and all 18 skip reasons between markers;
`test_progress_contract.py` runs the real handler over three fixtures and
collects the reasons with `ast`, premise first; mutations P1, P1b, P2, P3
and P4 killed, each proven by bytes.

**S6 — A repository's current job is reachable from the repository API, and
ISS-034 is closed.** `GET /api/repositories`, `GET /api/repositories/{id}`
and the `201` of `POST /api/repositories` carry `current_job`: the same
object `GET /api/admin/jobs/{id}` returns, or `null`. "Current" is the live
job when there is one, otherwise the most recent job by `(created_at, id)`,
otherwise `null`, and it does not depend on `created_at` happening to order a
live job last. A connect's response carries the job that connect enqueued.
Each of the lookup's two steps (the live job, then the newest) is served by
an index with a `Limit` and no `Sort`, **as measured by `EXPLAIN`**; if the
planner chooses otherwise, this clause is reported as not holding.
*Evidence:* the current-job isolation test's definition and connect
scenarios; the migration and its `EXPLAIN`; ISS-034 moved to Closed with that
evidence. *Shape 1 and the `status` vocabulary (S8) were accepted by the user
on 2026-10-06.*

*Met 2026-10-06 by 22.1-03 (`22.1-03-SUMMARY.md` §3–§6):*
`repositories_current_job_isolation_test.go` Scenarios 1, 3 and 5 (M2, M2b,
M3 and M7 killed); migration 000018, the seeded gate passing and up/down/up
identical; `EXPLAIN (ANALYZE, BUFFERS)` over 19,900 jobs as `rag_doc_app`:
the live lookup on `idx_ingestion_jobs_one_live_per_repo` and the newest on
`idx_ingestion_jobs_repository_recent`, each a `Limit` over an `Index Scan`
with no `Sort`, under both custom and generic plans; ISS-034 in Closed.

**S7 — Every tenant-facing reader of `ingestion_jobs` is isolated by a test
written on purpose, and the test can fail.** The table has no row-level
security and the CI gate does not scan `GET`s, so each statement that reads
it for a tenant-facing request handler filters by the caller's organization
explicitly, and a test fails when that filter is neutered. **The one
exception is by design:** the internal token route's `liveLeaseSQL`
(`internalapi/repository_token.go:178-194`) reads the queue queue-wide,
authorized by the lease, on the internal listener only; `docs/isolation.md`
names it. For the repository responses, where the repository's own
row-level security would otherwise mask the mutation, the test plants drifted
job rows (another organization's, on the caller's repository, beside a
terminal job of the caller's) in a transaction that is never committed. The response never
carries `lease_owner` or `payload`; the key set is asserted, not two names.
Another organization's repository stays a byte-identical `404`. *Evidence:*
the isolation tests; the mutation table (both lookups' organization filters,
the repository correlation, the live-first lookup, a forbidden column, each
`status` branch, the connect read, the `Get` and `List` claim guards), each
mutation proven present before it ran.

*Met 2026-10-06 by 22.1-03 (`22.1-03-SUMMARY.md` §5, §6):* Scenario4 plants
another organization's live and newest rows under replica mode in a
transaction never committed and runs the three exported production
statements built from the fragment (Get's, List's and Connect's) as
`rag_doc_app` (M1a, M1b killed, each failing all three); `jobs_isolation_test.go` Scenario2 still
kills `jobByIDSQL`'s neutered filter (M8); the literal key set (M4); the
byte-identical 404 (Scenario2); the `Get` and `List` twins (M9a, M9b);
`docs/isolation.md`, "Readers of `ingestion_jobs`", names `liveLeaseSQL` as
the exception.

**S8 — A UI can tell what a job is doing from the job row, never from
`sync_state`.** The job object carries a `status` computed in SQL against the
database clock: `queued`, `scheduled`, `retrying`, `deferred_suspended`,
`running`, `stalled`, `dead_pending`, `completed`, `dead` or `superseded`.
The vocabulary, its precedence and what a UI should show for each are in
`docs/api-ingestion-jobs.md`, which is its one authority. Each value is
reached by a seeded row in a test whose repository reads `syncing`, so the
test proves the status does not come from the projection. *Evidence:* the
status scenarios; the doc table; the branch mutations killed.

*Met 2026-10-06 by 22.1-03 (`22.1-03-SUMMARY.md` §2, §5, §6):* Scenario6
seeds 16 rows reaching all ten values (both `dead_pending` shapes, the
healthy final attempt, the suspended-and-uninstalled twin, and PR #64's three
rows: suspended after a failed attempt, a cap of 2, a cap of 8), each
repository read back as `syncing` first, asserted on `current_job` and on the
job endpoint; the doc's status table is the one authority; M5, M6, M10, M11
(the row's cap) and M12 (suspended over retrying) killed.

### 22.1-05 — D2's recall test and the operating numbers

**S9 — The rules come first.** Before any timing run or recall query, a
commit records the rule that will set each operating number
(`max_job_duration`, the pool size, the heartbeat's `statement_timeout`, the
lease, the OpenAI throughput ceiling, and compose's `stop_grace_period`) and
the recall rule. Nothing measured afterwards changes a rule; a rule that turns
out unworkable is reported to the user with its measurement, and the number
stays provisional. The OpenAI spend never passes the **$3.00 hard cap the
user approved on 2026-10-06**, counted cumulatively across every run of the
plan, the concurrency confirmation included. *Evidence:* the rule commit's
hash precedes every measurement commit; the reviewer diffs the rules section
against it; the spend ledger.

**S10 — Per-stage ingest timings are measured and recorded.** Fetch, parse,
embed and store, from the worker's own stage log lines, for the three
benchmark corpora and one large public repository, each at a pinned commit,
through the real `Worker` as `rag_doc_app` on a scratch database. Also at
U6's chunk cap (synthetic, no OpenAI): the store's duration, peak worker
memory and peak working-directory disk. Incremental timings are recorded as
equal to full until 22.1-02 makes them differ (S3 carries the rest).
Measured and inferred values are marked. *Evidence:*
`22.1-05-operating-numbers.md`; the committed scripts.

**S11 — Every operating number is set by its rule, as a dated record that
replaces P16.** The code constants, compose's defaults, the tests that pin
them and the operator docs all carry the measured values; `22-CONTEXT.md` P16
points at the record. The OpenAI ceiling is the key's own reported limits
(dated, per key), with the measured per-worker rate beside them. Each number
names the events that require it to be measured again. *Evidence:* the
record; the changed pins; a confirmation run at the chosen pool size with no
HTTP 429, counted at the HTTP layer.

**S12 — A store never blocks its own heartbeat (A-L3).** Measured before the
fix at the chunk cap; then `write_results` takes the job row's lock last,
after a lock-free fence check, so heartbeats land throughout the store.
Measured again after the fix. A test fails if the lock moves back to the
start. *Evidence:* the before and after measurements; the mid-store
heartbeat test; its mutation killed.

**S13 — D2's recall test exists and passes its committed rule.** Seeded with
the corpora's and the large repository's **real** ada-002 vectors, copied
into synthetic tenants, through the production writer as `rag_doc_app`. At
least one scope is served by HNSW under default settings, and the test
asserts it from the plan. Repositories are filtered inside a partition; one
partition is shared by several tenants, one of whom holds the same vectors as
another; the exact baseline runs the production statement in the same scope
with index scans off, and its plan is asserted exact. Recall and short
results are both asserted, under the thresholds **the user locked on
2026-10-06**: mean recall@10 ≥ 0.95, every query's recall@10 ≥ 0.70, mean
recall@50 ≥ 0.90 in every HNSW-served scope, and zero short results. No
result row belongs to another tenant or another repository. `DECISIONS.md` D2's verification item points at the
record. *Evidence:* `22.1-05-recall.md`; the test's output.
