<objective>
Make `incremental` re-parse and re-embed only what changed, with an outcome
indistinguishable from a full ingest of the same tree, and close ISS-027
(P11).

1. **A content-addressed file manifest** per repository, in a new table:
   each indexed file's content hash, the indexer version and the embedding
   model that produced its rows, and its chunk count.
2. **`incremental` becomes its own handler.** It fetches the whole tree as
   today, classifies every file against the manifest (added, changed,
   unchanged, removed), parses and embeds only added and changed files, and
   in `complete()`'s transaction replaces exactly those files' chunks,
   deletes the removed files' chunks, upserts their symbols and archives the
   ones that vanished, and updates the manifest. It survives force-pushes
   and missed pushes because it compares content, not commits.
3. **Vector reuse that cannot reuse the wrong vector.** A vector is reused
   only from a stored row whose vector was produced from exactly the text
   being embedded, under the same model, recorded per row as the hash of
   the text actually sent to the API.
4. **The rule that makes it trustworthy:** after any sequence of trees,
   an incremental's stored state equals a full ingest's of the last tree,
   measured by tests that run both and compare them.

`full_ingest` stays the from-scratch path: it ignores the manifest, re-embeds
everything, and writes the manifest it would have read.

**Output:**
- migration `0000NN_repository_files` (one table, one column, one index);
- `workers/ingest/incremental.py` and the registry change;
- the equivalence tests, the mutation table, and the incremental timings
  (S10's incremental half);
- ISS-027 closed; P11 locked as the user decides it; a new issue for the
  in-run vector sharing this plan finds and does not change.

**Estimate:** 19–27 h, 3 tasks. `22-CONTEXT.md`'s row said 12–16 h. The
difference:
- the per-row embedded-text hash (a column, the writer, the reuse lookup),
  without which reuse can attach a vector made from another text (~2–3 h);
- the manifest carrying the model and the chunk count, so a model change
  and U6's chunk cap behave as a full ingest would (~1 h);
- the parse guard and the cap computed over the whole tree (~1–2 h);
- the full-versus-incremental equivalence tests over tree sequences (~2–3 h);
- the incremental timings with 22.1-05's harness (~1–2 h).

**Acceptance criteria owned** (`22.1-ACCEPTANCE.md`): **S3**, and S14 for
this plan's records.
</objective>

*How vectors are shared today, and why reuse needs more than P11 says.*

vector made from a sibling's text whenever the row was a duplicate. This
plan records, per row, the hash of the text its vector was **actually**
produced from (`embedded_text_sha256`), so reuse is exact; it does **not**
change the in-run sharing, because which vector a chunk gets is ranking,
and that is 22.2's protocol (SU13).

**The algorithm.** One function decides, `classify(tree, manifest,
indexer_version, model)`, pure, unit-tested:

| A tree file is… | when |
|---|---|
| `added` | no manifest row for its path |
| `changed` | a row exists and its `content_sha256`, `indexer_version` or `embedding_model` differs |
| `unchanged` | all three equal |
| a manifest row is `removed` | its path is not in the tree (deleted, renamed away, or now skipped by a filter) |

Then, in order:
1. **parse** added and changed files with `chunk_file_with_symbols`;
2. **the cap and the guard over the whole tree**: chunks = new chunks + the
   unchanged rows' `chunk_count`; `parsed` counts unchanged files as parsed;
   `errors` counts raises among the parsed ones. Same clauses, same
   messages;
3. **embed** with reuse: group the new chunks by content hash exactly as
   `_embed` does; for each group's representative `r`, the key is
   `sha256(embedding_text(r))` and the model; a stored row of the
   repository with that `embedded_text_sha256` and model gives its vector;
   otherwise `r` is embedded. Every row of the group gets the vector and
   `embedded_text_sha256 = sha256(embedding_text(r))`;
4. **store**, in `complete()`'s transaction, with the job row's lock last:
   fence check; resolve the run; upsert the added and changed files'
   symbols; archive the symbols of changed and removed files that were not
   just written; bump `last_seen_commit` on the unchanged files' live
   symbols (SU14); delete the chunks of changed and removed files; insert
   the new chunks; upsert the added and changed files' manifest rows;
   delete the removed files' rows; complete the run; attach the run.

A file whose chunker raised gets **no manifest row** (its old row, if any,
is deleted with its chunks), so the next job retries it, exactly as a full
ingest would parse it again.

`full_ingest` runs the same code with every file `added` and reuse off
(SU11), and its store deletes the repository's chunks and manifest rows
wholesale, as today.

**The equivalence tests (`test_ingest_end_to_end.py`, real `Worker`, as

`state_of(conn, repo)`, reads what the rule compares:
- chunks: the multiset of `(file_path, start_line, end_line, chunk_type,
  content_hash, breadcrumb, docstring, symbol_id, embedded_text_sha256,
  embedding as float32)`;
- live symbols: `(id, symbol_path, kind, ordinal, start_line, end_line,

- the manifest without timestamps and run ids.

**The rule:** for a sequence of trees `T0 … Tn`, ingest `T0` full, then
`T1 … Tn` incrementally in repository R, and `Tn` full in a fresh
repository R′ of the same tenant. Then R's state equals R′'s, except:
symbol ids (they contain the repository id, so they are compared through
`(file_path, symbol_path, kind, ordinal)`), R's archived set (it must equal
every symbol R ever saw minus the live ones), and the duplicate-body rows
SU13 names, which are listed and counted. Each sequence is a test:
- **a force-push**: `T1` rewrites half the files and deletes a third;
- **a missed push**: `T1` and `T2`'s changes arrive as one tree;
- **a file deleted then restored** (D1's resurrection path): its symbols
  archived at `T1`, back with the same ids at `T2`, `first_seen_commit` the
  first ingest's;
- **a rename**: the old path's chunks gone and symbols archived, the new
  path's written, its vectors **reused** (same embedded text);
- **a file that becomes skipped** (grows past 1 MB, or matches the
  deny-list): treated as removed;
- **an indexer-version bump**: every file re-parsed, every vector reused;
- **a model change**: every file re-indexed, no vector reused across models;
- **a Go doc comment changed, body unchanged**: the chunk is re-embedded
  (the embedder saw the new text), not reused.
