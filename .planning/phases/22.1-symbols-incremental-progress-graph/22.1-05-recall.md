## Rule

- **R — the recall rule. LOCKED by the user on 2026-10-06.** For each scope
  (a tenant, one repository, one query), comparing the production search with
  the exact baseline:
  - **R1** — the largest scope of the HNSW tenant is served by the HNSW
    index, under default planner settings and with iterative scan set as
    production sets it. `EXPLAIN` shows `Index Scan using
    chunks_pNN_embedding_idx`.
  - **R2** — the exact baseline's plan contains no `embedding_idx`.
  - **R3** — in every HNSW-served scope: mean recall@10 ≥ **0.95**, and every
    query's recall@10 ≥ **0.70**; mean recall@50 ≥ **0.90**. 50 is the
    production limit.
  - **R4** — in every exactly-served scope, recall@50 = **1.000**.
  - **R5** — **no short results** anywhere: every query returns min(50, the
    rows in its scope).
  - **R6** — no result belongs to another tenant or another repository.
  - **Recall is tie-aware.** A returned chunk counts as a hit if its exact
    distance is within **2e-6** of the exact k-th distance. 2e-6 is QD2's
    tolerance; mealie's duplicate-content chunks share vectors.
  - **If R1 fails**, no real repository up to the cap makes the planner choose
    HNSW. The record says so and the user is told: D2's "at production
    volumes the planner will use HNSW" is then unproven.
  - **If R3 fails,** nothing is tuned in this plan. The `hnsw.ef_search`
    curve (the default, then 80, 100, 200) is measured as exploration and
    brought to the user. Changing it changes rankings.

## The user's decision, 2026-10-06: R3 is a correctness fix, then a re-test

Recorded before the re-run, in the same commit as the setting.

- **The finding is a bug, not tuning.** At pgvector's default
  `hnsw.ef_search` of 40, below the vector leg's `LIMIT 50`, HNSW cannot
  return the results the query asks for: run 1's short result (R5) shows it.
- **The fix:** `hnsw.ef_search = 100`, defined once as `HNSW_EF_SEARCH = 2 ×
  VECTOR_LEG_LIMIT` in `workers/retrieval/vector_retriever.py`, set per
  transaction beside `hnsw.iterative_scan` (the only place that is set), and
  pinned by `test_ef_search_is_twice_the_limit_inside_the_retrievers_own_
  transaction`. `QueryEngine` passes `VECTOR_LEG_LIMIT`.
- **R stays exactly as locked:** mean recall@10 ≥ 0.95, every query ≥ 0.70,
  mean recall@50 ≥ 0.90, zero short results. No threshold changes.
- **The re-test:** once, on a fresh scratch database, with the committed
  code. Django's and the corpora's vectors are re-embedded through the spend
  ledger (cumulative $3.00 cap; $1.513141 already spent); if a projection
  would pass the cap, everything stops. **Its R1–R6 are the verdict.** The
  80/100/200 results above stay recorded as exploration, not as the verdict.
- **The benchmark is unaffected**, to be shown with `EXPLAIN`: its corpora
  are served by exact scans at their size, where `ef_search` does nothing.
- **If R3 or R5 still fails after the fix,** stop and report; nothing further
  is tuned.

## The re-run after the fix — THE VERDICT (2026-10-06)

**R1 FAILS: no scope was served by HNSW. R2, R4, R5 and R6 hold; R3 has no
HNSW-served scope to apply to. Stopped and reported, as R says ("if R1
fails ... the user is told: D2's 'at production volumes the planner will use
HNSW' is then unproven"). Nothing further was tuned.**

- **Code:** committed `a516faa` (the setting committed in `8652704`, with the
  decisions above, before this run). Fresh scratch database (`chunks_p10`
  shared by H, S1, S2 and T: 120,580 rows). The production search sets
  `hnsw.iterative_scan = relaxed_order` and `hnsw.ef_search = 100`
  (`production_vector_leg_sets` in the record).
- **The vectors were re-embedded** for this run (the first export was
  deleted at teardown, as the plan requires), through the same ledger, on the
  merged chunker (22.2-02): django 48,707 rows, mealie 6,149, miniflux 3,600,
  RAG-Doc 3,868 (`export/manifest-reembed.json`; records in `reembed/`).
  **Spend: $1.127998, exactly the free dry run's projection; ledger total
  $2.641139 of $3.00.**
- **Result** (`recall/recall-run3-after-fix.json`): all 13 scopes were served
  exactly, H/L (48,607 rows) and T/L-twin included, by an index scan on
  `chunks_p10_organization_id_idx` and a sort. So every scope scored recall@10
  and recall@50 **1.000** (R4), **0 short results** (R5), **0 foreign rows**
  (R6), and every baseline plan was exact (R2). **R1 fails:** H's largest
  scope is not served by `embedding_idx`.
- **Why the planner chose exact, measured on this run's database**
  (read-only, as `rag_doc_app`, H/L, one query):
  - with the production settings, at `ef_search` 40, 60, 80, 100 and 200, the
    planner chose the exact plan every time (estimated total cost 4,813.62;
    `recall/rerun-plans-by-ef-search.json`). **On this data, even at the old
    default, L at 48,607 rows sits on the exact side of the flip point**:
    runs 1 and 2 chose HNSW at about the same size, so the choice at this size
    is sensitive to the data and its statistics;
  - with the sort disabled, so that only the HNSW path is left, its estimated
    cost **rises with `ef_search`**: 5,344 at 40, 6,672 at 60, 7,934 at 80,
    9,151 at 100 (8,275 at 200) (`recall/rerun-hnsw-cost-by-ef-search.json`).
    So `ef_search = 100` **moves the flip point up**: a scope needs to be
    larger before the planner will choose HNSW at all.
- **EXPLORATION, not the verdict: recall when HNSW is FORCED** (`enable_sort
  = off`, the plan asserted to be `Index Scan using chunks_p10_embedding_idx`),
  the same 230 queries, against the exact baseline
  (`recall/rerun-forced-hnsw-recall-exploration.json`):

  | Scope | `ef_search` | recall@10 mean (min) | recall@50 mean | Short |
  |---|---|---|---|---|
  | H/L | 40 | 0.925 (0.10) | 0.881 | 0 |
  | H/L | **100** | **0.939 (0.10)** | **0.897** | 0 |
  | T/L-twin | 40 | 0.923 (0.10) | 0.879 | 0 |
  | T/L-twin | **100** | **0.937 (0.10)** | **0.896** | 0 |

  **When HNSW actually serves, `ef_search` 100 still misses all three of R3's
  thresholds** (0.95 mean, 0.70 each, 0.90 at 50). It removes the short
  results but not the misses.
- **This changes how the first exploration reads.** Runs 1 and 2's "1.000 at
  80, 100 and 200" recorded recall, not plans. Given the costs above, those
  queries were **most likely served by the exact plan once `ef_search` was
  raised** (inferred, not measured: the plans were not captured then). So
  they did not show that HNSW recovers recall; they showed that the planner
  stops using it.

**For the user:** the fix that was approved does not make HNSW meet R at
this size. What it does is make the planner choose exact search more often,
which is correct and exact, but it leaves D2's "HNSW at production volumes"
unproven here. The options are the user's, and none was taken:
- keep `ef_search = 100` (exact up to a higher flip point; HNSW recall above
  it unmeasured beyond this exploration);
- measure at U6's cap (a 100,000-row scope), where the planner should choose
  HNSW, to see whether R3 holds there;
- look at why HNSW misses with iterative scan under a selective repository
  filter (the misses concentrate on the benchmark questions, which are
  off-topic for django: run 1's held-out vectors scored 0.994);
- revise R (only the user can).
