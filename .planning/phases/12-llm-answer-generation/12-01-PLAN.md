Create AnswerGenerator class that orchestrates QueryEngine → LLM pipeline with cost-efficient prompt construction.

**Class structure:**
```python
class AnswerGenerator:
    def __init__(self, query_engine: QueryEngine, openai_api_key: str, model: str = "gpt-4o-mini")
```

**Implementation requirements:**

1. **Dependencies:** openai SDK (already in requirements.txt), add tenacity (for retries) and tiktoken (for token counting) to requirements.txt

2. **RAG prompt construction** (from RESEARCH.md pattern):
   - Format retrieved chunks with [number] source citations
   - Include file_path:start_line for each chunk
   - Explicit grounding instruction: "Answer using ONLY the provided code context. Cite sources with [number]. If answer isn't in context, say 'I don't have enough information to answer that'. Do not add information from your training data."
   - Use system message for caching: "You are a code documentation assistant." + context (OpenAI caches identical system message prefixes automatically)

3. **Token counting** with tiktoken:
   - Pre-flight token count for prompt + chunks
   - If exceeds 100K tokens (safe margin for 128K window), truncate chunks to fit
   - Log warning if truncation occurs

4. **Retry handling** with tenacity:
   - @retry decorator with wait_random_exponential(min=1, max=60), stop_after_attempt(6)
   - Handles rate limits automatically with exponential backoff + jitter

5. **LLM call:**
   - Use OpenAI chat.completions.create with model="gpt-4o-mini" (cost-efficient)
   - temperature=0.0 for deterministic factual answers
   - Return dict with: answer, model, prompt_tokens, completion_tokens, total_cost (calculated)

6. **Cost calculation:**
   - GPT-4o Mini: $0.15/1M input, $0.60/1M output
   - Include in response for observability

**Why not hand-roll:**
- Prompt caching: OpenAI handles automatically (50% discount)
- Retry logic: tenacity handles jitter + Retry-After headers
- Token counting: tiktoken handles model-specific tokenization

**Error handling:**
- On token overflow: Truncate chunks, log warning
- On API errors: Let tenacity retry (up to 6 attempts)
- On persistent failure: Raise exception with clear message

**Verification criteria:** Class instantiates, generate() method accepts query+chunks and returns dict with answer and metadata.

<task type="auto">
  <name>Task 2: Implement Semantic Cache with Redis and vector similarity</name>
  <files>services/workers/workers/generation/semantic_cache.py, services/workers/workers/generation/__init__.py, docker-compose.yml, services/workers/requirements.txt</files>
  <action>
Create SemanticCache class for query similarity-based caching to reduce LLM API costs by 40%.

**Docker setup first:**
- Add Redis service to docker-compose.yml (same level as postgres/qdrant)
- Image: redis:7-alpine
- Port: 6379:6379
- No persistence needed (cache is ephemeral)

**Class structure:**
```python
class SemanticCache:
    def __init__(self, redis_url: str, embedding_generator: EmbeddingGenerator, similarity_threshold: float = 0.95)
```

**Implementation (from RESEARCH.md pattern):**

1. **Dependencies:** Add redis[hiredis] to requirements.txt

2. **Cache key structure:**
   - Key: `cache:query:{hash(query_text)}`
   - Value (Redis hash): {query, embedding (JSON string), response, timestamp, repository_id}
   - TTL: 3600 seconds (1 hour) - balances freshness vs cost savings

3. **get_cached_response(query: str, query_embedding: list[float], repository_id: UUID) -> dict | None:**
   - Scan Redis keys matching `cache:query:*` for same repository_id
   - For each cached entry, compute cosine similarity between query_embedding and cached embedding
   - If similarity >= threshold (0.95 default from RESEARCH): Cache hit! Return cached response
   - If no match: Cache miss, return None
   - **Performance note:** For production, use Redis vector search module or separate vector DB. For MVP, linear scan is acceptable with expected ~100-1000 cached queries.

4. **cache_response(query: str, query_embedding: list[float], repository_id: UUID, response: dict):**
   - Store in Redis hash with embedding as JSON string
   - Set TTL to 3600 seconds
   - Repository_id scoping ensures cache isolation per repo

5. **Integration with AnswerGenerator:**
   - Before calling LLM: Check cache with get_cached_response
   - On cache hit: Return cached answer immediately (log hit for metrics)
   - On cache miss: Call LLM, then cache_response
   - Include cache_hit boolean in response metadata

**Why 0.95 threshold:** From RESEARCH.md - balances hit rate (40%) with accuracy (maintains 97% answer quality). Lower threshold = more hits but risks serving wrong cached answers for different queries.

**Don't hand-roll:** Vector similarity search at scale would use Redis vector module or Qdrant. Linear scan is fine for MVP with <1K cached queries.

**Verification criteria:** SemanticCache can store and retrieve responses, similarity matching works, TTL expires entries.
