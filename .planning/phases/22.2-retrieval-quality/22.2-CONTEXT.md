## Objective

Make the retrieval that Phase 23 puts in front of users the retrieval we mean
to launch with. That takes three steps:
- **Fix what the chunker gets wrong,** with offline proof that it is fixed.
- **Decide three quality questions on fresh blind questions,** each under a
  rule the user commits first:
  - what a chunk should contain;
  - which embedding model;
  - how the keyword leg should search.
- **Add a TypeScript corpus,** so that every decision is also measured on the
  language most customer repositories are written in.

This is U10's track, and DESIGN.md §9 calls it "the real gate". The research
changes what goes inside each step. It keeps the order U10 locked: chunker,
then model, then ranking.

### QD1 — Correctness or quality · PROPOSED

**A correctness fix** meets three conditions:
- it makes the code do what it states, or what every other language path
  already does;
- it chooses between no designs that would rank differently;
- "fixed" is checkable offline: a census number, a parse, a unit test.

It is adopted on that evidence. The benchmark is re-run and **reported, not
judged**. This repository's precedent is PR #27 (Go methods and doc comments),
PR #28 (breadcrumbs) and 22-02 (duplicate vectors). QU2 asks whether to add a
tripwire.

**A quality decision** is one where any of three things holds:
- several reasonable designs exist;
- it removes or re-weights text retrieval can use today;
- its value shows only in ranking.

It is adopted only past a rule committed before its questions exist.

The classification, item by item, is `22.2-RESEARCH.md` R1's table. In short:
- **Correctness:**
  - the TypeScript grammar and queries;
  - named function expressions;
  - JSDoc;
  - decorators inside their chunk;
  - grouped Go structs;
  - visible truncation.
- **Quality:**
  - class chunks that repeat their methods (ISS-026) and the other duplicates;
  - splitting large functions;
  - chunking types and constants;
  - the model;
  - the keyword leg (ISS-029, ISS-028, ISS-038).
- **Correctness, neutral at today's boosts:** ISS-024, and ISS-025's defect 3.

### QD2 — The tolerance · PROPOSED

**The value:** 2.0e-6 on vector similarity, absolute, **fixed 2026-09-29**,
before any track measurement exists.
- **Where it comes from:** 22-03's largest cross-store difference was 6.03e-07
  over 6,395 pairs. 2e-6 is about 3.3× that.
- **Where it applies:** every comparison in this track of two runs' scores for
  the same stored vectors. That covers two things:
  - the equivalence runs that prove a change neutral (QD9's cleanups, and
    22.1-01 if it claims no ranking change);
  - ties at a rank cut in a decision's report.
- **Where it does not apply:** across two separate ingests. Whether the
  embedding API returns identical vectors for identical text is not verified.
  22.2-01 measures it, for about $0.001, before any rule relies on it.
- **The tool:** `compare_runs.py` gains a `--vector-tolerance` flag defaulting
  to 22-03's 1e-5, so the committed 22-03 verdict re-judges byte-identically.
  The track passes 2e-6. The harness's exact-list tie tail
  (`EXACT_TIE_TOLERANCE`) follows the same flag.
- **If the user changes the value,** the change must also precede the first
  rule.

### QD3 — The judge · PROPOSED

`compare_runs.py` cannot judge this track's decisions. It refuses runs whose
models or query-vector hashes differ, and it needs a Qdrant point set that can
never be recorded again (R4). **`decide.py`** is built in 22.2-01.

**Its input:**
- two recorded runs per corpus, for the decision's question set;
- the rule, as a small JSON file committed beside its protocol document. So
  the judge cannot be changed after the numbers exist without a visible
  commit.

**It refuses** (exit 2), before comparing anything, when:
- the question sets differ, by id or by text;
- a record's ranks are not what its own final list gives under `scoring.py`;
- a measuring connection is a superuser, bypasses RLS, or is unrecorded;
- any query failed;
- the headers differ in anything except the one declared variable. For a model
  decision that means the chunk-set digests must match. For a chunk decision it
  means the models must match;
- a query vector was embedded with a model other than its run's;
- the rule file was committed after its questions (read from `git log`).

**It prints:**
- per corpus and pooled: MRR, recall and rank-1 at 5 for file and symbol, plus
  MRR at 20, reported;
- the per-question table;
- each clause of the rule, evaluated;
- `VERDICT: ADOPT` (exit 0) or `REJECT` (exit 1).

Every refusal has a test, and every guard a killed mutation, as
`compare_runs.py` has.

### QD5 — The TypeScript fix · PROPOSED

The design constraints for 22.2-02:
- **Grammars:**
  - `tree_sitter_typescript.language_typescript()` for `.ts`;
  - `language_tsx()` for `.tsx`;
  - JavaScript keeps its own grammar *and gains its own queries*.

  Today JavaScript shares the TypeScript queries
  (`tree_sitter_parser.py:110`). The TS class query must name a
  `type_identifier`, which the JavaScript grammar does not have.

  `.tsx` needs to be told apart where the language is decided: a `tsx` key in
  `workers/fetch/filters.py`'s `LANGUAGES` and in the harness, or a parser
  choosing by extension. The plan picks one.
- **What gets chunked,** for parity with Python and Go:
  - function declarations and methods;
  - classes, abstract classes included;
  - module-level `const`/`let` bound to an arrow function or a function
    expression, exported or not, named by the variable.

  Anonymous callbacks are not chunked, as Python lambdas are not.
- **JSDoc:** a `/** … */` block directly above becomes `metadata["docstring"]`,
  as a Go doc comment does.
- **Interfaces, type aliases and enums:** symbols (22.1-01), **not** chunks.
  That is the same rule P8 gives Go's non-struct types. Chunking them is a
  quality bet (QD7).
- **The evidence it is fixed:**
  - the census shows 0 files with parse errors on linkwarden and the self
    frontend;
  - the named chunks match the named declarations (601 on linkwarden);
  - the TS chunks carrying a docstring match the JSDoc blocks (17);
  - fixture tests assert `has_error` is false for TS, TSX and JS fixtures.
    Today's tests do not, which is how the bug hid (R1).

### QD6 — One span rule · PROPOSED

**The rule:** a chunk and its symbol start at the first decorator.
- **Doc comments** are part of the *symbol* span, so `span_digest` sees them.
  They reach the embedded text through `metadata["docstring"]`, as today, and
  are **not** copied into the chunk text as well, which would embed them twice.
- **Decided once,** at whichever of 22.2-02 and 22.1-01 is approved first.
  The other cites it.

**Why it matters:** in mealie, 245 of 270 route decorators reach the index
only through the duplicated class chunks (R6). If ISS-026 were adopted before
this rule, they would leave the index altogether. So the rule is a
precondition of QD7, not only an identity detail.

### QD7 — The chunk-shape decision · PROPOSED

**One protocol decision over one bundled candidate,** in 22.2-04. Each part is
explored on tuning sets first, and kept in the bundle only if it helps there:
- class chunks that no longer repeat their methods' bodies (ISS-026). The

- nested functions and Go local structs no longer chunked twice;
- optionally, splitting functions over a size to be chosen on tuning, and

The bundle is judged under one rule the user commits (QU5 asks whether to

### QD10 — Blind questions · PROPOSED

**Per decision, per corpus: one fresh set** (the size is QU6). The process
follows PR #31 and the boost protocol:
1. **The user commits the protocol file:**
   - the candidate;
   - the test set's definition;
   - the rule, and its JSON;
   - the measurement.
2. **The writers.** After that commit, one or two writer agents per corpus are
   launched.
   - Each may read only the pinned checkout: no RAG-Doc code, no harness, no
     database, no web, no retrieval result, and no earlier question files.
   - They get the list of symbols already targeted, to avoid them.
3. **The questions.** Each carries an id, the decision's set name, the
   question, the path, the answering symbol and `path:line` evidence.
   - Phrasing: the way a newcomer asks, never naming the symbol or the file.
     About a third deliberately use words the code does not.
   - Spread: at most five per package.
   - Kinds: a mix of "where", "how", "what happens when" and "what decides".
4. **Committed before any measurement.** The questions are committed before
   any run touches them; that commit order is the evidence. Then `--check`
   runs offline with 0 failures.
5. **A spot-check.** The planner hand-checks at least a third of the answers
   against the cited code, with no retrieval, and records the result.
6. **The measurement.** Each arm is run once, as `rag_doc_app`, recorded
   (gzipped) and judged by `decide.py`. The verdict is reported whichever way
   it falls.
7. **After the verdict,** the set is spent for that decision and becomes
   exploration material for later ones.

The harness gains a set name per decision (today it accepts only `tuning`,
`holdout` and `confirm`, `rag_quality_harness.py:189`, `:366-367`) in 22.2-01.

### QU2 — Which fixes are "just bugs", and how they are checked

**What it's about.** Some chunker problems are plain bugs, like a smudged lens:
TypeScript is read with the wrong grammar, and 351 of 379 files come out
garbled. Others are choices between two good lenses, like how much of a class
to index. The draft treats bugs as fixable on proof (the file parses now) and
choices as protocol decisions. See QD1 and R1's table for the list.

- **A — Fix bugs on proof, re-run the benchmark and report it.** The
  precedent of PR #27 and #28. +0 h.
- **B — As A, plus a tripwire (recommended).** If any benchmark number on the
  existing questions falls after a bug fix, stop and find out why before
  merging.
  - Adopt unless the fix itself turns out wrong. Do not tune.
  - +1–2 h per plan, and only when it fires.
- **C — Put the bug fixes under the protocol too.**
  - A fourth protocol run with 45 fresh questions: +9–15 h.
  - It would hold a bug fix hostage to a ranking result.

Also confirm the list itself. The ones most worth a second look:
- **decorators inside their chunk,** which changes the embedded text of 844
  decorated mealie functions and classes: R1 calls it a bug, by the Go
  doc-comment precedent;
- **module-level arrow functions,** a common way to write a TypeScript
  function: 213 in linkwarden, 466 in seerr. 67 of linkwarden's are in no
  chunk at all today.

*Bottom line:* B keeps bug fixes fast and still catches a fix that quietly
makes search worse.

### QU5 — The chunk-shape changes: one decision or several

**What it's about.** Several changes would stop the index storing the same
code twice. The biggest is ISS-026: mealie's index is 46% bigger than its
source. Each one can be decided on its own, or all of them together.

- **A — One bundle, each part tried on practice questions first
  (recommended).** One set of fresh questions. If the bundle fails its rule,
  nothing in it is adopted.
  - Cost: 22.2-04, 12–19 h.
- **B — Separate decisions:** ISS-026 alone, then the others. Each is
  attributable on its own.
  - Cost: +1–2 protocol runs, ~9–15 h each.
- **C — ISS-026 only.** The cheapest. It leaves nested functions and local
  structs doubled.
  - Cost: 22.2-04 at about 10–16 h.

*Bottom line:* A gets to a cleaner index with one round of questions.

### QU6 — How many fresh questions each decision gets

**What it's about.** Fresh blind questions are what this track really costs.
The draft assumes 6–12 minutes a question, written and checked, so a set of 45
is ~4.5–9 h. The evidence brackets that: the boost protocol's questions came
within ten minutes of its rule, and U3 estimated 12–20 minutes each (R1).
Fewer questions make the verdict noisier: on 15 questions per app, one answer
moving decides a close call (R4).

- **A — 15 per app, on all three apps, for every decision (recommended).**
  - 45 per decision, 135 in all, plus 30 for the new app.
  - The track at ~66–104 h.
- **B — Only the apps a change touches.**
  - The chunk-shape change barely touches Go, so 22.2-04 needs 30, not 45.
  - Saves ~1.5–3 h. The Go app then goes unmeasured for that decision.
- **C — Decide chunk shape and model together, on one set.**
  - Four arms, both rules committed first.
  - Saves one set of 45, ~4.5–9 h.
  - The rules and the judge get more complicated (+2 h), and the model rule
    has to say which chunk arm it is judged on.
- **D — 20 per app for the model decision.**
  - More sensitivity where the effect may be small.
  - +1.5–3 h. Worth it if QU7's answer is M1.

*Bottom line:* A is the protocol as practised, times three apps. C is the
honest way to save a few hours.

### QU7 — The rule for the embedding model (U3)

**What it's about.** `text-embedding-3-small` costs a fifth of ada-002 and is
newer. The question is whether it retrieves better on our apps. You commit
the rule before the questions are written; nothing here is committed. The
full texts are in R4.

- **M1 — Better on every app.** Symbol MRR higher and file MRR not lower, on
  each of the three. Strict, with precedent. On 15 questions per app, a modest
  real improvement may still fail.
- **M2 — Better overall, with no app badly worse (recommended if the model
  should change only for quality).** All three must hold:
  - over all 45 questions, symbol MRR up by at least 0.03;
  - file MRR not down;
  - no app's file MRR down by more than one question's worth.
- **M3 — No worse (recommended if the price and model age matter to you).**
  Switch if, overall, neither MRR falls by more than 0.02, and no app is
  badly worse. This can adopt a slightly worse model.
- **M4 — More questions better than worse.** Pooled count of questions
  improved minus questions worsened, at least 4. Robust to one big swing; it
  ignores how big each change is.

Cost: the same for every rule, 22.2-05 at 11–18 h and about $0.15 of
embeddings. Money is not the question: a whole app at the U6 cap costs about
$1.50 to embed on ada-002 and $0.30 on 3-small.

*Bottom line:* pick M2 to switch only for better answers, and M3 to switch
unless it is worse. The same shape should serve the other two decisions.

### QU8 — What the keyword-leg decision covers

**What it's about.** Hybrid search has two halves, and the keyword half found
nothing for all 90 benchmark questions. It demands that every word of a
question appear in the code. Fixing that is the main ranking decision.

- **A — One bundle (recommended):**
  - the keyword fix (ISS-029);
  - breadcrumbs split into words (ISS-028, which needs a small migration);
  - the misfiring `migrations/` penalty (ISS-038).

  Two cleanups that change nothing today ride along, proven neutral. For the
  dead content boosts (ISS-024), **delete them**: they are set to 1.0 by your
  boost decision, and re-adding them would need a protocol run anyway.
  - Cost: 22.2-06, 17–27 h.
- **B — The keyword fix alone first, the others later.** Attributable. +1
  protocol run, ~9–15 h.
- **C — As A, but wire the content boosts instead of deleting them.** +2–3 h,
  and still no effect at 1.0.

*Bottom line:* A turns the second half of search on and fixes the one penalty
that was measured hiding a correct answer.

### QU9 — Secret scanning of file contents (U7's option B)

**What it's about.** Today the fetcher skips files *named* like secrets. A key
pasted into `config.py` is still indexed and sent to OpenAI. U7's review
parked this question on this track.

- **A — Not in this track (recommended).** It is a security control, not a
  retrieval-quality question. Schedule it with 25-02's security review, or as
  its own plan before launch. 6–10 h, wherever it lands.
- **B — In this track, as a seventh plan.** 6–10 h. It changes which chunks

- **C — Leave it as U7's A for v1.** 0 h. The gap stays documented.

*Bottom line:* worth doing before launch, just not as a ranking decision.

### QU10 — Confirm the tolerance

**What it's about.** When two runs score the same chunk, how different may the
scores be and still count as equal? 22-03 measured at most 0.0000006.

- **A — 0.000002, which is 2e-6 (recommended).** The hand-off's value, about
  3× the measured maximum, fixed today before any track measurement.
- **B — 1e-6.** Tighter, with 1.7× headroom. It risks calling floating-point
  noise a change.
- **C — Keep 1e-5.** About 16× generous, per 22-03's reviewer.

*Bottom line:* one word confirms A.
