## 2. The tightened guard (Task 3, first)

`_parse` raises `ParseFailed` when there were indexable files and, **checked in this order**:

1. **every file raised.** PR #58's guard, with its message verbatim;
2. **some raised and the rest produced no chunks** (`files and errors and not chunks`). Its message

3. **more than half raised** (`errors > len(files) * MAX_PARSE_ERROR_SHARE`). Its message names the

## 3. TypeScript (Task 1)

- **Grammars:** `TreeSitterParser.grammar_for(language, path)` is the one place a grammar is chosen:
  - `language_typescript()` for `.ts`;
  - `language_tsx()` for `.tsx`;
  - JavaScript's own grammar for `javascript`.

  `parse_file` and both extractors take the path and choose through it, and so does the census's one
  "as chunked" call. TypeScript with no path is refused (`ValueError`). The stored `language` stays
  `typescript`, so `filters.py` and the benchmark specs are unchanged.
- **One compiled query set per grammar:** TS, TSX and JavaScript each get their own, plus Python's
  and Go's as before.
  - `_queries_for` checks `tree.language` against the chosen grammar and raises `GrammarMismatch`
    rather than query across grammars. A TS-compiled query matches nothing on a TSX tree, silently.
  - Every query compiles in the constructor, so one that cannot compile raises `QueryError` from
    `TreeSitterParser()`, outside any fallback.
- **What is chunked (QD5):**
  - `function_declaration` and `generator_function_declaration`;
  - `method_definition` only inside a `class_body`, named by its `name` field, private `#names` and
    computed keys included;
  - `class_declaration` and `abstract_class_declaration`, named by `type_identifier` in TypeScript
    and `identifier` in JavaScript;
  - a `lexical_declaration` directly under `program` or `export_statement` whose declarator's value is
    an `arrow_function` or `function_expression`: one chunk per such declarator, named by the
    variable and spanning the declaration.
- **Not chunked,** each pinned by a test:
  - `export default function () {}`;
  - a function passed to a call (`wrap(async () => …)`);
  - an object literal's method;
  - a class-field arrow function;
  - interfaces, type aliases and enums.
- **Names:** `metadata_builder.py` makes `abstract_class_declaration` and
  `generator_function_declaration` scopes and named nodes, and reads every ECMAScript scope's name
  from its `name` field.
  - **Decision, not in the plan's text:** a module-level const-bound function is a scope too. So
    `function render()` inside `export const Page = () => {…}` reads `Page.render`, as a function
    nested in a Python function reads `outer.inner`. The alternative, a bare `render`, would make
    TypeScript the one language where a nested function loses its owner. It touches no benchmark
    corpus, since there is no TypeScript in any. 22.1-01 should cite it, or overrule it before its
    symbols land.
- **The settled questions:**
  - `.tsx` is chosen by extension;
  - anonymous default exports and object-literal methods are not chunked; a file with nothing else
    falls back to windows, as before (tested);
  - decorators: §4;
  - JSDoc: the census's definition (§4).

## 4. QD6, JSDoc and grouped Go types (Task 2)

- **A chunk starts at its definition's first decorator** (`SemanticChunker._span_start_line`).
  - **Python:** the start of the `decorated_definition` that wraps it.
  - **TypeScript** (`ts-decorator-placement.txt`, one fixture per position):

    | position | where tree-sitter-typescript 0.23.2 puts the decorator | where the chunk starts |
    |---|---|---|
    | a class | a child of the `class_declaration` | the decorator (the class node already starts there) |
    | an exported class, decorator before `export` | a child of the `export_statement` | the decorator |
    | an exported class, decorator after `export` | a child of the `class_declaration` | the `export` line, which holds it |
    | a method | a preceding sibling in the `class_body` | the first decorator |
    | a property | a child of the `public_field_definition` | not a chunk; it stays in its class's chunk |

  - The chunk's NODE does not move, so its breadcrumb, ancestor chain and parent scope are built as
    before. For Python and Go, the multiset of `(file_path, chunk_type, breadcrumb)` is identical
    before and after, on every benchmark corpus (§5).
- **JSDoc is the docstring** (`MetadataBuilder._extract_js_docstring`).
  - It is the `/** … */` that is the previous named sibling of the declaration's outermost node and
    ends on the line before it. The outermost node is its `export_statement` when exported, a method's
    first decorator, or the node itself.
  - It is cleaned as before, and it is not in the chunk text, so it is embedded once.
  - A `//` comment, or a JSDoc a blank line away, is not a docstring.
  - A JSDoc above a decorator is still the docstring, and the chunk starts at the decorator.
- **A grouped Go `type ( … )`:** each struct is chunked as its own `type_spec`, with its own doc
  comment falling back to the group's.
  - Its names are built from the declaration exactly as before.
  - "Grouped" means more than one spec, the census's definition. A single
    `type X struct {…}`, or a parenthesised group of one, is unchanged.
- **Python docstrings are still embedded twice,** in the chunk text and in `metadata["docstring"]`.
  That is as the user decided on 2026-10-06 (QA5 covers Go comments and JSDoc only). It is left for
  22.2-04 to consider with the chunk-shape candidate.

## 7. Truncation (QA6)

- **`EmbeddingGenerator.tokens_over_limit(chunk)`** is the one rule. It returns the token count of
  `embedding_text(chunk)` when that is over `max_tokens_per_chunk`, and None otherwise.
- `_prepare_text_for_embedding` truncates by it and logs **one WARNING per truncated chunk**, naming
  its path, its breadcrumb, and the tokens before and after. It never names the content.
- **The handler counts `chunks_truncated` by the same method.** It counts rows, not distinct texts,
  logs one WARNING per such row, and reports the count with the parse's counts at `embed`, so it is
  in every later report.
- The test fake's `tokens_over_limit` is the real generator's, so no test reads a copy of the rule.
- `embedding_text` is a module function now, and the census's `embed_text` uses it, so it is no
  longer a copy.
- **The census still restates the 8,000 limit** to count truncation offline without building a
  generator. That is a measurement, not the product's rule. Its docstring says so.
- **Tests:**
  - the rule passes a chunk that fits and names one that does not;
  - an over-limit chunk is sent truncated and logged once, and a content sentinel is in no log record
    (`test_embeddings.py`);
  - an oversized fixture counts 1 and is named in a WARNING without its content, and the `store`
    report keeps it beside `skipped` (`test_handler.py`);
  - **the completed job row**, read from a real database as `rag_doc_app`, holds `chunks_truncated:
    0` for the normal fixture and `1` with the oversized one (`test_ingest_end_to_end.py`).
- 22-05's key-set assertion gained `"chunks_truncated"`, in the same commit as the handler change.
- `docs/api-ingestion-jobs.md` gained the key in its progress table and in its example job.
