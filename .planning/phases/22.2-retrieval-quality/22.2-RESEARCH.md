## Summary

The locked sketch holds in shape: chunker first, then the model, then ranking.
The evidence changes what is inside each step, and adds one step in front.

1. **The chunker's worst defects are bugs, not matters of taste, and they are
   measurable without a single question.** [measured]
   - TypeScript is parsed with the JavaScript grammar
     (`tree_sitter_parser.py:19`).
     - On linkwarden, the proposed TS corpus, **351 of 379 files parse with
       errors** (3,316 `ERROR` nodes).
     - With `tree-sitter-typescript`'s own grammars, **0 of 379** do.
     - The same holds on the other three TypeScript corpora measured.
   - **131 of those 379 files fall back to 50-line windows**, and no
     TypeScript chunk in any corpus carries its JSDoc.
   - A common TS function form, `export const f = () => …`, never gets a chunk
     of its own. **67 of linkwarden's 213 are in no chunk at all.**
   - Swapping the grammar alone would crash the parser: the current class query
     is an **impossible pattern** under the TypeScript grammars.

   These can be fixed and proven fixed offline, before any decision. So the
   track gains a correctness plan in front of its three protocol runs.
2. **ISS-026's fix cannot land by itself.** [measured] A Python function's
   chunk starts at `def`, so its decorators sit outside it.
   - In mealie, **245 of the 270 route decorators** (`@router.get("/…")`)
     reach the index only through the duplicated class chunks that ISS-026
     would strip.
   - The other 25 reach it nowhere.

   Decorators must move into their function's own chunk first. That is also
   P8's span rule for 22.1-01, so the rule can be decided once.
3. **Duplication is concentrated in Python and in TS classes. Go has none.**
   [measured]
   - mealie: the index holds **1.457×** the source text, which is PR #31's
     "46% more", reproduced exactly. 147 of its 679 class chunks are at least
     80% covered by their own method chunks. 31 of its 32 chunks over 5,000

   `migrations/` pattern (`metadata_booster.py:21`, ×0.3) hits mealie's

   - One tuning question's answer is the vector leg's **#1**, and it ends up a

   Filed as ISS-038, to be decided with the keyword leg.
6. **The track needs a judge it does not have.** [read]
   `compare_runs.py` refuses any two runs whose query-vector hashes or models

## R1 — Scope and order

### What each later measurement depends on

Every protocol run measures retrieval over chunks. If the chunks are wrong in a
way that varies by candidate, the measurement answers a different question
from the one asked. That is the user's original worry, and the census shows
where it bites:

| Measurement | What a defective chunk does to it | Evidence |
|---|---|---|
| **The model decision** | The model embeds whatever the chunker hands it. On mealie that is 1.457× the source: 147 class chunks mostly made of their own methods, and 31 of 32 chunks over 5,000 characters being classes. A model judged on those is judged partly on how well it averages a whole class into one vector. That property stops mattering once ISS-026 is decided. | [measured] `census-mealie.json` |
| **The keyword leg** | `ts_rank_cd` without length normalisation rewards long chunks (ISS-026's original finding). The longest chunks are the duplicated classes. Turn the keyword leg on first, and those duplicates are what it would promote. | [read] ISS-026, ISS-029; [measured] the oversized-by-type table in R6 |
| **Any TypeScript question** | Symbol-level scoring matches a chunk's breadcrumb (`scoring.py:28-29`). With the JavaScript grammar, linkwarden yields 344 named chunks against 601 named declarations. None of its 213 module-level `const f = () => …` functions has a chunk of its own: 146 sit inside 50-line windows, and **67 are in no chunk at all**, because their file has a `function` declaration and so never falls back. Most TS questions would be unscorable at symbol level, and `--check` would warn on them. | [measured] `census-linkwarden.json`; [read] `rag_quality_harness.py:454-460` |
| **Symbol scoring on every corpus** | If a change rewrites the breadcrumb, symbol ranks move without any retrieval change. `generate_breadcrumb`'s display form (`metadata_builder.py:80-82`) must stay stable, or scoring must move to symbol ids. | [read] |

So the order "chunker → model → ranking" is right. The census refines it in
three ways:
- the chunker step splits into **correctness** (no question needed) and
  **shape** (a protocol decision);
- the TypeScript grammar belongs to correctness;
- "ranking" reduces to the keyword leg.

### Correctness or quality: a test, and a classification

**Proposed test** (QD1 in the context):
- A change is a **correctness fix** when three things hold:
  - the code does something other than what it states, or what every other
    language path already does;
  - the fix restores that behaviour without choosing between designs that rank
    differently;
  - "fixed" is checkable offline: a census number, a parse, a unit test.

  It is adopted on that evidence. Its effect on the benchmark is measured and
  reported, not judged.
- It is a **quality decision** when any of three things holds:
  - several reasonable designs exist;
  - the change removes or re-weights text that retrieval can use today;
  - its value shows only in ranking.

  It is adopted only past a rule committed before its questions exist.

**The precedent for the first category is this repository's own.** [read]
`STATE.md`, "Retrieval quality":
- **PR #27** indexed the 85 Go methods that had never been indexed and put Go
  doc comments into the embedded text. It was adopted as a fix, and it
  *reported* held-out MRR 0.444 → 0.554.
- **PR #28** populated an empty column: "Fixed; ranking unchanged".
- **22-02** gave the 92 duplicate-content chunks their vectors, as a fix, and
  22-03 explained the rank movements this caused.

## R2 — The interaction with 22.1-01

### What each changes

**22.1-01** (P8, PROPOSED, the user decides it at that plan's approval) makes
the chunker emit symbols. It adds:
- a full-chain `symbol_path`;
- a `kind` and an `ordinal` (including `@typing.overload`);
- a span that includes decorators and doc comments, and its `span_digest`;
- `module` symbols;
- Go non-struct types and constants as symbols;
- the alias rule;
- chunks linked to symbols;
- ISS-036's composite keys.

It covers Python and Go only; "TypeScript waits for the quality track's
grammar decision" (`22-CONTEXT.md`, the 22.1 table). [read]

**The track** changes, in the same three files (`semantic_chunker.py`,
`tree_sitter_parser.py`, `metadata_builder.py`):
- the TS grammar and queries;
- which declarations get chunks;
- what a chunk's text starts at (decorators);
- what a class chunk contains (ISS-026, if adopted).

### What each needs from the other

- **22.1-01 needs from the track:**
  - the TypeScript grammar and queries, which 22.1-01 cannot emit TS symbols
    without;
  - one span rule, so that `span_digest` and a chunk's text describe the same
    region;
  - the knowledge that a class's chunk may change shape (ISS-026), so that its
    chunk-to-symbol mapping holds either way. P7 already maps both `class`
    and `class_summary` to the class symbol, so it does.
- **The track needs from 22.1-01 very little:**
  - retrieval reads no symbol today;
  - the benchmark scores by breadcrumb;
  - one constraint the track places on it: **22.1-01 must not change
    `metadata["breadcrumb"]`**, or every symbol rank moves with no retrieval
    change. P8 already keeps `symbol_path` separate from the display
    breadcrumb (`metadata_builder.py:80-82`); the plan should assert it.

### Where they collide

| Collision | Consequence if unmanaged | Resolution proposed |
|---|---|---|
| Same three files edited by two branches | Merge conflicts in the parser's queries and the chunker's span logic | Serialize: 22.2-02, then 22.1-01, then 22.2-04 |
| **The span rule** | P8 puts decorators and doc comments in the *symbol* span. If the *chunk* span stays at `def`, mealie's route decorators still reach no function chunk, and ISS-026 later removes their only path into the index (245 of 270, [measured]) | One rule, decided once (QD6): a chunk and its symbol start at the first decorator. Doc comments: in the symbol span for `span_digest`, and embedded through `metadata["docstring"]` as today, **not** also in the chunk text, which would embed them twice |
| TS symbols | 22.1-01 leaves TS out and a later plan reopens the same code | If 22.2-02 lands first, 22.1-01 can include TS (QU4, +3–5 h there) |
| Go consts and non-struct types | P8: symbols without chunks. 22.2-04 may later chunk them | No conflict: a chunk added later links to the existing symbol |
| `ordinal` and overloads | A chunk-shape change that drops overload stubs (5 rows in mealie) would change which chunk carries which ordinal | 22.1-01 computes ordinals from declarations, not from chunks |
| `indexer_version` (P11, 22.1-02) | After 22.1-02 exists, a chunker change must bump it | 22.2-04 and later chunker changes bump it; before 22.1-02, re-ingest (cents) |

### A sequence that decides each thing once

22.2-02 (correctness, including the span rule), then 22.1-01 (identity on the
corrected chunker), then 22.2-04 (chunk shape). 22.2-01 and 22.2-03 do not
touch the chunker and can run alongside.
- **What it costs:** 22.1's chain (22.1-02 depends on symbols) starts one plan
  later. That is ~12–17 h of correctness work in front of it [inferred].
- **What it saves:**
  - the chunker's parse and span code restructured once, not twice;
  - the span rule decided once;
  - TS symbols in 22.1-01 rather than a follow-up plan.

**The alternative, 22.1-01 first,** is workable if 22.1-01 computes symbol
spans independently of chunk spans and leaves TS out. Then:
- 22.2-02 aligns chunk spans to P8's rule afterwards;
- a small follow-up adds TS symbols.

The cost is a second pass through the same functions, and a TS identity plan
[inferred, ~4–6 h].

### The proposal: linkwarden, pinned at `952ac4540657cae3a67c3ca59433899d2fda8374`

[measured, `census-linkwarden.json`; read in the checkout]

- **TS constructs present:**

  - 150 type aliases, 40 interfaces and 8 enums;
  - 17 JSDoc blocks.

  It has almost no classes (1), so it does not exercise TS class duplication.

## R4 — The embedding-model decision (U3)

### What is true today

[read]
- **Three places construct an `EmbeddingGenerator` with the default model**,
  `text-embedding-ada-002` (`embedding_generator.py:20`):
  - the pipeline (`ingestion_pipeline.py:34`);
  - the query engine (`query_engine.py:73`);
  - the answer generator's cache lookup (`answer_generator.py:122-124`).

  `EMBEDDING_MODEL` in `services/workers/.env.example:5` is read by nothing (a
  grep of `services/`), as `22-RESEARCH.md` Q3 found. A model change is
  therefore one value in three places today, and must become one setting.
- **The guards P4 built hold:**
  - every chunk records `embedding_model`;
  - the vector leg filters on the generator's model (`vector_retriever.py:44`);
  - the harness's query-vector cache refuses a vector embedded with another
    model (`rag_quality_harness.py:700-702`).
- **`compare_runs.py` refuses exactly the comparison this decision needs.**
  It refuses runs whose embedding models differ (`:321-326`) or whose
  query-vector hashes differ (`:308-310`), and a model change changes both.
  It also requires `qdrant_ids-<c>.json` (`:636-642`), which cannot be
  recorded again. It is the storage move's arbiter; the track needs its own.
- **Both models tokenize with `cl100k_base`,** which tiktoken reports for both
  names [measured]. The 8,191-token limit (`openai_client.py:42-43`) applies
  to both [verified source, `22-RESEARCH.md` Q3].

### What the decision needs

1. **The chunks it will ship with:** after 22.2-04's verdict. Both arms embed
   **identical chunk texts**, and each record header carries a digest of the
   chunk set. The judge refuses two arms whose digests differ, since then the
   comparison measures more than the model.
2. **One setting** for the model, read by all three constructors, plus a
   harness `--embedding-model` flag (22.2-01).
3. **Query vectors cached per model** (`vecs-<model>.json`), embedded once
   each. The existing cache already refuses to mix them.
4. **Fresh blind questions:** one set per corpus, written after the rule is
   committed (QD10).
5. **A committed rule** (QU7). This research proposes candidates below and
   commits none.
6. **`decide.py`,** reading both arms' records and applying the rule. Its
   verdict is its exit code.
7. **Each arm measured once**, as `rag_doc_app`, reported whichever way it
   falls.

### How sensitive a 15-question rule is

[measured, `pgvector-<c>.summary.json` in `22-03-records/`] The per-question
reciprocal rank at `top_k = 5` has a standard deviation of:

| | symbol RR | file RR |
|---|---|---|
| miniflux | 0.403 | 0.430 |
| mealie | 0.381 | 0.407 |

[inferred] What follows from that spread:
- One arm's MRR over 15 questions therefore carries a standard error near
  **0.10**. Over 45 pooled questions it is near 0.06.
- The difference between two arms on the same questions is less noisy, by an
  amount that depends on how correlated the arms are, which only the
  measurement shows.
- **A rule requiring "higher on each corpus of 15" decides small real
  differences largely by chance**, in both directions. The boost decision
  passed it with room to spare (+0.21 and +0.15 on symbol MRR). A model swap's
  effect is unknown. OpenAI's own general-benchmark figures are close (61.0%
  against 62.3%) [verified source, via `22-RESEARCH.md` Q3], and they say
  nothing about code retrieval here.

One more limit, [measured, `records-analysis.json`]: MRR at 5 cannot see
answers ranked 6–50. Those are 16 of 45 answering symbols on miniflux and 13
of 45 on mealie today. The judge can compute any cut up to 50 from the
recorded trace, so a rule may use @5, the product's cut and the precedent,
and report @20.

### Rule candidates for the user

**None of these is committed. The user picks, edits or writes one, and commits
it before the questions are written.** Each assumes 15 fresh questions per
corpus on miniflux, mealie and linkwarden (45).

- **M1 — superiority on every corpus (the boost protocol's shape).**
  - **Rule:** adopt 3-small only if, on each corpus's fresh set, symbol MRR@5
    is higher and file MRR@5 is not lower.
  - **Strength:** strict, with precedent.
  - **Weakness:** with three noisy 15-question sets, a real but modest
    improvement is likely to fail on one of them.
- **M2 — pooled superiority with a per-corpus floor.**
  - **Rule:** adopt only if all three hold:
    - over all 45 questions, symbol MRR@5 rises by at least 0.03;
    - file MRR@5 does not fall;
    - on no corpus does file MRR@5 fall by more than 0.067, which is one
      answer going from #1 to a miss on 15 questions.
  - **Strength:** more power than M1, and it still demands an improvement.
- **M3 — non-inferiority.**
  - **Rule:** adopt if all three hold:
    - pooled symbol MRR@5 is at least baseline − 0.02;
    - pooled file MRR@5 is at least baseline − 0.02;
    - no corpus's file MRR@5 falls by more than 0.067.
  - **Justification:** 3-small costs a fifth as much, and OpenAI labels
    ada-002 an older model.
  - **Weakness:** it can adopt a slightly worse model.
- **M4 — paired count.**
  - **Rule:** adopt if, pooled, the number of questions whose symbol RR rises
    exceeds the number whose symbol RR falls by at least 4, and file-level
    falls do not exceed file-level rises.
  - **Strength:** robust to one large swing.
  - **Weakness:** it ignores the size of each change.

**Recommendation:** M2 if the model should change only for better retrieval.
M3 if the user judges the price and the model's age reason enough to switch at
parity. The same rule family should serve 22.2-04 and 22.2-06, so the track's
three verdicts read alike.

### If 3-small is adopted

- **One setting** changes the default for the pipeline, the query engine and
  the cache lookup together.
- **Every indexed repository is re-embedded.** Before launch that is the
  benchmark corpora and 22-05's one live repository, for cents.
- **ISS-021's semantic cache** must key on the model when repaired (P4 already
  says so). Its 0.95 similarity threshold (`semantic_cache.py:30`) was chosen
  for ada-002. Cosine similarities are distributed differently across models
  [inferred; not verified here], so the threshold must be re-derived for
  3-small, not carried over. Recorded as a dependency; repairing the cache
  stays out of the track (Boundaries).
- **Dimensions:** the candidate is 3-small at its default of 1,536. A
  shortened dimension would be a different decision, and a migration.

## R7 — Acceptance criteria

Drafted in `22.2-ACCEPTANCE.md`, in `22-ACCEPTANCE.md`'s style: numbered,
testable, each naming the evidence that closes it. Four principles shaped them:
- **The order of record is checkable.** Every rule is committed before its
  questions, and every question set before its measurement. Git shows it, and
  the judge can refuse a rule committed after its questions.
- **The verdict is a script's exit code** on committed records, never a
  reading.
- **Correctness is proven with census numbers,** before and after, committed.
- **A failed rule ends a candidate.** Retrying needs a new rule and new
  questions.
