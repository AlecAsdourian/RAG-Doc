<objective>
Rebuild `chunks` as D2 decided, and move every writer of `chunks` onto it in
the same PR. The new table is:
- partitioned by `HASH (organization_id)` into 64 partitions;
- protected by row-level security on the parent **and on every partition**;
- tied to its tenant by a composite foreign key;
- carrying a `vector(1536)` and the model that produced it.

Also:
- create D1's `symbols` table;
- drop the foreign key from `retrievals` to `chunks`;
- keep `DELETE /api/repositories/{id}` honest now that the cascade stops at
  `chunks`.

**Why every writer moves in this PR.** The new table requires
`organization_id`, `embedding` and `embedding_model`. About ten Go and Python
test files and `PostgresWriter` insert rows without them, so landing the
migration alone would turn CI red on `main`.

**Output:**
- migration `000017_partitioned_chunks`;
- schema tests, including the partition-RLS guard and the measured
  cross-tenant leak written as a test;
- every writer of `chunks` updated;
- `PostgresWriter` storing each chunk's vector;
- the repository delete fixed.

**Estimate:** 16–22 h, 3 tasks. Task 2 touches many files, mechanically.
</objective>

**Locked decisions this plan implements:**

**P1** (U1): drop and recreate `chunks`, with **no DML**.

**P2** (correction to D2): RLS, FORCE and the policy on **every partition**.
- **Decided here, the question P2 left open:** do **not** also revoke the app
  role's direct privileges on the partitions.
- **Why:** grants live outside migrations. Both harnesses run
  `GRANT … ON ALL TABLES` **after** migrating, and production's grants belong
  to Phase 24, so a `REVOKE` in 000017 would be silently undone.
- Per-partition RLS is the guard, and it is tested without depending on grants.
- Recorded for Phase 24's grant model, **with the fact-check's addendum:**
  per-partition RLS closes the direct path only while grants **exclude
  `TRUNCATE`**, which row-level security does not govern. Both harnesses grant
  `SELECT, INSERT, UPDATE, DELETE` only. Phase 24's grants must keep it that way,
  and 000017's table comment says so.

**P3 — LOCKED 2026-09-17 by the user at this plan's approval: the composite
foreign key**, as below. The earlier justification contained a mistake, now corrected:
- **What the key guarantees:** `FOREIGN KEY (repository_id, organization_id)
  REFERENCES repositories (id, organization_id) ON DELETE CASCADE` makes a
  misfiled row unrepresentable **while the foreign-key triggers are enabled**.
- **⚠ What it does not guarantee (measured by the fact-check):** under
  `SET session_replication_role = replica`, a misfiled chunk inserted cleanly
  past the key, because foreign keys are enforced by triggers that replica mode
  switches off. This repository uses exactly that in `pkg/auth/testing.go:54-60`,
  for test cleanup.
- **Consequences:**
  - D5's "a trigger-disabled bulk load leaves no drift, or is documented as
    forbidden" **still applies**. 000017's `COMMENT ON TABLE` forbids loading
    `chunks` or `symbols` under replica mode or `DISABLE TRIGGER`.
  - **The drift query stays load-bearing.** It runs in CI at the end of the new
    test file.
  - No validating trigger is added; the constraint's name carries the message.

**P4** (U3): `embedding_model TEXT NOT NULL`; the model stays ada-002.

**P7 — LOCKED 2026-09-17 by the user at this plan's approval:** `symbols` is
**unpartitioned**, and `chunks` carries **one nullable**
`symbol_id REFERENCES symbols(id) ON DELETE SET NULL`.

**P17** (U9): drop `retrievals_chunk_id_fkey`.

**P15, stated as the transition it is.** Between this plan and 22-03, the

**ISS-031's rule, which this migration follows** (22-01):
- **Declare every foreign key inside `CREATE TABLE`,** on the parent `chunks`
  and on `symbols`. Partitions created with `PARTITION OF` inherit it.
- Never rely on the session's tenant. This migration runs **in the same session**
  as 000013's and 000015's loops in the seeded gate. **After 000015 the setting
  reads `''`**, as the fact-check measured, not the last organization's id. So
  anything here that validated a constraint or evaluated a policy would fail
  with `22P02`.
- 22-01's gate proves the migration in exactly that shape.

**Measured facts** (`22-RESEARCH.md` Summary and Q2; confirmed by the
fact-check). D2's DDL, transcribed onto the real schema:
- **The partitions got no RLS.** All 64 showed `relrowsecurity = false`.
- **The app role could read and overwrite other tenants' rows.** Tenant A,
  addressing B's partition directly, read B's row and got `UPDATE 1` on it.
- **Per-partition RLS closes it:** B's rows read 0 and the update matched 0.
- **`Subplans Removed: 63`,** from the policy alone.
- **`trg_assert_tenant` is cloned to all 64 partitions.**
- **A misfiled row gets `23503`.**
- **`retrievals.chunk_id REFERENCES chunks(id)` cannot be recreated.**
- **A trigger cannot fill in a partition key:** `0A000`, "moving row to another
  partition during a BEFORE FOR EACH ROW trigger is not supported".

**The policy expression, stated.** On the parent and on every partition:
```sql
USING (organization_id = current_setting('app.current_tenant', true)::uuid)
```
Scalar equality on the partition key is what lets the planner prune.
000008's two-hop `EXISTS` form would not prune.

**P17's consequence, decided: delete explicitly and keep the contract.**
- In the repository delete's tenant transaction, before deleting the repository:
  1. count the feedback reachable through the repository's chunks;
  2. `DELETE FROM retrievals WHERE chunk_id IN (SELECT id FROM chunks WHERE
     repository_id = $1)`, with **the same predicate** as the count;
  3. let `feedback` cascade from `retrievals`, whose foreign key stays.
- **Why:** it keeps the documented contract (`docs/api-repositories.md:255-295`)
  for every row it can reach, and those tables hold **zero rows** today because
  nothing writes them.
- **The limit, stated:** a retrieval whose chunk a re-index already replaced is
  unreachable through any chunk, and after 22-05 every full ingest replaces a
  repository's chunks. The shape of that link is U9's deferred decision.
- **What catches a missing delete (corrected):** the existing
  `ingestedCounts(orgA) == {1,1,1}` assertion at
  `repositories_connect_test.go:1236`. Feedback's row-level security runs
  through `queries` and `projects` (`000008:82-92`), so orgA's surviving feedback
  is still counted. The earlier plan claimed a count-only test would pass; it
  would not.

**Lessons from Phase 21 that apply here:**
- **A changed migration needs a FRESH database.** Drop 22-01's scratch database,
  or `docker rm -f rag-doc-isolation-tests-pgv16`, between edits to 000017.
- **Verify in the deployment shape.** 22-01's gate runs 000017 as a
  non-superuser owner on seeded rows, in one session with 000013 to 000016.
- **Ask what the fixture cannot distinguish.** Two random organizations share a
  partition 1 time in 64, so a cross-partition test asserts its premise (the
  rows are in different partitions, checked through `tableoid`).
- **Neuter; do not delete.** Mutate a policy to
  `USING (organization_id IS NOT NULL)`; deleting it changes what exists.
- **Never prove drift detection by dropping an FK on the shared container**
  (ISS-032). Use a 22-01 scratch database.
- **Commit before mutating; prove each mutation landed.**
