<objective>
Rebuild `chunks` as D2 decided, and move every writer of `chunks` onto it in
the same PR. The new table is:
- partitioned by `HASH (organization_id)` into 64 partitions;
- protected by row-level security on the parent **and on every partition**;
- keyed to its tenant;
- carrying a `vector(1536)` and the model that produced it.

- create D1's `symbols` table;
- drop the foreign key from `retrievals` to `chunks`;
- keep `DELETE /api/repositories/{id}` honest now that the database cascade
  stops at `chunks`.

`organization_id`, `embedding` and `embedding_model` on every row. About ten Go
and Python test files and `PostgresWriter` insert rows without them. Landing
the migration alone would turn CI red on `main`.

**Output:**
- migration `000017_partitioned_chunks`;
- schema tests, including the partition-RLS guard and the measured cross-tenant
  leak written as a test;
- every Go and Python writer of `chunks` updated;
- `PostgresWriter` writing each chunk's vector with it;
- the repository delete fixed.

**Estimate:** 16–22 h, 3 tasks. Task 2 touches many files, but mechanically.

**Two decisions in this plan are PROPOSED and decided by the user when this plan
is approved: P3 and P7.** Both are written here on the recommendation. Each
section below says what changes if the user picks the alternative.

**⚠ P3 — PROPOSED, decided by the user at this plan's approval. The plan is
written on the recommendation.**

**Recommended: tenancy by composite foreign key.**
```sql
FOREIGN KEY (repository_id, organization_id)
  REFERENCES repositories (id, organization_id) ON DELETE CASCADE
```
The key sits on `chunks` and `symbols`, named `chunks_repo_tenant_fk` and
`symbols_repo_tenant_fk`. This is 21-01's and 21-02's pattern.
- **A mismatched tenant is unrepresentable,** not merely rejected. The check
  holds even with triggers disabled, because foreign-key checks bypass
  row-level security.
- **No filling trigger.** The inserting code supplies `organization_id`.

**The alternative: D5 as written, a `BEFORE INSERT OR UPDATE OF
organization_id, repository_id` trigger that validates the value against
`repositories`.** Picking it changes Task 1 as follows:
- `chunks_fix_tenant()` and `symbols_fix_tenant()` are transcribed from
  000014's `ingestion_jobs_fix_tenant()`: schema-qualified, with
  `SET search_path = public, pg_temp`. They are attached to the parent, and the
  guard test asserts the trigger on all 64 partitions.
- Plain `REFERENCES repositories(id) ON DELETE CASCADE` stays for deletion.
- The misfiled-row test expects the trigger's message, not `23503`.
- The drift query becomes **load-bearing**, because a disabled trigger allows
  drift. The migration's `COMMENT ON TABLE` must say trigger-disabled bulk loads
  are forbidden (D5's third verification).
- The drift self-test becomes a plain insert with the trigger disabled, not an
  FK drop.
- Cost is about equal. What is lost is the guarantee that holds when a trigger
  is off.

Either way, every writer supplies `organization_id`. **A trigger cannot fill in
a partition key.** Measured on PostgreSQL 16 on 2026-09-17: a `BEFORE INSERT`
trigger that sets the key raised `moving row to another partition during a
BEFORE FOR EACH ROW trigger is not supported`, because routing happens on the
value the writer supplied. So Task 2's churn is the same under both options.

**⚠ P7 — PROPOSED, decided by the user at this plan's approval. The plan is
written on the recommendation.**

**Recommended: `symbols` unpartitioned, and one nullable
`chunks.symbol_id UUID REFERENCES symbols(id) ON DELETE SET NULL`.**
- Partitioning `symbols` would force every foreign key into it into a composite
  key. That is the same break measured for `retrievals`, and it would hit
  `chunks`, `symbol_edges` and D4's `memory_anchors`.
- `symbols` has no vector index, so D2's index-size argument does not reach it.
- Nothing writes `symbols` until 22.1-01. It exists now so that `chunks` can
  carry the FK from the day it is created.

**Alternative (a): a join table instead of the FK.** Task 1 drops
`chunks.symbol_id` and adds
`chunk_symbols (organization_id, chunk_id, symbol_id)`, which has:
- primary key `(organization_id, chunk_id, symbol_id)`;
- a **composite** FK `(organization_id, chunk_id) REFERENCES chunks
  (organization_id, id) ON DELETE CASCADE`, needed because the partitioned
  table's key includes the tenant;
- an FK to `symbols`;
- RLS, FORCE, the policy, `trg_assert_tenant` and the P3 tenant guarantee;
- an entry in `protectedTables`.

That adds about 3–5 h. Nothing writes it until 22.1-01.

**Alternative (b): partition `symbols` as well.** `symbols` gets 64 partitions,
each with its own RLS (P2 applies to it too). Its key becomes
`(organization_id, id)`, and `chunks.symbol_id` becomes a composite
`(organization_id, symbol_id)` FK. That adds about 3–4 h here, and makes every
future FK into `symbols` composite.

**P17's consequence, decided here: delete explicitly, keep the contract.**
- **Today's cascade:** `DELETE /api/repositories/{id}` relies on
  `chunks → retrievals → feedback` cascading, and reports `feedback_deleted` by
  counting through that chain first (`repositories.go:336-341`).
  `docs/api-repositories.md:255-295` documents it as the one irreplaceable
  number a user is told about.
- **What breaks:** with the key dropped, the cascade stops at `chunks`. The
  response would report feedback it no longer deletes.
- **Decision:** in the same tenant transaction, before deleting the repository:
  1. count the feedback reachable through the repository's chunks;
  2. `DELETE FROM retrievals WHERE chunk_id IN (SELECT id FROM chunks WHERE
     repository_id = $1)`, using the **same predicate** as the count;
  3. let `feedback` cascade from `retrievals`, since that foreign key is kept.
- **Why not change the response instead:** that would drop a documented field
  Phase 23's confirmation dialog is told to show, to fix a case that has **zero
  rows** today, because nothing writes `retrievals`.
- **The limit, stated rather than hidden:** a retrieval whose chunk a re-index
  already replaced points at nothing, so no delete can reach it through a
  chunk. After 22-05, every full re-ingest replaces all of a repository's
  chunks, so this is real, not rare. The link's final shape is U9's deferred
  decision. It is recorded in the doc and in the summary for when feedback
  ships.

**Lessons from Phase 21 that apply here:**
- **A changed migration needs a FRESH container.** Between edits to 000017,
  `docker rm -f rag-doc-isolation-tests-pgv16`, the name 22-01 set. golang-migrate
  will not re-apply a recorded version.
- **Verify in the deployment shape.** 22-01's seeded gate runs 000017 as a
  `NOSUPERUSER NOBYPASSRLS` owner on seeded rows. Add its 000017 assertions
  here.
- **Ask what the fixture cannot distinguish.**
  - Two random organizations hash to the **same** partition 1 time in 64. A
    cross-partition test must assert its premise (the two tenants' rows are in
    different partitions, found through `tableoid`) and regenerate ids if not.
  - A delete test that checks only `feedback_deleted` passes while the rows
    survive. Assert the rows are **gone**.
- **Neuter; do not delete.** To mutation-test a policy, set it to
  `USING (organization_id IS NOT NULL)` rather than dropping it, so the object
  still exists and only its effect goes. Deleting a SQL predicate outright can
  change a statement's arity and produce a false kill (21-07's M1a).
- **Never prove the drift query by dropping an FK on the shared container.**
  That is ISS-032's deadlock. Prove it in a fresh, unshared container.
- **Commit before mutating, and prove each mutation landed:** the mutated text
  is present and the original absent.
- **Environment facts:** the CRLF test fails locally only; point
  `DATABASE_TEST_URL` at a scratch pgvector container, not 5434; run `-race` in
  `golang:1.25`; use the workers venv for testcontainers.
