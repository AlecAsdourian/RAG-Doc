<objective>
Turn the queue on. This plan:
- registers a `full_ingest` handler that runs `fetch → parse → embed → store`,
  writes the repository's chunks and vectors in the completion transaction, and
  reports each stage;
- teaches the runtime the endings a real ingest needs:
  - a cap ends the job `dead` in one attempt (U6);
  - an installation suspended or uninstalled **mid-run** takes the same ending
    Phase 21 gives it at claim time;
  - a refused token writes nothing;
- sets P16's operating numbers, **provisionally**;
- declares the compose `workers` service, without the App key, and without
  letting it start by accident.

Then **prove it on a real repository**: `AlecAsdourian/ES-SC-API-Navigator`,
approved by the user, indexed end to end from the development App into a
**scratch** database, and searched.

**Output:**
- `workers.ingest`;
- the runtime's new endings;
- `REGISTRY` filled;
- the operating numbers;
- a deliberately changed entrypoint test;
- an end-to-end test with fakes;
- the recorded live proof.

**Estimate:** 15–21 h, 3 tasks.
</objective>

**The endings, reconciled with Phase 21** (fact-check c1, c2).

*What exists today.*
- `return` → complete.
- `Unfinished` → defer with no delay, and **only** during a shutdown.
- `LeaseLost` → write nothing (`runtime.py:973-985`).
- Anything else → fail, with backoff; the job is `dead` at 5 attempts.

*What this plan adds, each mapped to an ending Phase 21 already defines where
one exists.*

| Raised by the handler | Ending | Why |
|---|---|---|
| **`Rejected(reason)`** (and `workers.fetch.FetchRejected`, which becomes its subclass) | **new**: a fenced `REJECT_SQL` → `dead` in one attempt, `sync_state = failed` | A cap violation is deterministic. As a plain `fail` it would re-download up to 500 MB five times over ~81 minutes. U6 says it "ends `dead`". |
| **`InstallationSuspended`** (22-04's `409`) | Phase 21's **`defer`**: 60 minutes (`suspended_defer`), attempt handed back, `sync_state` unchanged | The same policy as at claim time (`docs/api-ingestion-jobs.md:392-424`, `DEFER_SQL`'s comment). A suspension mid-run must **never** dead-letter a healthy repository. The earlier plan's mapping to `Rejected` did exactly that, and is withdrawn. **Known and documented, not changed:** `mark_started` has already projected `syncing` and `DEFER_SQL` writes no projection, so the repository reads `syncing` for up to 60 minutes. That is the class 21-06's second review accepted for a shutdown deferral, but for an hour it is user-visible. `DEFER_SQL` is frozen (21-05) and is not changed. The **job row** is the truth: `state = 'queued'`, `run_after` about an hour out, `last_error` saying why, `lease_expires_at` NULL, `stalled` false. `docs/api-ingestion-jobs.md` says so (Task 1). |
| **`InstallationUninstalled`** (22-04's `409`) | Phase 21's **`abandon`**: `superseded`, `never_synced` | As at claim time. |
| **`TokenRefused`** (22-04's **marked** `404`) | the handler **raises `LeaseLost`** → nothing is written | The earlier plan returned `None`, which **writes `completed` for undone work**. The token route refuses an **expired** lease, `COMPLETE_SQL` does not check expiry (`transitions.py:224-228`), and `lease_lost` is only set on the heartbeat's next tick. So an expired but unreclaimed lease reached `complete()`. |
| **`InternalApiMisrouted`** (22-04: any response **without** the route's marker, an unmarked 404 included) | an ordinary failure → **`fail`**: attempt consumed, backoff, `last_error` naming the misconfiguration | A misconfigured `INTERNAL_API_URL` (the public router answers chi's 404) must fail **loudly**. Treated as a lost lease, it would expire five times with `last_error` NULL (fact-check c3). |
| **`should_abort()`** is true between stages | the handler **raises `LeaseLost`** | The same reasoning. Do not rely on the runtime's `lease_lost` check happening to have fired. |

**Stage vocabulary** (fact-check a6).
- **What was documented:** `clone|parse|embed|store` (`runtime.py:557`, and
  000014's `--` comment). There is no clone any more (U5).
- **What it becomes:** **`fetch|parse|embed|store`**, in
  `docs/api-ingestion-jobs.md` and `runtime.py`'s docstring. 000014's `--`
  comment is not schema and is left alone; the doc says so. `last_stage` stays
  advisory text, with no `CHECK` (21-07).
- **Where `store` is written:** `report_progress` cannot run inside
  `write_results`. It uses the same connection, and psycopg2's re-entrancy guard
  refuses it (`runtime.py:562-575, 598`). `COMPLETE_SQL` does not touch
  `last_stage`. So the handler reports `store` **as its last statement, just
  before it returns** `write_results`.
- **What a completed job therefore reads:** `last_stage = 'store'`. That is what
  the tests assert.

**`progress` is replaced whole on every report, so every report carries the
cumulative counts** (fact-check, would break).
- `PROGRESS_SQL` overwrites the column (`runtime.py:336-341`), and
  `report_progress(stage)` with no payload writes NULL (`runtime.py:585-592`).
- A `store` report of `{"chunks": n}` would therefore erase the skip counts
  written at `fetch`, and the "progress counted the `.env`" checks would read
  nothing.
- **The handler contract:** the handler keeps one running dict and passes the
  **whole** dict on every call. Each stage adds its keys and removes none:
  - `fetch`: `files_indexable` and `skipped`;
  - `parse`: `files_parsed` and `chunks`;
  - `embed`: `chunks_embedded`;
  - `store`: `chunks_stored`.
- The tests assert on the **completed row's** `progress`, which must still hold
  `skipped`.
- 22.1-03 documents this as the progress contract.
