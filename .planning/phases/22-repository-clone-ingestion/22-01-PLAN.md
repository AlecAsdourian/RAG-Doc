**⚠ ISS-031 IS LIVE, not latent. It was measured by the fact-check and
reproduced by the planner on 2026-09-17.**

*The failure.*
- A database owned by a `NOSUPERUSER NOBYPASSRLS` role (the deployment shape,
  21-01) was migrated to **10** and seeded with two tenants' rows, each under its
  own scope. One `migrate up` was then run as that owner.
- 000013's backfill loop (`set_config('app.current_tenant', org.id, true)`,
  `000013:79`) leaves `app.current_tenant = ''` on the migrating session once it
  commits. That is ISS-013's placeholder behaviour: nothing short of a new
  session clears it.
- 000014's `ALTER TABLE ingestion_jobs ADD CONSTRAINT
  ingestion_jobs_repo_tenant_fk` (`000014:158-161`) then validates the new
  foreign key. Under FORCE RLS as the owner, the validation reads `repositories`
  through its policy, evaluates `''::uuid`, and fails with
  `invalid input syntax for type uuid: ""`.
- `schema_migrations` is left at **14, dirty**.
- The comment above that statement, "foreign-key checks run with row-level
  security bypassed", is true of per-row checks and **not** of `ADD CONSTRAINT`'s
  validation.

*Where it does and does not bite.* **Measured, 2026-09-17:** with a
**superuser** owner, the identical seeded 10→15 upgrade passes. Superusers
bypass RLS even under FORCE.
- The **compose** database's migrations run as its `POSTGRES_USER`, a superuser,
  so migrating it from 10 today does **not** hit this.
- The **harnesses and CI** migrate empty databases, where 000013's loop never
  calls `set_config`.
- **What it breaks is the deployment shape**: the first time a production-like
  database, owned by a non-superuser, is migrated across 13 and 14 with rows in
  it. Nothing is deployed yet (Phase 24), so the fix still costs nothing.

*The fix, measured to work on 2026-09-17.* **Declare
`ingestion_jobs_repo_tenant_fk` inside 000014's `CREATE TABLE`** instead of in a
later `ALTER TABLE`.
- A foreign key created with its table has no existing rows to validate, so no
  validation query runs and the poisoned setting is never read.
- **Measured:** with the edited 000014, the same seeded deployment-shape upgrade
  reaches **15, not dirty**, and both tenants' repositories are backfilled with
  one queued job each.
- **Measured:** the resulting schema is **identical** to the original path's.
  A `pg_constraint`, `pg_indexes`, `information_schema.columns`, `pg_trigger`,
  `pg_policies` and RLS-flag dump matches line for line (295 lines), and the
  constraint reads `validated=true` both ways.

*Why editing an applied migration is acceptable here, and only here.*
- Nothing is deployed. golang-migrate never re-applies a recorded version, so a
  database that has already applied 000014 (CI's ephemeral ones, developers'
  harness containers, the fact-check's scratch databases) keeps its existing,
  identical constraint and is not touched.
- Only databases that have not reached 14 take the new path. The compose
  database is at 10.
- **After the first production deploy this fix is no longer available.** The
  class must then be handled by the runner or by the migrations themselves,
  which is why the rule and the gate below exist.

*What it does not fix, stated.* 000013 still poisons its session with `''`, and
000015 leaves the last organization's id set for the rest of the run. So a later
migration **in the same run** that validates a constraint or runs DML against an
RLS table would fail (on `''`) or quietly see one tenant (on 000015's leftover).

Hence **the rule**, written into ISS-031 and into 000014's comment, and followed
by 22-02:
- declare foreign keys on new tables **inside `CREATE TABLE`**;
- never rely on the session's tenant. A migration that needs one sets it itself,
  per organization, as 000015 does;
- **never** fix a validation by setting a sentinel tenant, which makes it see
  zero rows and pass vacuously.

The gate enforces the rule, because it runs every migration after 10 in one
session on seeded rows.

*The alternatives, rejected, with their trade-offs:*
- **Lift FORCE on `repositories` around the constraint,** as 000012 does. It
  works, but it briefly disables a guard, which 21-01 deliberately avoided. The
  inline declaration needs no guard lifted at all.
- **Make every policy tolerant of `''`** with `NULLIF`. That is ISS-013's
  territory: six tables and more, and it turns a loud failure into silent empty
  results.
- **One session per migration.** Correct for the whole class, but every runner
  has to honour it: the Go harness, the Python conftest, CI, the gate and Phase
  24's deploy. A single `migrate up` anywhere reintroduces the bug.

**The extension, measured 2026-09-17** (`vector` 0.8.6, `trusted = f`).
- As a non-superuser, with the extension **absent**:
  `CREATE EXTENSION IF NOT EXISTS vector` →
  `permission denied to create extension "vector"` /
  `Must be superuser to create this extension`.
- As a non-superuser, with it **present**: a NOTICE, `already exists, skipping`,
  and success.
- A bare `CREATE EXTENSION vector` with it present → `already exists`.

So **000016 is a plain `CREATE EXTENSION IF NOT EXISTS vector`**. No `DO` guard
is needed, and the earlier plan's claim that one was needed is withdrawn. The
gate tests the two cases that matter: absent, where it fails with the privilege
error, so an operator must create it; and present, where it passes as a
non-superuser owner.

**What the seed can contain at version 10** (fact-check a2).
`github_installations.uninstalled_at` arrives in **000012** (`000012:97`), so an
uninstalled installation cannot be seeded at 10. The gate therefore seeds in two
steps:
1. **At version 10:**
   - four organizations with default projects;
   - installations;
   - repositories in `pending`, `pending` with `installation_id` NULL, and
     `synced`;
   - ingestion runs;
   - chunks for two organizations;
   - one `queries` → `retrievals` → `feedback` chain.
2. **Migrate to 12**, in its own `migrate` call. Then mark one installation
   `uninstalled_at = NOW()`, **under that installation's tenant**.
3. **One `up`** from 12 to the newest version, **in one session**, which is where
   ISS-031 lives.

The pause at 12 costs nothing: the poison starts at 13.

**Lessons from Phase 21 that apply here:**

- **Verify in the DEPLOYMENT shape.** The whole of ISS-031 is invisible to the
  harness superuser.
- **Ask what the fixture cannot distinguish.** A single-tenant seed cannot tell
  "backfilled all" from "backfilled the last tenant set", and the fact-check's

- **Commit before mutating; prove each mutation landed** (the mutated text is
  present and the original is absent).

  - `-race` needs `golang:1.25`.
