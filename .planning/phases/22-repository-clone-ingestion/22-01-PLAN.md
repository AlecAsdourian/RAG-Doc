<objective>
Put `pgvector/pgvector:pg16` behind every Postgres this project starts:
- the Go test harness
- the Python test harness
- CI
- compose

Prove all of them with a migration that fails on any image lacking the
extension. Then land ISS-031's seeded-migration gate **before** the storage
migration (22-02) exists, so the largest schema change this project has made is
tested on a database that has rows in it.

Also delete `pkg/vectordb`, the dead Go Qdrant client (K2). It is dead code
whatever happens to Qdrant, and it is the only Go dependency on Qdrant.

**Output:**
- migration `000016_enable_pgvector`
- the image swap in four places, with the harness's reuse container renamed
- a Go test that migrates a seeded database from version 10 in the deployment
  shape
- `pkg/vectordb` gone

**Estimate:** 6–9 h, 2 tasks.
</objective>

**Measured facts this plan rests on** (`22-RESEARCH.md` Q2). All were measured
on 2026-09-17 on scratch containers.
- **No current image has pgvector.** `postgres:16-alpine` (16.15) has no
  `vector.control`.
- **`pgvector/pgvector:pg16` works.** It is PostgreSQL 16.15 with pgvector
  0.8.6, at digest `sha256:ccc6e83d6e35e931dc7c5def2022729d5a6c370318d099181995567ff1fb4d6b`.
  Re-check the digest with `docker buildx imagetools inspect` before pinning it:
  a digest copied from a document is a claim, not a fact.
- **Creating the extension needs a superuser.** `pg_available_extension_versions`
  reports `vector | 0.8.6 | superuser=t | trusted=f`, and no
  `shared_preload_libraries` entry is needed.
- **Both harness paths produce the same schema.** All fifteen current
  migrations apply through golang-migrate and through the Python conftest's
  raw-SQL path (`conftest.py:98-110`), with identical resulting schemas. Both
  suites pass on the new image: Python 284/284; Go all `ok` except the known
  CRLF test.
- **The Go harness waits for the right log line.** It waits for
  `database system is ready to accept connections` twice
  (`container.go:103-105`), and the Debian-based pgvector image prints it
  twice. Measured.

**⚠ The trap P14 exists for: the Go harness reuses its container by NAME and
never checks the image.**
- **Where:** `WithReuseByName(containerName)` (`container.go:101`) reaches
  testcontainers-go v0.44.0's `ReuseOrCreateContainer`, which finds a container
  by name and uses it (`docker.go:1424-1441` in the module cache). Ryuk is
  disabled (`container.go:93-95`), so `rag-doc-isolation-tests` outlives every
  run.
- **Measured failure:** with the image constant changed and the name kept, a
  leftover `postgres:16-alpine` container was reused. The first
  `CREATE EXTENSION vector` then failed with `extension "vector" is not
  available`.
- **The fix is the new name.** `rag-doc-isolation-tests-pgv16` means a stale
  container is simply not found.
- **Do not `docker rm` the old container.** It belongs to the developer; the
  new name makes it irrelevant.
- **The Python harness is unaffected.** It never reuses across sessions
  (`conftest.py:36-41`).

**⚠ Compose: this plan changes the image and never starts the service.**
- **Hands off the compose volume.** `testtgsd_postgres_data` (port 5434) holds
  harness and benchmark data at migration **10**, measured read-only. This plan
  never starts compose, never runs a migration against it, and never touches
  its volume.
- **[not verified] A possible index problem on the old volume.** The volume was
  initialised by Alpine (musl libc) and the new image is Debian (glibc). Text
  indexes built under one C library's collation can be wrong under another.
- **This plan documents; the user decides.** `docs/local-development.md` should
  say to recreate the compose Postgres volume (its data is re-creatable, per P1)
  or `REINDEX DATABASE` after pulling this change.

**ISS-031, the gate this plan builds.**
- **The hazard:** a migration that sets `app.current_tenant` (000013's and
  000015's backfills) leaves the session poisoned for later DML in the same run.
  That passes on CI's empty database and fails on a database with rows.
- **Why baseline 10:** the compose database is itself a seeded database at
  **migration 10**, measured. Migrating it to the latest version is the exact
  scenario ISS-031 describes. So the gate seeds at **version 10**, runs `up` to
  the latest, and asserts what each later migration did to the seeded rows.
  22-02 adds its own assertions for 000017.

**Lessons from Phase 21 that apply here. Each one produced a real finding.**
- **A changed migration needs a FRESH container.** golang-migrate never
  re-applies a recorded version. Iterating on `000016` against the reused
  container silently tests the old file: `docker rm -f
  rag-doc-isolation-tests-pgv16` between edits.
- **Verify in the DEPLOYMENT shape** (21-01). Tables are owned by a
  `NOSUPERUSER NOBYPASSRLS` role under `FORCE ROW LEVEL SECURITY`, and
  migrations run while connected as that role. The harness superuser bypasses
  exactly what 000013's and 000015's backfills must survive.
- **Ask what the fixture cannot distinguish.**
  - A seed with one organization cannot show a backfill that only processed the
    last tenant it set.
  - A seed with no `pending` repository cannot show 000015 creating jobs.
  - Seed several of each.
- **Commit before mutating, and prove each mutation landed.** The mutated text
  is present and the original is absent, checked before believing the result.
- **Environment facts:**
  - `TestSignatureComparisonIsConstantTime` is a known CRLF-only local failure.
  - `pkg/auth`'s helpers default to port **5434**, the compose database. Point
    `DATABASE_TEST_URL` at a scratch pgvector container.
  - `-race` needs the `golang:1.25` container.
  - `testcontainers` needs the workers venv.
</context>

**A Go test in `pkg/testing/isolation` that runs in `go test ./...`,** so CI
gates on it with no new workflow step.

**It needs its own FRESH container.** Never use the shared reused one, whose
schema is already at the newest version: a migration cannot be re-applied
there, and dropping or migrating it down would break every package running in
parallel. So:
- Start `postgresImage` without `WithReuseByName`.
- `Terminate` it in `t.Cleanup`. Ryuk is disabled process-wide by
  `setupContainer`, so nothing else will remove it.
- Assert its name is not `containerName`.

**The deployment shape**, as 21-01 measured it:
1. As the container superuser:
   - create `rag_doc_owner NOSUPERUSER NOBYPASSRLS LOGIN` and make it the
     database owner;
   - create the `vector` extension, as an operator would.
2. Run golang-migrate **connected as `rag_doc_owner`** up to **version 10**.
   Add a `migrator.go` helper, `applyMigrationsTo(dsn, dir, version)`, using
   `m.Migrate(version)`.
3. Create `rag_doc_app` with the grants `ensureAppRole` gives. Load
   `testdata/seed_at_000010.sql` **as `rag_doc_app`, each tenant's rows under
   that tenant's `set_config('app.current_tenant', …, true)`**. That is the
   deployment path for writes, and the only one `trg_assert_tenant` accepts.
4. `m.Up()` as `rag_doc_owner`, to the newest version.
5. Assert `schema_migrations` is at the newest version and `dirty = false`.

**The seed**, written against schema 10:
- four organizations, three of them with repositories;
- at least one repository per organization in each of three `sync_state`s:
  `pending` with a live installation, `pending` with `installation_id` NULL,
  and `synced`;
- one uninstalled installation;
- ingestion runs and chunks for two organizations;
- one `queries` → `retrievals` → `feedback` chain.

Why this shape: every later migration's DML must see more than one tenant. A
single-tenant seed cannot tell "backfilled all" from "backfilled the last
tenant set" (21-01).

**Assertions, one per migration with an effect on data**, read as the superuser
so RLS cannot hide a gap:
- **000013:** every seeded repository has `organization_id` equal to its
  project's.
- **000015:**
  - a `pending` repository under a live installation has exactly one `queued`
    `full_ingest` job;
  - the unsyncable ones have none and read `never_synced`.
- **000016:** the `vector` extension is present, and `rag_doc_owner` **never
  called** `CREATE EXTENSION`. This works because the guard skipped it: had it
  been called, the non-superuser would have raised.
- **Every seeded row outside `chunks` still exists.** 22-02's assertions add
  what 000017 deliberately rebuilds.
- **The session is not poisoned.** After `Up()`, a fresh statement on the
  migration connection can read `repositories` under a new tenant. That is
  ISS-031's hazard, stated as a test.

**Mutation checks.** Each runs on a copy, each is confirmed present before its
result is believed, and the results are recorded:
- a `000013` copy whose loop sets the tenant only for the **first**
  organization;
- a `000016` copy with a bare `CREATE EXTENSION vector` (it must fail as
  `rag_doc_owner`);
- the seed's second organization removed, to show whether the 000013 assertion
  still distinguishes anything. It should fail to catch the first mutation,
  which is the fixture lesson written down.

Put each mutation in a scratch migrations directory passed to the test through
an environment variable read only by this test. **Never edit the committed
migration files.**
