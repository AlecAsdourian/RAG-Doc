<objective>
Route every GitHub webhook that requests or cancels work through `pkg/jobs`:
- `push`
- `installation_repositories` (`added` and `removed`)
- `installation` `deleted`

After this, no webhook uses `sync_state` as a queue.

Two more things ship with it:
- **A race test.** It proves the bulk case (L8) queues every repository; that case once silently lost two of three in review.
- **A one-off migration.** It gives a job to every repository left `pending` by the old path.

Output:
- producer calls in `github_webhook_events.go`
- migration `000015_backfill_ingestion_jobs`
- tests on the real receiver
- updated webhook docs
</objective>

**How the receiver runs.**
- Each handler resolves its tenant with `resolveInstallation` and does tenant work through `inTenant` (around 422-459).
- The delivery claim and outcome are recorded by separate pool statements, outside the tenant transaction (`github_webhook.go`, around 296-331).
- **Handlers never see the delivery id.** Only `Receive` has it; `dispatch` takes `(ctx, event, payload)` (`github_webhook.go:181, 222, 347-349`). Don't change that signature for logging. The outcome string `Receive` records is already stored against the delivery id, so put the counts there.

**A failed delivery is re-claimed on redelivery** (`claimDelivery` re-claims `'failed'`), so a handler can run twice.
- The comment at `github_webhook.go:227-232` says a failure "is not automatically retried, by design", which contradicts the code. Correct it.
- Every producer call here must be safe to repeat. The upsert is.

**One interaction to handle.** Under 21-05's projection, a repository whose job is retrying shows `failed`. `markUninstalled`'s `('pending','syncing')` filter would leave it `failed` after its job is superseded. That is exactly the retry-looking state the comment forbids. Use the repository ids `SupersedeLive` returns.

**⚠ THE PRODUCER SIGNATURES 21-03 SHIPPED,** which differ from what this
plan was written against. Read `pkg/jobs/producer.go` before writing a call:

```go
func Enqueue(ctx, tx pgx.Tx, reqs []jobs.EnqueueRequest) ([]jobs.EnqueueResult, error)
func SupersedeLive(ctx, tx pgx.Tx, organizationID string, repositoryIDs []string) ([]string, error)
```

- **`SupersedeLive` takes the organization,** added in PR #39's review. It is
  the ONLY tenant scope that statement has: `ingestion_jobs` has no
  row-level security and the UPDATE touches neither `organization_id` nor
  `repository_id`, so `trg_ingestion_jobs_tenant` never fires. **This plan
  is the reason it exists.** A webhook resolves repositories by
  `github_repo_id`, which `idx_repositories_project_github_repo` makes
  unique only PER PROJECT, never globally, so a resolution that is less
  careful than `github_webhook_events.go:288-296` already is can hand this
  function another tenant's repository. With the predicate it cancels
  nothing and the id is simply absent from the return value; without it, it
  cancels another tenant's in-flight ingest, successfully and silently.
  Pass the handler's own resolved tenant, never a payload field.
- **`Enqueue` is guarded by the database** by contrast — its `BEFORE INSERT`
  trigger refuses a mismatched tenant with 42501 — so the asymmetry is
  deliberate, not an oversight to tidy up.
- **A rerun flag on an unstarted job is cleared by `Enqueue` itself.** So
  `WasExisting = true` means "a live job already existed and this call
  joined it", NOT "a rerun is now pending". A `push` whose outcome string
  says `"rerun flagged"` on the strength of `WasExisting` would therefore
  be wrong for a job that has not been claimed yet; say "joined the live
  job", or read the row back if the outcome has to be exact.

**Handlers,** all in their existing tenant transactions:

- **`push`** (default branch only, unchanged):
  - Call `jobs.Enqueue(incremental)` for the connected repository.
  - Outcome is `"queued"` when a job was inserted, `"rerun flagged"` when `WasExisting`, or the existing `"ignored: repository not connected"`.
  - Remove the `sync_state` write and its `<> 'syncing'` guard; the upsert lets a live job absorb the push (L7).
- **`installation_repositories` `added`:**
  1. Find the known rows whose `installation_id` will actually change: `SELECT … FOR UPDATE OF r`, then compare in Go.
  2. Update `installation_id` for all matched rows, as today.
  3. Call `jobs.SupersedeLive` for the changed ids, passing the handler's resolved organization.
  4. Call `jobs.Enqueue(full_ingest)` for **every** matched row, in one call. Rows with an unchanged installation and a live job are flagged `needs_rerun`, not duplicated.
  - Unknown repositories are still not inserted.
  - Outcome string: counts of inserted, flagged and superseded.
- **`installation_repositories` `removed`:** keep `installation_id = NULL, sync_state = 'never_synced'`, and add `jobs.SupersedeLive` for those repositories. A job for a repository the App can no longer read will fail anyway, so stop it promptly (L4).
- **`installation` `deleted`:**
  - Call `jobs.SupersedeLive` for every repository of that installation.
  - Widen the stand-down to `WHERE installation_id = $1 AND (sync_state IN ('pending','syncing') OR id = ANY(<superseded ids>))`. The `pending` and `syncing` states still catch rows stranded before this phase.
  - Keep the comment about `'failed'`.
- **`suspend`:** no change here. The worker defers jobs for suspended installations at claim time without consuming an attempt (21-05, 21-06).
- **Fix the stale redelivery comment** in `github_webhook.go`.

**Logging.** Handlers log with `slog`: repository ids and counts, no payload bodies. The delivery id is attached where `Receive` records the outcome.

**Migration `000015_backfill_ingestion_jobs`.** Once this plan ships, only `pkg/jobs` writes `pending`. Rows set `pending` by the old paths have no job and would wait until a push or relink.
- **Up:** one `DO` block, one organization at a time (same reason as 21-01: `trg_assert_tenant`, `FORCE ROW LEVEL SECURITY`, and the job trigger's read of `repositories`):
  ```sql
  PERFORM set_config('app.current_tenant', org.id::text, true);
  INSERT INTO public.ingestion_jobs (organization_id, repository_id, job_type, state)
  SELECT r.organization_id, r.id, 'full_ingest', 'queued'
  FROM public.repositories r
  WHERE r.organization_id = org.id
    AND r.sync_state IN ('pending','syncing')
    AND r.installation_id IS NOT NULL
  ON CONFLICT (repository_id) WHERE state IN ('queued','running') DO NOTHING;
  UPDATE public.repositories SET sync_state = 'pending', updated_at = NOW()
  WHERE organization_id = org.id AND sync_state = 'syncing' AND installation_id IS NOT NULL;
  ```
  - **The `syncing` branch:** production code never writes `syncing` today, so it should match nothing. It exists so that no row can be stranded in `syncing`.
  - **Uninstalled installations:** skip repositories whose installation has `uninstalled_at` set. Join `github_installations` under the same tenant.
- **Down:** a deliberate no-op (`SELECT 1;`), with a comment. Deleting jobs on rollback would discard work.
