<objective>
Write the Python consumer's state transitions as plain, tested functions over psycopg2:

| Transition | What it does |
|---|---|
| **claim** | takes the next job and its lease |
| **mark_started** | writes the `syncing` projection |
| **complete** | runs the rerun follow-up; accepts an in-transaction result writer for Phase 22 |
| **fail** | capped, jittered backoff; `dead` directly on the last attempt |
| **defer** | puts a job back without using up an attempt (suspended installation) |
| **abandon** | supersedes a job that can never run (uninstalled installation, or no installation) |
| **sweep** | moves exhausted jobs to `dead` |
| **resolve run** | finds or creates the ingestion run (W6) |

**Every terminal write is fenced on the lease (L3).** No long-running process yet; that comes in 21-06.

Output: `workers.jobs`, and integration tests against a real Postgres.
</objective>

**Use the SQL 21-02 proved, copied verbatim from `pkg/jobs/schema_test.go`.** It covers:
- the claim, the sweep, and the fenced failure write
- `clearRerunSQL` (W4) and `resolveRunSQL` (W6)
- the enqueue upsert

**Order matters (W5, corrected in 21-02).** Re-enqueueing before the completion write raises nothing: the rerun is lost silently.

**Two connection modes, never mixed.**
- **Unscoped:** the claim, the sweep and the lease-only writes touch only `ingestion_jobs`, which has no RLS. They run on a plain connection with no tenant.
- **Tenant-scoped:** everything that touches a table with RLS, or enqueues, runs inside `require_tenant(conn, job.organization_id)`. The enqueue needs this because the tenant trigger must see the repository (21-02). This covers the projection, run resolution, result writes, the rerun enqueue and the installation read.
- **`require_tenant` refuses a connection that isn't idle** (`tenant.py`). Finish the unscoped claim transaction before entering tenant scope.

**Worker identity (a 21-CONTEXT open question, settled here).** `lease_owner` is a UUID4 string generated when the worker starts. Hostname plus PID repeats across container restarts.

**Backoff (open question, settled here).**
- **Formula:** the delay before the next attempt, after attempt `n` fails, is `min(60 s × 4^(n-1), 60 min)`, multiplied by a random factor in [0.5, 1.0].
- **Total wait:** with `max_attempts = 5`, at most about 81 minutes.
- **Implementation:** a small pure function with its own unit test. tenacity's `wait_random` *adds* jitter and cannot produce a multiplier, so don't use it here.

**The `sync_state` projection.** Documented in the module docstring and in 21-07's docs:

| Transition | `sync_state` |
|---|---|
| claim | not written (the installation check comes first) |
| mark_started (`running`) | `syncing` |
| complete | `synced`, plus `last_synced_at = NOW()` |
| fail, retrying (`queued`, `attempts > 0`) | `failed` |
| fail, `dead` | `failed` |
| defer (suspended installation) | unchanged |
| abandon (uninstalled, or no installation) | `never_synced`, matching the webhook stand-down; never `failed` (see `github_webhook_events.go:164-167`) |
| superseded by a producer | not written (the replacing enqueue writes `pending`) |

"Currently retrying" and "dead" are told apart by the job's state, not by `sync_state`.

**`PostgresWriter.create_ingestion_run` has no `ON CONFLICT`.** A repeat of the same commit raises `23505` today.
- The resolve helper here fixes that for jobs. **Do not change `PostgresWriter` in this plan.**
- Phase 22 owns two related changes: wiring the pipeline to runs, and making chunk writes idempotent per run (delete by run, then insert; see the research doc's "What the transaction actually buys"). Note both in the summary.

**`last_error` must never contain credentials or tokens.**
- Truncate it to 2,000 characters.
- Redact anything matching the `ghs_`, `ghp_`, `github_pat_` or `sk-` token patterns before writing.
- Test it.

```python
@dataclass(frozen=True)
class Job:
    id: UUID; organization_id: UUID; repository_id: UUID; job_type: str
    attempts: int; max_attempts: int; needs_rerun: bool; payload: dict | None

class LeaseLost(Exception): """Our fenced write matched no row: reclaimed or superseded."""

def claim(conn, worker_id: str, lease: timedelta) -> Job | None
def mark_started(conn, job: Job, worker_id: str) -> None
def complete(conn, job: Job, worker_id: str,
             write_results: Callable[[cursor], None] | None = None) -> bool  # True if a rerun was enqueued
def fail(conn, job: Job, worker_id: str, error: BaseException) -> str  # "queued" | "dead"
def defer(conn, job: Job, worker_id: str, delay: timedelta, reason: str) -> None
def abandon(conn, job: Job, worker_id: str, reason: str) -> None
def sweep(conn) -> int
def resolve_ingestion_run(cur, repository_id, commit_sha, branch) -> UUID
def next_run_after_delay(attempts: int, rng=random.random) -> timedelta
def sanitize_error(error: BaseException) -> str
```

**`claim`:** one short unscoped transaction running the proven claim query. Return `None` if no row comes back. It writes no projection.

**`mark_started`:** tenant-scoped. Write `syncing`, fenced through the job, so a worker that has lost its lease writes nothing:
```sql
UPDATE repositories SET sync_state = 'syncing', updated_at = NOW()
WHERE id = $repo
  AND EXISTS (SELECT 1 FROM ingestion_jobs
              WHERE id = $job AND lease_owner = $worker AND state = 'running')
```

**`complete`:** one tenant-scoped transaction, in this order:
1. **`write_results(cur)`,** if given. This is Phase 22's chunk write, committing together with completion.
2. **`clearRerunSQL`** (W4), fenced. Note whether a row came back.
3. **The fenced completion write:** `state = 'completed'`, lease cleared, `WHERE id AND lease_owner AND state = 'running'`. **If it touches zero rows, raise `LeaseLost`,** so the transaction rolls back and no results are committed for a job we no longer own.
4. **The projection:** `synced` and `last_synced_at`.
5. **If a rerun was flagged,** enqueue one `incremental` job with the upsert. This must come **after** step 3 (W5).

**`fail`:** one tenant-scoped transaction.
- The proven fenced write sets `dead` if `attempts >= max_attempts`, otherwise `queued` with `run_after = NOW() + next_run_after_delay(attempts)`.
- Also write `last_error = sanitize_error(error)`, clear the lease, and set the projection to `failed`.
- Zero rows → `LeaseLost`.

**`defer`:** one tenant-scoped transaction. The fenced write gives the attempt back (the claim incremented it):
```sql
UPDATE ingestion_jobs
SET state = 'queued', attempts = attempts - 1, run_after = NOW() + $delay,
    lease_owner = NULL, lease_expires_at = NULL, last_error = $reason, updated_at = NOW()
WHERE id = $job AND lease_owner = $worker AND state = 'running'
```
- The projection is unchanged. Zero rows → `LeaseLost`.
- A suspended installation therefore never exhausts its attempts or becomes `dead`.

**`abandon`:** one tenant-scoped transaction.
- Fenced write: `state = 'superseded'`, lease cleared, `last_error = $reason`.
- Projection: `never_synced`. Zero rows → `LeaseLost`.
- Uninstall means "nothing to do", not "failed", so this does not retry.

**`sweep`:** the proven sweeper, unscoped. Return the count, and log each job moved to `dead` with its id, repository and attempts.

**`resolve_ingestion_run`:** the W6 upsert. The caller sets `ingestion_jobs.ingestion_run_id`, fenced, in the same transaction.

**Logging.** Log every transition with `logging.getLogger(__name__)`, as the workers do: job id, organization, repository, attempt, and the from/to state.

- Tests that need extra connections build them from the container DSN under `SET ROLE rag_doc_app`, as `test_query_engine_isolation.py` does.

**Tests, one behaviour each:**
- **Happy path:**
  - enqueue, then `claim` → `running`, `attempts = 1`, and `sync_state` still `pending`
  - `mark_started` → `syncing`
  - `complete` → `completed`, `synced`, `last_synced_at` set
- **Rerun follow-up:** `needs_rerun` set while running → `complete` returns True, and exactly one new `queued` `incremental` job exists.
- **Fencing, reclaimed:**
  - worker A claims; expire the lease via SQL; worker B claims
  - A's `complete` raises `LeaseLost`, and **the probe row A's `write_results` wrote is rolled back**
  - A's `mark_started` writes nothing
  - B is unaffected
- **Fencing, superseded:** claim, then mark the job `superseded` via SQL. `complete`, `fail`, `defer` and `abandon` each raise `LeaseLost`, and the state stays `superseded`.
- **Retry:** `fail` below max → `queued`, `run_after` within the formula's jitter bounds, `last_error` redacted, lease cleared, `sync_state = failed`.
- **Dead:** at `attempts = max_attempts`, `fail` → `dead`.
- **Defer:** after `defer`, `attempts` is back to its pre-claim value, `run_after` is pushed out, and `sync_state` is unchanged. After deferring `max_attempts + 2` times in a row (claim, then defer), the job is still `queued`, not `dead`.
- **Abandon:** `superseded`, `sync_state = never_synced`, and the sweeper leaves it alone.
- **Sweeper:**
  - a `queued` job at max attempts → `dead`
  - a lease-expired `running` job at max attempts → `dead`
  - a `running` job with a live lease → **not** `dead`
- **Run resolution:** called twice for the same repository and commit, it returns the same id.
- **Tenant scope:** completing org A's job cannot change org B's repository projection. Assert under org B's scope that its row is unchanged.
