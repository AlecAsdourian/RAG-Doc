**Facts this plan rests on (fact-checked against the code 2026-09-14).**

**How tenancy works today:**
- **Derived, not stored.** `repositories` has no `organization_id`. A repository reaches its tenant through `project_id → projects.organization_id`. The 000008 policy is `FOR ALL USING (…EXISTS via projects…)`. A `FOR ALL` policy without `WITH CHECK` also applies to written rows, so RLS already refuses a cross-organization re-parent (D5).
- **`projects` has neither RLS nor the tenant trigger** (000008 covers six tables; see the 000009 header). A trigger can always read `projects`.
- **The only writer of `projects.organization_id` is 000010's one-time backfill** (line 62; grep of `services/`). No application code moves a project between organizations.

**Why 000012's backfill can't be copied here:**
- **`repositories` carries `trg_assert_tenant` (000009, lines 49-66).** Any INSERT, UPDATE or DELETE with `app.current_tenant` unset or `''` raises `42501`. That applies to superusers too, and lifting `FORCE ROW LEVEL SECURITY` does not help.
- **000012's pattern wrote into `github_installation_tenants`, which has no such trigger.** Copied here, it passes on CI's empty database and fails on any database with rows.
- **So the backfill sets the tenant one organization at a time,** inside a single `DO` block. That satisfies both `trg_assert_tenant` and `FORCE ROW LEVEL SECURITY` **without lifting either guard**.

**How to prove the backfill filled every row:**
- **A `SELECT … WHERE organization_id IS NULL` check proves nothing.** Run under `FORCE ROW LEVEL SECURITY` with no tenant, it sees zero rows and passes.
- **Use `ALTER COLUMN … SET NOT NULL` instead.** Its validation scan is not subject to row-level security, so it fails if any row was missed. Don't trust this sentence: the mutation checks in Task 1 show it on seeded data.
- **Afterwards, the session's `app.current_tenant` is `''` (ISS-013).** Nothing after the `DO` block in this migration may run DML against a table with row-level security; DDL is fine.

**This plan follows D5's intent with a stronger guarantee than the one D5 names.** Flag it in the PR description.
- **What D5 asks for:** "a trigger on the parent that keeps it in step", plus `reject_cross_org_reparent`.
- **The guarantee here is a composite foreign key instead:** `repositories (project_id, organization_id) REFERENCES projects (id, organization_id)`.
- **Why it's stronger:** foreign-key checks bypass row-level security, so the key holds even where a trigger's read would be filtered. It also makes a project's organization unchangeable while it has repositories. Nothing changes it today.
- **The triggers remain,** to fill the column on insert and to give readable errors. D5's `reject_cross_org_reparent` is transcribed verbatim.
- **This closes L5's latent "drift on re-parent" item** at the repository level. Once 21-02 lands, jobs → repositories → projects is enforced by foreign keys end to end. Record that in the summary.

**Constraints on how migrations are written:**
- **Numbering.** The highest existing migration is `000012`. golang-migrate keys on the integer, and a duplicate is a hard error.
- **No `GRANT`s.** `rag_doc_app` is a test-harness role only (`000010` line 140).
- **Plain SQL.** The Python isolation harness applies every `*.up.sql` in order through psycopg2 (`conftest.py`, `parents[3]`).

**Existing writers to `repositories`.** None supplies `organization_id`, and all must keep working unchanged; the trigger fills the column. If any of them fails, the migration is wrong, not the writer.
- `RepositoriesHandler.Connect` (`repositories.go`)
- `isolation.WithTwoOrgs` (`fixtures.go`)
- `pkg/auth/testing.go:223`
- `pkg/auth/provisioning_isolation_test.go:120`
- `pkg/testing/isolation/db_assertion_test.go:49`

**Out of scope:** simplifying `repositories`' RLS policy to scalar equality on the new column. D5 names that as a consequence worth having, but changing an RLS policy deserves its own isolation review. Note it in the summary as a follow-up.

  <action>
**Up**, in this order:

1. **Add the column,** nullable for now: `ALTER TABLE repositories ADD COLUMN organization_id UUID;`.
2. **Key `projects` for the composite reference:** `ALTER TABLE projects ADD CONSTRAINT projects_id_org_key UNIQUE (id, organization_id);`.
3. **Backfill, one organization at a time,** in a single `DO` block:
   ```sql
   DO $$
   DECLARE org RECORD;
   BEGIN
     FOR org IN SELECT id FROM public.organizations LOOP
       PERFORM set_config('app.current_tenant', org.id::text, true);
       UPDATE public.repositories r
       SET organization_id = p.organization_id
       FROM public.projects p
       WHERE p.id = r.project_id
         AND p.organization_id = org.id
         AND r.organization_id IS NULL;
     END LOOP;
   END $$;
   ```
   Comment above it:
   - why one organization at a time: `trg_assert_tenant` plus `FORCE ROW LEVEL SECURITY`
   - that no guard is lifted
   - why 000012's pattern does not apply
   - the ISS-013 note: no DML against a row-level-security table after this block
4. **Prove it:** `ALTER TABLE repositories ALTER COLUMN organization_id SET NOT NULL;`. Comment that this is the proof, and why a `SELECT` check would not be.
5. **The guarantee:** `ALTER TABLE repositories ADD CONSTRAINT repositories_project_org_fkey FOREIGN KEY (project_id, organization_id) REFERENCES projects (id, organization_id) ON DELETE CASCADE;`.
   - Keep the existing `project_id` foreign key.
   - Comment that this key, not a trigger, is what makes drift unrepresentable, because foreign-key checks bypass row-level security.
6. **The key 21-02 references:** `ALTER TABLE repositories ADD CONSTRAINT repositories_id_org_key UNIQUE (id, organization_id);`.
7. **Fill-and-guard trigger** `repositories_organization_id_guard()`, with `SET search_path = public, pg_temp` and a schema-qualified body.
   - **Attachment:** `trg_repositories_organization_id` runs `BEFORE INSERT OR UPDATE OF organization_id`.
   - **INSERT:** look up `p.organization_id` for `NEW.project_id`.
     - If no project is found, return `NEW` and let the `project_id` foreign key reject it. Don't raise a message for a case the FK already words.
     - If `NEW.organization_id` is NULL, set it from the project. That is the normal case.
     - If it differs from the project's, `RAISE` with a readable message.
   - **UPDATE:** if `NEW.organization_id IS DISTINCT FROM OLD.organization_id`, `RAISE` with "organization_id is maintained by the database; move the repository's project instead".
   - **Branch on `TG_OP` explicitly.** `OLD` is undefined in an INSERT trigger; D5 records that bug being shipped once.
8. **Transcribe D5's `reject_cross_org_reparent()` and `trg_reject_cross_org_reparent`** verbatim from `DECISIONS.md` (§D5), including the UPDATE-only guard and its comment.
   - **Same-organization re-parent:** `NEW.organization_id` carries over, and the composite FK accepts it.
   - **Cross-organization re-parent:** D5's trigger raises first, so the error is readable.
9. **`COMMENT ON COLUMN repositories.organization_id`:**
   - it is a copy of `projects.organization_id`, guaranteed by `repositories_project_org_fkey` and filled by trigger (D5)
   - it is an **authorization input**: 21-02's composite FK and the worker's tenant scope rely on it
   - application code never writes it

**Down:** drop both triggers and functions, both constraints on `repositories`, `projects_id_org_key`, and the column, in reverse order.

**Test setup:**
- Use `SetupTestDB` and `WithTwoOrgs`. Run writes under the app role in a tenant transaction, as production does.
- **When a test needs superuser access,** take a dedicated connection from the pool and `RESET ROLE`. The session user is the `isolation` superuser (`container.go:67-69`).
- **Never use `session_replication_role = replica`** (as `pkg/auth/testing.go:60-62` does). It disables foreign-key checks, which several of these tests exist to prove.

**One behaviour per test:**
1. **Insert without the column:** a repository inserted under org A's scope gets org A's id.
2. **Insert with the wrong tenant:** supplying org B's id for org A's project fails with the trigger's message.
3. **The guarantee does not depend on the trigger:** repeat test 2 as superuser, in a transaction with `trg_repositories_organization_id` disabled. It fails with SQLSTATE `23503` from `repositories_project_org_fkey`. Roll back.
4. **Rewriting the column** (`UPDATE … SET organization_id = <org B>`) is rejected.
5. **Re-parent within the organization:** moving `project_id` to a second project in org A succeeds, and `organization_id` is unchanged. Create that project in the test.
6. **Re-parent across organizations:** moving `project_id` to org B's project fails with D5's message, and the row is unchanged.
7. **Moving a project with repositories to another organization** (`UPDATE projects SET organization_id = <org B>`, as the app role; `projects` has no RLS) fails with `23503`.
8. **D5's drift-detection check.** Put a helper `AssertNoRepositoryTenantDrift(t, pool)` in the isolation package. As superuser, it runs `SELECT r.id FROM repositories r JOIN projects p ON p.id = r.project_id WHERE r.organization_id IS DISTINCT FROM p.organization_id` and fails on any row. Call it at the end of tests 1-7. Later plans reuse it.
9. **The schema's shape:** `organization_id` is NOT NULL, and `repositories_id_org_key`, `repositories_project_org_fkey` and `projects_id_org_key` exist. Query `pg_constraint`.
