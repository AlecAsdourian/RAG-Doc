**⚠ A correction to the context, pinned here (fact-checked 2026-09-14).**
- **What the context says:** L4 and L7 say the wrong order raises `23505` (enqueue before supersede, or re-enqueue before completion).
- **What actually happens:** that is only true for a *plain* `INSERT`. Through L7's upsert, the only enqueue path, the conflict just sets `needs_rerun` on the old live job. The supersede or completion then removes that job from the live set, leaving the repository with **no live job and no error**.
- **The order is still mandatory.** The failure it prevents is silent lost work, which is worse than an error. The tests below pin both behaviours.

**No RLS, by decision (L5).**
- **Documenting it:** the table carries a `COMMENT ON TABLE` in the style of `github_installation_tenants` (000012:157-160). `github_webhook_deliveries` has only `--` header comments.
- **What the comment must say:** `organization_id` **is an authorization input**, and any request handler reading this table must filter by organization explicitly (21-07).
- **Existing tests need no change.** `db_assertion_test.go` checks a fixed `protectedTables` list (:42), and `container_test.go` checks a minimum table count. **Do not** add `ingestion_jobs` to `protectedTables`: it has no RLS and no `trg_assert_tenant`, by design.

**The tenant trigger reads `repositories`, which has FORCE RLS.**
- So a write to `ingestion_jobs` must run under the job's tenant scope, or the trigger cannot see the repository.
- **Without a tenant the error depends on connection history (ISS-013):**
  - `app.current_tenant` unset → the read finds nothing → the trigger raises "does not exist"
  - a connection that earlier committed a `SET LOCAL` holds `''` → the read raises `22P02`
- Pin both, so nobody later "fixes" the trigger instead of scoping the enqueue.

**`ingestion_runs` already has `UNIQUE (repository_id, commit_sha)`** (000002). The retry rule (W6) needs only the resolve upsert, tested here and used in 21-05.

**Superuser access in tests.**
- Take a dedicated connection from the pool and `RESET ROLE`; the session user is the `isolation` superuser (`container.go:67-69`).
- **Never use `session_replication_role = replica`.** It also disables foreign-key checks, which W1 exists to prove.

**No `GRANT`s.**

- `enqueueUpsertSQL`, exactly L7's form:
  ```sql
  INSERT INTO ingestion_jobs (organization_id, repository_id, job_type, state)
  VALUES ($1, $2, $3, 'queued')
  ON CONFLICT (repository_id) WHERE state IN ('queued','running')
  DO UPDATE SET needs_rerun = TRUE, updated_at = NOW()
  RETURNING id, (xmax <> 0) AS was_existing;
  ```
- `claimSQL`, `sweepSQL` and `failSQL`, from the research doc
- `clearRerunSQL` (W4)
- `resolveRunSQL` (W6)

**Tests, one behaviour each:**
- **W1 — the composite FK makes a tenant mismatch unrepresentable.**
  - On a superuser connection, in a transaction: `ALTER TABLE ingestion_jobs DISABLE TRIGGER trg_ingestion_jobs_tenant`.
  - Insert a job whose `organization_id` differs from its repository's. It fails with `23503` from `ingestion_jobs_repo_tenant_fk`.
  - Roll back.
- **Tenant trigger message:** the same mismatch, trigger enabled, under the tenant, fails with the trigger's message.
- **One live job per repository:**
  - a plain `INSERT` of a second `queued` job while one is live raises `23505`
  - after the first job is `completed`, a new one inserts
- **W2 — the upsert parses and reports correctly:**
  - first call → `was_existing = false`
  - second call → `true`, and `needs_rerun` is set
  - `ON CONFLICT DO UPDATE` with no target → `42601`
  - `ON CONFLICT (repository_id)` without the index predicate → `42P10`
- **W3 — a bulk enqueue racing a live job handles every row.**
  - One multi-row statement over three repositories, one already live.
  - Result: 1 flagged, 2 inserted, and all 3 have exactly one live job.
- **W4 — the conditional clear reports a rerun.** With `needs_rerun = true`:
  - the fenced `clearRerunSQL` returns one row
  - the naive `RETURNING needs_rerun` form yields `false`
- **W5 — completion then re-enqueue.**
  - **The right order,** in one transaction: complete, then run the upsert → a new live job, no error.
  - **The wrong order, through the upsert:** upsert, then complete → **no error, and no live job afterwards**. The rerun is lost silently; this is the corrected failure mode.
  - **The wrong order, through a plain `INSERT`:** → `23505`, the failure mode the context recorded.
- **W6 — a retry reuses its run.** `resolveRunSQL` returns the **same** id twice for the same repository and commit, and a different id for a different commit.
- **L4 — supersede before enqueue.** With a `running` job:
  - supersede then upsert, in one transaction → the old job `superseded`, one new `queued` job
  - upsert then supersede, **through the upsert** → no error, no live job
  - upsert then supersede, through a plain `INSERT` → `23505`
- **Enqueueing needs tenant scope.** The upsert under the app role without a tenant fails in two ways (ISS-013):
  - on a **fresh** connection (`pgx.Connect` plus `SET ROLE`) → the trigger's "does not exist"
  - on a connection that has committed a `SET LOCAL` → `22P02`
  - Pin both.
- **Claim,** run against each of:
  - a `queued` job with `run_after` in the past → claimed, `attempts` incremented
  - a `running` job whose lease has expired → reclaimed
  - a `running` job with `lease_expires_at IS NULL` → reclaimed
  - a job at `attempts = max_attempts` → **not** claimed
- **Sweeper:**
  - a `queued` job at max attempts → `dead`
  - a `running`, lease-expired job at max attempts → `dead`
  - a `running` job with a live lease → **not** `dead`
- **Drift:** call 21-01's `AssertNoRepositoryTenantDrift` at the end of the suite.

**Mutation checks,** each confirming a test fails. Record the results.
- remove the predicate from the upsert's `ON CONFLICT`
- drop `AND attempts < max_attempts` from the claim
- drop the `state = 'queued'` branch from the sweeper
- drop `lease_expires_at IS NULL` from the claim
- make the unique index non-partial
