<objective>
Build one Go producer package with two functions:
- **`Enqueue`** — L7's per-row upsert, for one repository or many.
- **`SupersedeLive`** — L4's cancel-before-enqueue step.

**What Connect does today** (`repositories.go`; line numbers fact-checked 2026-09-14):
- **Two transactions.**
  - tx1 is a read-only installation lookup, around line 415.
  - `ListInstallationRepositories` then runs outside any transaction, around 452. This is deliberate.
  - tx2 is the only write, around 475-637.
- **Inside tx2, the decision to set a repository to `pending` is made in SQL `CASE` expressions:**
  - the adopt `UPDATE`, around 552-580, uses the rule "installation changed, or `github_repo_id IS NULL`"
  - the `INSERT … ON CONFLICT`, around 595-636, uses "installation changed"
- **Neither reports whether this call changed anything.** `RETURNING` gives the resulting `sync_state`, so "already pending" and "just re-queued" look the same.
- **The org-wide lookup of an existing row** joins `projects`, around 537-546.
- **A comment around 615-620 admits the ISS-016 race.**

**Where the enqueue goes.** It belongs in tx2, after the row write, so it commits atomically with it. This answers a 21-CONTEXT open question; it was confirmed by reading the code.

**Who writes `sync_state` after this phase.** L2 says it is "written by the job". Read that as the job's lifecycle:
- **Enqueue** (the producer, in the same transaction) writes `pending`.
- **Worker transitions** write the rest (21-05).
- **Webhook stand-downs** keep writing `never_synced`. That describes the installation, not a job (21-04).

| Event | Written by | `sync_state` |
|---|---|---|
| enqueue of a new job | producer, same transaction | `pending` |
| upsert flags an existing live job | nobody | unchanged |
| claim, after the installation check | worker | `syncing` |
| completion | worker | `synced` |
| failed attempt (retrying) | worker | `failed` |
| job dead | worker | `failed` |
| superseded by a relink | nobody | the replacing enqueue writes `pending` |

**Idempotent reconnect keeps today's behaviour.** Reconnecting a repository already connected to the same installation, with `github_repo_id` set, enqueues nothing.

**The CI isolation gate will not check this change.** The scanner only inspects route lines added in the diff (`check-isolation-tests.py:9-12, 545-561`), and `router.go:413` doesn't change. The tenant-boundary tests below are written deliberately, not to satisfy the gate.

**Logging.** Use `slog`, as the handlers do. Log enqueue outcomes with repository and organization ids, and never tokens.

```go
type JobType string // "full_ingest" | "incremental"

type EnqueueRequest struct {
    OrganizationID string
    RepositoryID   string
    JobType        JobType
}

type EnqueueResult struct {
    RepositoryID string
    JobID        string
    WasExisting  bool // true: a live job already existed and was flagged needs_rerun
}

// Both take the caller's transaction: the caller owns atomicity and tenant scope.
func Enqueue(ctx context.Context, tx pgx.Tx, reqs []EnqueueRequest) ([]EnqueueResult, error)
// SupersedeLive returns the repository ids whose live job it superseded.
func SupersedeLive(ctx context.Context, tx pgx.Tx, repositoryIDs []string) ([]string, error)
```

**`Enqueue`:**
- **One statement:** 21-02's `enqueueUpsertSQL` in set form, e.g. `INSERT … SELECT … FROM unnest($1::uuid[], $2::uuid[], $3::text[])` with the same `ON CONFLICT (repository_id) WHERE state IN ('queued','running')` clause. `RETURNING` includes `repository_id` and `was_existing`.
- **Validate before running:** reject an invalid job type, or a non-canonical UUID.
- **De-duplicate `RepositoryID` first.** `ON CONFLICT DO UPDATE` cannot touch the same row twice in one statement, and raises `21000` if asked to.
- **Write the projection in the same transaction:** `UPDATE repositories SET sync_state = 'pending', updated_at = NOW() WHERE id = ANY(<ids where was_existing = false>)`.
- **Prove the set form before relying on it** by running W3's scenario through it. 21-02 proved only the multi-row `VALUES` form.

**`SupersedeLive`:** `UPDATE ingestion_jobs SET state = 'superseded', updated_at = NOW() WHERE repository_id = ANY($1) AND state IN ('queued','running') RETURNING repository_id`.

**Both doc comments state the L4 contract:** supersede, then enqueue, in one transaction. Getting the order wrong raises nothing; it silently leaves no live job (21-02 corrected this).

**Tests** (harness, app role, tenant transactions):
- **Single enqueue:** one `queued` job, `WasExisting=false`, projection `pending`.
- **Second enqueue:** `WasExisting=true`, `needs_rerun=true`, still one live job.
- **Bulk enqueue with one repository already live:** a result per row, all live, and the live repository's projection unchanged.
- **Duplicate ids in the input:** de-duplicated, no `21000`.
- **Supersede then enqueue in one transaction:** returns the superseded repository id; the old job `superseded`, the new one `queued`.
- **Wrong tenant** (org B's repository under org A's scope): an error, and nothing written.
- **A race through a barrier,** per `container_concurrency_test.go`:
  - **Setup:** 16 goroutines, each with its own transaction, released together to enqueue the same repository.
  - **Assert:** every call succeeds, exactly one `WasExisting=false`, and exactly one live job.
  - **Repeat:** 5 rounds on a warm pool. A single cold round proves nothing (21-CONTEXT).
- **Drift:** end with `AssertNoRepositoryTenantDrift`.

**Restructure tx2** so the decision is made in Go, not hidden in SQL `CASE` expressions:

1. **Lock the existing row, if any.** Use the org-wide lookup (around 537-546) with **`FOR UPDATE OF r`**. Plain `FOR UPDATE` would also lock the joined `projects` row and serialize every connect in the organization. Read `installation_id` and `github_repo_id`.
2. **Classify the call:**
   - `new`: no row
   - `relink`: the installation changed, or `github_repo_id IS NULL`
   - `unchanged`: anything else
3. **Write the row** (the adopt `UPDATE` or the `INSERT`) without touching `sync_state`. The producer's projection writes it.
4. **Act on the classification:**
   - `new` → `Enqueue(full_ingest)`
   - `relink` → `SupersedeLive`, then `Enqueue(full_ingest)`
   - `unchanged` → nothing
5. **Keep the response shape.** `sync_state` in the response must reflect the value after the transaction: re-read it, or return it from the write.

**Replace the ISS-016 comment** with a short pointer to L4 and the partial unique index.

**Keep tx1 and the GitHub call outside the write transaction.** Holding a transaction open across a network call is what the current structure deliberately avoids.

**Tests** (`repositories_connect_test.go`):
- **New repository:** one `queued` `full_ingest` job, `sync_state = pending`.
- **Reconnect to the same installation:** no new job; the existing job untouched.
- **Relink while a job is `running`** (set via SQL): the old job `superseded`, one new `queued` job, one live job.
- **Two concurrent relinks of the same repository through a barrier:** both responses 2xx and exactly one live job (L8), over several rounds.
- **Concurrent connects of two different repositories in the same organization:** neither blocks the other. This pins `FOR UPDATE OF r`.
- **Tenant boundary:** a connect under org A never produces a job carrying org B's id. Assert with explicit `organization_id` filters, since the table has no RLS.

**`docs/api-repositories.md`:** `sync_state` is now a projection of job state, not a queue. Include the table above.
