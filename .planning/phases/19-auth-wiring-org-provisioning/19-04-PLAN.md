> # REVISION NOTICE — 2026-09-08, before execution
>
> This plan was written before 19-03 executed, and it assumes a **Supabase Auth Hook** that does not and cannot exist: the hook is a Postgres function inside Supabase's database, and `organization_memberships` lives in a different Postgres instance. Every "via the 19-03 hook" reference below is wrong — the claim is written by the backend through the admin API instead.
>
> Three consequences, in increasing order of severity:
>
> **1. The membership check in `Select` is not defense-in-depth. It is the only check.**
> Task 1 says to avoid a membership check because "the hook already handles missing/mismatched memberships". There is no hook, and nothing else validates. Without this check any authenticated user could put themselves in any organization by POSTing its id — reintroducing, through a new door, exactly the vulnerability 19-03 closed. It is load-bearing, and it gets a test that fails without it.
>
> **2. Writing only `organization_id` is a privilege escalation.** VERIFIED against the live project, 2026-09-08:
>
> ```
> admin PUT {app_metadata:{organization_id:X, organization_role:"member"}} → refresh → role=member
> admin PUT {app_metadata:{organization_id:Y}}          (role omitted)     → refresh → role=member  ← STALE
> ```
>
> The admin API merges, so an omitted key keeps its old value. The sketch in Task 1 writes only `organization_id`. A user who is `owner` of orgA and `member` of orgB would switch to orgB carrying `organization_role: "owner"`. Nothing reads the role today, which is the only reason this is not currently exploitable — and exactly why it would have shipped unnoticed. **`Select` must write both keys, sourced from the membership row it just validated.**
>
> **3. `is_active` cannot come from `OrgIDKey` if `List` sits outside `TenantMiddleware`.** Sub-step B says to move these routes out of the tenant group; Sub-step A reads `auth.OrgIDKey`, which only `TenantMiddleware` sets. Both cannot be true. Resolved by reading the claim off the token directly (`auth.TokenKey`) — which also makes scenario 4 reachable, since a user with no org claim must get an empty list rather than the 403 `TenantMiddleware` would return.
>
> **Also corrected:** `WithTwoOrgs` exposes `OwnerID` as the internal `users.id`, and existing tests sign JWTs with it. In production the `sub` claim is the **Supabase** user id, which is what `users.supabase_user_id` stores. Nothing noticed because `UserIDKey` is written by the middleware and read nowhere — 19-04 is its first consumer. The fixture now exposes the Supabase ids, and these tests sign with those.
>
> **Verified good, no change needed:** `session.refresh()` genuinely re-reads `raw_app_meta_data` (same probe). Task 3's frontend contract is correct as written: 202 → `refreshSession()` → new claim; no sign-out/sign-in needed.

<objective>
Give multi-org users the backend endpoints to see their org memberships and switch their active org. Switching updates `raw_app_meta_data.organization_id` in Supabase; the frontend calls `session.refresh()` to receive a new JWT with the updated claim. No server-side session state.

Purpose: today a user provisioned in 19-02 has exactly one org (their auto-created starter). This phase makes the multi-org story real: if a user is invited into another org (invitation flow ships later — Phase 20+), they can list every org they belong to and pick one as active. The JWT claim reissue via Supabase's `session.refresh()` closes the loop cleanly per user decision (JWT-scoped over session-scoped).

Output: `GET /api/user/organizations` and `POST /api/user/select-organization` mounted, tested, isolated. Frontend contract documented; frontend UI work stays deferred to Phase 23.
</objective>

**Constraining decisions (from 19-CONTEXT and user Q&A):**
- **JWT-scoped active-org.** Switching updates `raw_app_meta_data`; frontend `session.refresh()` gets a new access token via the 19-03 hook. No Redis, no cookie, no cross-request server state.
- **Membership validation is authoritative on the backend, not on the client.** `POST /api/user/select-organization` reads Supabase Admin API to update `raw_app_meta_data` — but only after the backend confirms the target org id is one the user belongs to. Client-tampered targets get 403.
- **Supabase Admin API access via Service Role Key.** Not the anon key. Env var already exists (`SUPABASE_SERVICE_ROLE_KEY`) — verify.
- **No return of a new JWT from POST /select-organization.** The endpoint returns 202 Accepted + instructions ("call session.refresh()"). Backend never mints or returns Supabase-signed tokens.

**Verification of upstream contract (ISS-002 pattern):**
Before writing new code, verify:
- Supabase Admin JS/Go SDK usage for updating `raw_app_meta_data`.
- Whether `session.refresh()` truly picks up new `raw_app_meta_data` on the next call, or requires a full sign-out/sign-in. If the latter, the endpoint documentation needs to reflect that.

`POST /api/user/select-organization`:
```go
type SelectOrgRequest struct {
    OrganizationID string `json:"organization_id" validate:"required,uuid"`
}

func (h *UserOrgsHandler) Select(w http.ResponseWriter, r *http.Request) {
    userID := r.Context().Value(auth.UserIDKey).(string)
    var req SelectOrgRequest
    // ... decode, validate

    // Confirm membership BEFORE calling Supabase Admin.
    var exists bool
    h.db.QueryRow(ctx, `
        SELECT EXISTS (
            SELECT 1 FROM organization_memberships om
            JOIN users u ON u.id = om.user_id
            WHERE u.supabase_user_id = $1 AND om.organization_id = $2
        )
    `, userID, req.OrganizationID).Scan(&exists)
    if !exists {
        render.Render(w, r, ErrForbidden())
        return
    }

    // Update raw_app_meta_data via Supabase Admin API.
    if err := h.supabaseAdmin.UpdateUserAppMetadata(ctx, userID, map[string]any{
        "organization_id": req.OrganizationID,
    }); err != nil {
        render.Render(w, r, ErrInternal(err))
        return
    }

    render.Status(r, http.StatusAccepted)
    render.JSON(w, r, map[string]string{
        "status": "org_updated",
        "next_action": "call session.refresh() on the client to receive a new JWT with the updated organization_id claim",
    })
}
```

**Sub-step B: Wire on router.** Inside the authenticated `/api` group (below the JWT + tenant middleware):

```go
userOrgsHandler := handlers.NewUserOrgsHandler(dbpool, supabaseAdmin)
r.Get("/api/user/organizations", userOrgsHandler.List)
r.Post("/api/user/select-organization", userOrgsHandler.Select)
```

Note: `List` doesn't strictly need `TenantMiddleware` (it operates on the user's memberships, not on tenant-scoped data). Move it OUT of the tenant-middleware group, into a "user-scoped" sub-group that has JWT auth but not tenant scope. `Select` similarly — it acts on the caller's user, not on any org's data.

Avoid: returning tokens or session cookies. The backend never mints Supabase JWTs.

Avoid: pre-validating the org id via a synchronous membership check inside the JWT hook — the hook already handles missing/mismatched memberships. The `Select` endpoint's membership check is defense-in-depth in case the hook is misconfigured or the Admin API race-conditions with a membership revocation.

Short document (~150 lines max) capturing the wire contract Phase 23 will implement against:

1. **Sign-in.** Frontend uses `supabase.auth.signInWithOAuth({ provider })`. On callback, JWT has `organization_id` and `organization_role` claims (via 19-03 hook).
2. **Reading active org.** Frontend decodes the JWT to display the active org name/role. No API call needed for the current org.
3. **Listing orgs.** `GET /api/user/organizations` returns `[{id, name, slug, role, is_active}, ...]`.
4. **Switching org.**
   - `POST /api/user/select-organization` with `{"organization_id": "<uuid>"}`. Returns 202 or 403.
   - On 202: frontend calls `supabase.auth.refreshSession()`. New JWT contains the new claim.
   - Frontend re-renders with the new active org.
5. **Signing out.** Standard Supabase `signOut()`. No custom cleanup.
6. **Multi-org UX conventions (guidance for Phase 23):**
   - Show active org name in the header.
   - Org switcher dropdown lists results of `GET /api/user/organizations`.
   - After switch, hard-refresh the current page to re-run all queries under the new tenant.

Not covered here (Phase 20+):
- Org invitations
- Org deletion / member removal
- Role changes
