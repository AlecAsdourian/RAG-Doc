<objective>
Move tenant identity from the `X-Organization-ID` request header into a Supabase JWT custom claim, and refactor `TenantMiddleware` to read from the JWT. Hard cutover: the header path is removed in the same PR. Update every isolation test that pinned header-trust behavior to expect the JWT path instead.

Purpose: closes the tenant-spoofing vulnerability the header trust created. After 19-03, tenant scope is inseparable from the authenticated identity — you cannot present a valid JWT for one org while impersonating another via a header, because there is no header path anymore. This closes ISS-004 and ISS-007.

Output: Supabase Auth Hook injects `organization_id` and `organization_role` into every access token; `TenantMiddleware` reads them; `X-Organization-ID` header handling is gone; the 17-02 scenarios that documented the header-trust behavior flip to expect 403 (or JWT-validation failure).
</objective>

**Constraining decisions (from 19-CONTEXT and user Q&A):**
- **Hard cutover.** No feature flag. `X-Organization-ID` header handling is deleted, not deprecated.
- Supabase Auth Hook (SQL function `custom_access_token_hook`) is the injection point. Alternative — post-signup patch of `raw_app_meta_data` and force refresh — is racier and rejected here.
- Membership check happens INSIDE the hook, not in the middleware. If a user isn't a member of their claimed org, the hook refuses to issue a token with that org id.
- Backend middleware trusts the JWT claim wholesale (it's server-issued and signature-verified via JWKS). No separate DB membership check per-request.
- The 17-02 isolation tests that used `testjwt.Sign(userID, orgID, "owner")` continue to work — that signer already emits `organization_id`/`organization_role` claims. Only the test harness's route-setup code changes: no more `X-Organization-ID` header on the test HTTP requests.

**Sub-step A: Write the hook.** Supabase's `custom_access_token_hook` is a SQL function that runs before every access token is issued. Signature: takes a JSONB argument with the claims-so-far, returns modified JSONB.

Create migration 000010:

```sql
CREATE OR REPLACE FUNCTION public.custom_access_token_hook(event JSONB)
RETURNS JSONB
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
    claims JSONB;
    user_supabase_id UUID;
    active_org_id UUID;
    active_org_role TEXT;
BEGIN
    claims := event->'claims';
    user_supabase_id := (event->>'user_id')::UUID;

    -- Look up the user's active org. Priority:
    --   1. If raw_app_meta_data.organization_id is set AND user has an active
    --      membership there, use it.
    --   2. Otherwise, fall back to the user's owner-role org (from provisioning).
    --   3. If neither exists, return claims unchanged; middleware will 403.
    SELECT om.organization_id, om.role
    INTO active_org_id, active_org_role
    FROM public.users u
    JOIN public.organization_memberships om ON om.user_id = u.id
    WHERE u.supabase_user_id = user_supabase_id
      AND om.organization_id = COALESCE(
          (SELECT (raw_app_meta_data->>'organization_id')::UUID
           FROM auth.users WHERE id = user_supabase_id),
          om.organization_id
      )
    ORDER BY (om.role = 'owner') DESC, om.created_at ASC
    LIMIT 1;

    IF active_org_id IS NOT NULL THEN
        claims := jsonb_set(claims, '{organization_id}', to_jsonb(active_org_id::TEXT));
        claims := jsonb_set(claims, '{organization_role}', to_jsonb(active_org_role));
    END IF;

    event := jsonb_set(event, '{claims}', claims);
    RETURN event;
END;
$$;

GRANT EXECUTE ON FUNCTION public.custom_access_token_hook TO supabase_auth_admin;
```

Down migration drops the function.

**Sub-step B: Register the hook via Supabase config.** This is a one-time UI step (Auth → Hooks → Custom Access Token → point at `public.custom_access_token_hook`). Document in `docs/supabase-setup.md`. This is not runnable via migration.

Avoid: putting the DB lookup on the request hot path via middleware. The hook runs once per token issue; subsequent requests read a signed JWT.

Avoid: reading `raw_app_meta_data` in a way that lets the client tamper. `raw_app_meta_data` is server-controlled; `raw_user_meta_data` is client-controlled. Use only the former for org id.

After:
```go
func TenantMiddleware(db *pgxpool.Pool) func(http.Handler) http.Handler {
    _ = db // TODO(17-03/ISS-008): wire request-scoped tenant tx here
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            token, ok := r.Context().Value(TokenKey).(jwt.Token)
            if !ok {
                http.Error(w, "missing token", http.StatusInternalServerError)
                return
            }
            orgID, err := ExtractOrganizationID(token)
            if err != nil {
                http.Error(w, "user has no active organization", http.StatusForbidden)
                return
            }
            role, err := ExtractOrganizationRole(token)
            if err != nil {
                http.Error(w, "user has no organization role", http.StatusForbidden)
                return
            }
            ctx := context.WithValue(r.Context(), OrgIDKey, orgID)
            ctx = context.WithValue(ctx, OrgRoleKey, role)
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}
```

The middleware chain also needs to add `OrgRoleKey`. Add both constants.
