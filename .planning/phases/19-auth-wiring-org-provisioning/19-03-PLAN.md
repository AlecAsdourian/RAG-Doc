> **REVISION NOTICE.** The original 19-03 plan (merged in PR #12) specified a
> Supabase Custom Access Token Hook — a PL/pgSQL function joining
> `public.users` to `public.organization_memberships` — to inject a top-level
> `organization_id` claim.
>
> **That design could not work.** Supabase and the application Postgres are
> two separate instances (`.env.example` points `SUPABASE_URL` at a hosted
> project while `DATABASE_URL` points at the docker-compose `postgres`
> service). An Auth Hook executes inside *Supabase's* database, where
> `public.organization_memberships` does not exist, so the function would
> have errored on every token issue.
>
> Caught before execution on 2026-09-07 while preparing the manual Studio
> step. This revision replaces the hook with the `raw_app_meta_data` carrier
> described below — which needs **no Supabase Studio configuration at all**
> and is the same mechanism 19-04 already assumed for org switching.

<objective>
Get the caller's organization into the JWT and make `TenantMiddleware` read it from there, then delete the `X-Organization-ID` header path entirely.

Mechanism: after provisioning succeeds, the backend writes `organization_id` and `organization_role` into the Supabase user's `raw_app_meta_data` via the Admin API. Supabase includes `raw_app_meta_data` in every issued JWT as the `app_metadata` claim, so the values arrive as `app_metadata.organization_id` / `app_metadata.organization_role` with no hook and no Studio step.

Purpose: closes the tenant-spoofing hole the header trust created. After 19-03, tenant scope is inseparable from the authenticated identity — there is no header path left to spoof. Closes ISS-004 and ISS-007.

Output: Supabase Admin API client; provisioning pushes org context to Supabase; middleware reads the nested claim; header path removed; the 17-02 scenarios that pinned header-trust behavior flipped.
</objective>

**Constraining decisions:**
- **No Auth Hook, no Studio configuration.** `raw_app_meta_data` is automatically surfaced by Supabase as the `app_metadata` JWT claim.
- **Claim path is nested:** `app_metadata.organization_id`, `app_metadata.organization_role`.
- **`raw_app_meta_data` only** — never `raw_user_meta_data`, which is client-writable and must not carry tenant identity.
- **Hard cutover.** The `X-Organization-ID` header is deleted, not deprecated. No feature flag.
- **Middleware trusts the claim wholesale.** It is server-issued and JWKS-signature-verified. The membership check happens at write time (when the backend sets `raw_app_meta_data`), not per-request.
- **Admin API failure must not strand the user.** Provisioning in our DB is the source of truth; the Supabase push is a projection. A failed push is logged and retried on the next webhook delivery or repaired by 19-04's select-organization endpoint.

**Verification of upstream contract (ISS-002 pattern):**
Before writing the middleware change, confirm empirically what Supabase actually emits. Decode a real access token from the configured project and verify `app_metadata` is present and carries what we wrote. If Supabase nests or renames differently than assumed, Task 2 adjusts to the observed shape rather than the documented one.
</context>

**Sub-step A: Admin client.** Create `pkg/auth/supabase_admin.go`:

```go
// AdminClient talks to Supabase's Admin API using the service-role key.
type AdminClient interface {
    UpdateUserAppMetadata(ctx context.Context, supabaseUserID string, meta map[string]any) error
}

type httpAdminClient struct {
    baseURL        string // SUPABASE_URL
    serviceRoleKey string // SUPABASE_SERVICE_ROLE_KEY
    httpClient     *http.Client
}
```

`UpdateUserAppMetadata` issues `PUT {baseURL}/auth/v1/admin/users/{id}` with body `{"app_metadata": {...}}`, headers `Authorization: Bearer <service-role-key>` and `apikey: <service-role-key>`. Supabase merges the supplied `app_metadata` keys rather than replacing the object wholesale — verify this empirically in Sub-step D and adjust (read-modify-write) if it replaces.

Interface + constructor so tests can inject a fake. Constructor panics on empty `serviceRoleKey`, matching the 19-01 fail-closed pattern for the webhook secret.

Timeouts: 10s. Never log the service-role key.

**Sub-step B: Push after provisioning.** In `webhook.go`'s `handleAuthUserEvent`, after the org exists (whether newly created or pre-existing), push:

```go
if err := h.admin.UpdateUserAppMetadata(r.Context(), event.SupabaseUserID, map[string]any{
    "organization_id":   orgID.String(),
    "organization_role": "owner",
}); err != nil {
    // Non-fatal: our DB is the source of truth. Log and continue —
    // the next webhook delivery or 19-04's select-organization repairs it.

        event.SupabaseUserID, err)
}
```

Note this needs the org id even on the replay path, so `handleAuthUserEvent` must resolve the user's owner org rather than only using the id returned by a fresh `CreateOrganizationForUser`.
